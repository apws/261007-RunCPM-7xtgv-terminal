== Objectives and constraints

* Keep the currently hardware-tested terminal/RunCPM behavior intact while
  making each product addition and its owner obvious by name and source path.
* Minimize changes to RunCPM-derived core headers. A generic, inert-by-default
  seam is preferable to a 7xtgv symbol in upstream code, but a copied CCP is
  an acceptable *local* choice until a cleaner extension has been proved.
* Permit serial-only RunCPM, integrated RunCPM plus terminal, and eventually
  terminal-only firmware for a UART-connected CP/M machine. Do not confuse a
  reserved build combination with an implemented one.
* *First clean our present fork against the recovered approximately 260126
  RunCPM*, keeping behavior unchanged and using searchable `++XTGV_++` names,
  better placement and narrow optional hooks. Retest that cleaned fork before
  attempting any replacement with current Mockba HEAD. The current HEAD is
  comparison evidence in this first step, not its implementation base.
* Preserve the recovered original CP/M 2.2 CCP commands in our local variant.
  A later port to current upstream and optional CP/M 3 is a distinct step,
  not a claimed working replacement now.
* Follow Mockba's destination-file style for core seams; in the product
  sketch, indent code within conditional branches consistently. Avoid a broad
  formatter pass over imported code.

== Explicit build modes and naming

Identifiers cannot start with a digit: use `++XTGV_++`, not `++7XTGV_++`.
The proposed composition flags are numeric 0/1 values, with
`++XTGV_RUNCPM=1++` and `++XTGV_TERMINAL=0++` as serial-only defaults.
The present display targets must explicitly request both as 1 *before*
inverting the existing `++!defined(RUNCPM_HEADLESS)++` branches.

[cols="1,1,3",options="header"]
|===
|`++XTGV_RUNCPM++` |`++XTGV_TERMINAL++` |Meaning
|1 |0 |Serial-only RunCPM, corresponding to the ordinary upstream-style sketch.
|1 |1 |Integrated RunCPM and TFT terminal; current product behavior.
|0 |1 |Standalone terminal using a physical UART to an external CP/M host; *reserved, not yet buildable*.
|0 |0 |Invalid; reject at compile/configuration time.
|===

`++XTGV_CCP_7XF++` is independent of display presence but valid only with
`++XTGV_RUNCPM++` and `++CCP_INTERNAL++`. It selects our CCP variant. Avoid
feature flags for every internal function: `++XTGV_TERMINAL_CONFIG++` can be
a searchable subsystem prefix/name without becoming another user-facing
build switch. Keep ordinary functions named `++xtgvTerminalConfig...++`
and `++xtgvTerminalHistory...++`; reserve macros for compile-time seams.

Target-aware build definitions must be explicit for *all* boards. At present
W535 is inferred from ESP32-S3 and RP2_2 from an RP2040-architecture fallback
in `++runcpm-config.h++`, while W550 and RP2_147 have explicit target flags.
A `++board.h++` dispatcher cannot distinguish future boards sharing an MCU
architecture unless the build identifies them. After migrating all target
profiles, reject unknown or conflicting target selections instead of silently
choosing a different panel. Maintain a serial-only profile separately; do
not let this flag migration change existing staged firmware images implicitly.

== Separate CCP 7XF: immediate preference and possible later seam

Petr prefers a separate, selectable `++ccp7xf.h++` *now*. Derive it from
our **current modified, recovered-era `++ccp.h++`**, initially by moving or
copying its code without changing behavior. Keep a recovered/original
`++ccp.h++` selectable beside it. Do *not* derive the first `++ccp7xf.h++`
from Mockba's 260824 HEAD; that would pull newer CCP, BDOS and disk
assumptions into what is meant to be a local cleanup. Only after this fork
is retested should a *separate* HEAD-port attempt adapt `++ccp7xf.h++` to
the newer CCP, retaining its `++#ifdef CPM3++` sections in the same file.
Do not maintain separate 2.2 and 3.0 full copies unless a real semantic
incompatibility later proves unavoidable.
`++ccp_catalog.h++` (or a more descriptive 7XF module name) contains the
named catalog, `++LS/LL/CD++`, aliases and file listing logic. A separate
product CCP can include it while unmodified upstream `++ccp.h++` remains
available for comparison and serial-only builds.

Preserve every recovered original CCP command's semantics in
`++ccp7xf.h++` where possible. In particular, the original `++VOL++`
reads `++INFO.TXT++`, whereas our present fork redirects it to
`++DIR.7XF++`. *Do not smuggle that behavior change into the mechanical
file split*: first preserve/test current behavior, then restore `++VOL++`
to `++INFO.TXT++` as a separately visible and tested compatibility correction.
The 7XF named catalog owns `++DIR.7XF++` and `++VOL.7XF++`. Likewise,
append 7XF help rather than silently rewriting original command descriptions.
Audit prompt widening, `++CLS++`/newlines, `++SUBMIT++` cancellation,
external-COM lifecycle, parser globals and first-start behavior against the
recovered CCP first; repeat against CP/M 3 only during the later HEAD port.

This copied CCP keeps the recovered original file untouched, but it incurs a
whole-file merge whenever upstream changes. A later *alternative* experiment
may put narrow, opt-in registration/prompt/help/external-lifecycle hooks into
one upstream `++ccp.h++`, for both 2.2 and 3.0. Choose that only if the
result is demonstrably cleaner and tests pass; it is not the immediate plan.
There is no zero-edit, zero-duplication extension of the current fixed
upstream command table.

`++ccp_catalog.h++` currently uses Arduino `++File++`/`++SD++` directly;
the native Linux C build therefore fails when it includes our present CCP.
The immediate `++ccp7xf.h++` may be Arduino-scoped. Reuse on POSIX or other
RunCPM ports needs a small filesystem adapter before claiming portability.
Moving the catalog under `++hardware/arduino_7xtgv/++` would hide rather
than resolve this dependency; 7XF command semantics do not belong to a
particular board HAL.

== Standalone UART terminal: feasible mode, unresolved storage protocol

`++XTGV_RUNCPM=0, XTGV_TERMINAL=1++` is a useful target for single-core
boards connected to a physical CP/M computer. The screen parser/renderer
can remain common, but the present runtime consumes RunCPM virtual queues;
`++Serial++` is the PC keyboard/mirror path. A UART transport must feed the
same terminal parser with *external* guest output and send composed keyboard
input back to that UART. Keep host mirror, guest UART, and local controls
distinct. CCP prompt recognition, 7XF commands, forced COM return, device
REFLASH and CP/M-specific profile actions may be unavailable or require
explicit per-transport capability decisions; do not imply they work on
arbitrary real hardware.

Present INI/BUF persistence also assumes the RunCPM/storage core owns SD and
can pause the other display core. `++terminalPause()++` waits for a separate
loop to acknowledge it; calling that unchanged from a single-core terminal
storage operation would deadlock. Give the standalone runtime its own
single-owner storage polling and non-self-pausing save path. Preserve atomic
new/verify/backup replacement and bounded latency; do not expose an
incomplete INI while the terminal parses it.

Petr's desired CP/M editing path is feasible but is **not a filesystem
alias over UART** by itself. The real CP/M machine and terminal normally
have separate filesystems. Start with terminal-local INI/BUF as authority:
terminal settings and history can persist without any CP/M disk access.
For later CP/M-side editing workflows, provide an explicit guest transfer
utility/protocol: fetch a copy to a normal CP/M file, edit with TE/TP3,
then send the INI text back; validate and atomically replace the terminal
copy, report success/error, and either reapply supported settings or request
a clearly identified terminal reboot. BUF need not share the same editing
workflow unless a concrete use calls for it. Specify
framing, length/checksum, escape from terminal graphics/control streams,
flow control, failure recovery, and whether a reboot/profile reload is
required before implementing. Current PC-host `++VTPUT/VTGET++` must not be
assumed to provide this external-UART endpoint without inspection. A truly
transparent CP/M drive alias would require guest BIOS/BDOS or block-device
support and is a much larger, separate project.

The smallest standalone prototype may keep INI/BUF solely on the terminal
board's filesystem. Its own controls may edit and persist settings there;
the terminal need not mount or emulate the external CP/M disk. Some existing
`++VT*++` workflows expect a CP/M editor to modify INI text and then reboot
or reload the terminal. Preserve that *future* workflow by planning an
explicit copy/send-and-apply command, but it need not block the first
standalone display/keyboard/UART prototype. Document the loss of
CCP-dependent conveniences honestly. Do not let reserved flags turn on an
incomplete mode in shipping builds.
