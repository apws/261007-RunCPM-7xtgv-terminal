== Publishing risks and a small pre-push checkpoint

Do not use a blind git add of the whole tree. Untracked root files include
`260923-0923 backup docs.zip` (949,674,532 bytes) and
`260924 backup - cpmcard.zip` (5,896,929 bytes). Other ZIPs exist in cpmdrive.
Their inclusion, licensing and private contents have not been audited. Preserve
them locally; do not assume they belong in Git. Uppercase MIXWORX filenames
remain private/ignored. An archive can contain private data even if its outer
name does not match that rule.

There are also old `_VTPAL.BAS` / `_VTPAL.INI` optional-level artifacts in A7.
Their old preset numbering conflicts with today's BW/plasma/VFD slots. Do not
deploy them accidentally. No archive or obsolete artifact was removed here.

There is no mandatory pre-push report gate in the current repository guidance.
There ARE many good dated implementation reports plus a feature index; their
presence is not equivalent to a reviewed release summary. Recommendation:

. Before a requested commit/push, write one compact checkpoint like this one:
  baseline commit, selected change groups, actual checks/targets, known limits,
  manual gaps, and files intentionally excluded.
. Compare feature rows against the baseline with git, not only last_reviewed:
  review date is not implementation date and not a publication marker.
. Check registry, regenerate the ledger, review changed manual sections, then
  stage explicit paths and inspect the staged diff. Commit/push only when asked.

This is a proposed lightweight practice, not a new automatic publishing hook.

== H and manual completion are different dimensions

The ledger is useful: it finds old ideas and prevents repetition. Its weakness
is stale or overly broad evidence, not its 45 KB size. DEC's old H meant only a
simple smoke test, as Petr clarified. Future H evidence should say target,
what was actually exercised, and what was not. A new test page needs its own
pending hardware gate; it must not inherit acceptance from old DEC support.

Several rows still said "not deployed" after later user acceptance. This pass
updates the clear palette/ramp evidence and qualifies DEC, without pretending
to re-audit every historical H claim. Unknown historical test dates stay empty.

Do NOT replace H with a single higher M state: a manual may be current before
hardware testing, and a hardware-tested feature's manual can become stale.
Recommended future addition: independent manual_ref plus manual_reviewed date,
with pending/current/not-applicable interpretation if needed. For now use
boundary/next_gate and linked documents; no registry schema change is made.

Specific documentation gap: the current manual describes ANSI/VT52 modes but
does not give a scoped DEC glyph inventory and the TFT/mirror approximation
differences. This review is the source for a later concise manual section.
VTPAL's help and ink labels also need alignment with the six actual presets.

== Small CP/M / FAND export idea

This already exists as feature `dev-cp-m-fand-feature-registry-demonstration`.
Keep TSV authoritative. A generated read-only ASCII fixed-width import listing
could retain short identifier, group, state, selected dates and short title,
with full descriptions left on the host. Roughly 128-byte records would make
140 rows about 18 KB; this is a size illustration, not a signed field layout.
Long canonical IDs must not be silently truncated into collisions: preserve a
separate mapping if compact stable IDs are chosen. Widths, character policy,
CRLF/Ctrl-Z and FAND import details need agreement before implementation.

An import listing is not itself a native FAND database. No database engine,
reverse synchronization or new storage schema is warranted for this demo.
Keep any live FAND application test observations in the existing private log.
