= JC8048W535 software rotation and framebuffer implementation
:source-highlighter: highlight.js

Date: 2026-09-12

== Reason for the workaround

The 3.5-inch JC8048W535 module contains a 320x480 AXS15231B panel. Its tested Arduino++_++GFX controller-rotation path did not produce a valid 480x320 image: attempts produced a blank display or only a narrow vertical fragment. The working implementation therefore leaves the controller in its native portrait orientation and rotates a software canvas.

This is a board-specific compatibility measure. It does not establish that controller rotation is unreliable on every supported panel.

== Target isolation

link:../src/7xtgv-vt100-runcpm/src/terminal/7xtgv-gfxsetup.h[`+7xtgv-gfxsetup.h+`] selects one of two current RunCPM display paths at compile time:

[source,cpp]
----
#if defined(RUNCPM_TARGET_JC8048W535)
#define JC8048W535_AXS15231
#else
#define WAVESHARE_RP2350_LCD_2
#endif
----

Only the `+JC8048W535_AXS15231+` block defines `+GFX_BUFFERED_CANVAS+` and creates an `+Arduino_Canvas+`. The default 2-inch RP2350 target continues to construct its ST7789 device directly. Consequently, the S3 canvas, PSRAM use, software coordinate transform and full-frame flush do not enter the RP2350 build.

The other 7xtgv display-demo projects also keep their display declarations in their own local `+gfxsetup+` branches. They share the higher-level Arduino++_++GFX drawing interface and palette, but a canvas used by one target does not alter another target's controller setup.

== JC8048W535 object arrangement

The target constructs these two Arduino++_++GFX objects:

[source,cpp]
----
Arduino_AXS15231B *panel = new Arduino_AXS15231B(
    qspi, GFX_NOT_DEFINED, 0, false, 320, 480);
gfx = new Arduino_Canvas(320, 480, panel, 0, 0, 1);
----

The objects have distinct roles:

* `+panel+` is the physical AXS15231B client. It remains 320x480 with rotation 0.
* `+gfx+` is the surface used by all terminal code. Canvas rotation 1 exposes a logical 480x320 client, so `+gfx->width()+` is 480 and `+gfx->height()+` is 320.
* The terminal therefore retains its intended 80x32 layout of 6x10 cells.

Terminal rendering does not contain a separate JC8048W535 coordinate formula. It draws normal landscape coordinates through `+gfx+`, for example a cell at `+column * 6, row * 10+`. `+Arduino_Canvas+` converts these positions into the native portrait framebuffer layout.

For rotation 1, a logical pixel is stored approximately as:

[source,text]
----
logical (x, y) -> native framebuffer (319 - y, x)
----

Arduino++_++GFX applies the equivalent transform to bitmap spans. This makes the software rotation functionally transparent above the `+gfxsetup+` layer.

== Memory and transfer path

The complete RGB565 canvas occupies:

[source,text]
----
320 * 480 * 2 bytes = 307,200 bytes
----

`+Arduino_Canvas::begin()+` allocates that buffer dynamically. In the selected ESP32-S3 build, OPI PSRAM is enabled and ordinary allocations larger than 4 KiB prefer external PSRAM when their capability requirements permit it. The canvas is therefore expected to live in PSRAM, with allocator fallback still possible; this expectation is not a linker-map proof of a particular runtime allocation.

The current cell-to-panel path is:

[arabic]
. `+drawCell()+` composes one opaque 6x10 RGB565 cell into a 120-byte scratch array.
. `+gfx->draw16bitRGBBitmap()+` rotates and copies that cell into the 307,200-byte canvas framebuffer, normally in external PSRAM.
. `+gfx->flush()+` sends the native 320x480 framebuffer to the physical panel.
. The ESP32 QSPI implementation byte-swaps/copies chunks into internal DMA-capable staging buffers before transmission to panel GRAM.

The terminal tracks dirty cells, but the canvas implementation has no dirty rectangle flush. Once any cell has changed, the current buffered path can compose only those dirty cells yet still transfers the whole 307,200-byte frame at flush time. Firmware limits these flushes to approximately 30 per second. Software rotation is therefore convenient and correct, but it costs a PSRAM copy path and full-frame QSPI traffic.

== Behavior of the direct 2-inch target

The 2-inch Waveshare RP2350 module uses a 320x240 ST7789 over SPI. Its target block creates `+Arduino_RPiPicoSPI+` and `+Arduino_ST7789+` directly with controller rotation 3. It does not define `+GFX_BUFFERED_CANVAS+` and does not allocate the 307,200-byte S3 canvas.

On that direct path, a 6x10 cell bitmap is sent through the display driver without a later canvas-wide flush. The existing narrow-display viewport and indicator behavior also remain selected by the absence of `+GFX_BUFFERED_CANVAS+`.

This source-level isolation preserves support for the 320x240 module. Because the recent terminal work has been exercised on the JC8048W535, the RP2350 module should still receive a real build-and-flash regression test after the xterm-256 implementation. Source isolation is strong evidence against an accidental canvas regression, but it is not a substitute for that hardware test.

== Effect on the xterm-256 renderer

The planned xterm-256 renderer should continue to use the post-rotation Arduino++_++GFX interface:

* size its temporary scanline from `+gfx->width()+`, which is 480 on this target and 320 on the 2-inch target;
* draw at logical coordinates with an ordinary Arduino++_++GFX bitmap/span call;
* request a pending `+gfx->flush()+` only when `+GFX_BUFFERED_CANVAS+` is defined;
* let direct-display targets transmit their span through their existing controller driver.

This keeps the parser and plot logic independent of native portrait versus landscape memory layout. It also keeps the JC8048W535 workaround confined to the display setup and buffered-runtime branches. The initial xterm-256 path will inherit the canvas's full-frame-flush cost on this S3 module; optimizing that transfer later can be done inside the target/display layer without changing the terminal protocol.
