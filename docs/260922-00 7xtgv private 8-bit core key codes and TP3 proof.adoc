= 7xtgv private 8-bit core key codes and TP3 proof — 260922

*Status:* hardware-tested on 260922. Explicit profile bindings emitted the compact one-byte codes for about 90% of TP301 editor controls, and the correctly TINST-patched device-side `+TURBO.COM+` responded as configured. Automatic compiled defaults and the optional `+0x8F+` extension grammar remain separate refinements.

This note records the 260921/260922 experiment proving that Turbo Pascal 3.01A for CP/M can use bytes above `+0x7F+` in its configurable editor controls. It also defines the proposed compact key-byte layout for the embedded 7xtgv terminal and later 7xtgv environments.

The photographed physical-key numbering is shown in link:260921-18%207xtgv%20KBD%20CORE%20KEYS%20CONTROL%20%20--%20Screenshot_20260921_180114.adoc[260921-18 7xtgv KBD CORE KEYS CONTROL].

[id="1-tinst-storage-model-clarified"]
== 1. TINST storage model clarified

Turbo keeps two different kinds of installation data:

[source,text]
----
TINST.DTA                 library of selectable terminal/screen definitions
installed command table  patched into the selected TURBO.COM
----

The configurable editor controls are not simply saved as the current control table in `+TINST.DTA+`. TINST installs them into `+TURBO.COM+` on the current CP/M drive/user area. Running a copied `+A0:TINST.COM+` can therefore patch `+A0:TURBO.COM+` while a later launch of `+A2:TURBO.COM+` continues to use its old controls.

This explained the apparently contradictory test:

* TINST accepted the experimental bytes and displayed forms such as `++Ctrl-?(+128)++` and `++?(+128)++`;
* the launched Turbo editor did not respond to them;
* the fetched `+A0:TURBO.COM+` still contained the earlier ordinary mappings, including `+ESC [ D+`, `+ESC [ C+` and Ctrl-letter sequences, rather than the newly displayed high-bit assignments.

The TINST display itself shows that its interactive command editor preserves bit 7. A definition must still be installed into the same `+TURBO.COM+` that will subsequently be executed.

The live `+A2:TINST.DTA+` was fetched after the investigation. It was 4,736 bytes, while the older local mirror had been 4,480 bytes. Inspection confirmed that this file consists primarily of terminal-definition records; it is not the active 45-entry Turbo editor command table.

[id="2-controlled-linux-runcpm-proof"]
== 2. Controlled Linux RunCPM proof

The application-side behavior was tested in a disposable copy of the native Linux RunCPM filesystem. This test deliberately did *not* claim to exercise the embedded 7xtgv terminal; Linux RunCPM was used only to inject exact console input bytes into the same CP/M Turbo binary.

In the fetched 30,720-byte `+A0:TURBO.COM+`, the installed command table begins at `+0x4185+` for this exact binary. Its entries are length-prefixed byte strings. Command slot 14, *To top of page*, originally contained:

[source,text]
----
02 10 62       length 2, then Ctrl-P b
----

Only the disposable copy was changed, retaining the two-byte length:

[source,text]
----
02 81 01       length 2, then private bytes 0x81 0x01
----

The test then:

[arabic]
. booted the isolated Linux RunCPM tree;
. ran Turbo Pascal 3.01A and loaded `+A:PROG.PAS+`;
. entered the screen editor;
. sent five configured Down sequences, moving the status from line 1 to line 6;
. injected the raw bytes `+81 01+` through the PTY.

Turbo immediately executed *To top of page* and changed the editor status back to line 1. Its normal cursor-positioning output was observed after the two high-bit/private bytes.

Therefore the tested path is proven:

[source,text]
----
raw 8-bit console input
        -> RunCPM CONIN
        -> Turbo's installed TINST command matcher
        -> configured editor action
----

Turbo accepts a private two-byte command containing `+0x81+`; it does not mask the command to seven bits at runtime.

[id="3-meaning-of-console_bits8"]
== 3. Meaning of `+console_bits=8+`

RunCPM's current `+CONSOLE7+`/`+CONSOLE8+` mask applies to console *output*. The 7xtgv profile `+send:+` path, keyboard queue, `+virtualRead()+` and RunCPM console-input path retain an input byte such as `+0x81+` unchanged. Booting in 8-bit console mode is still the correct general policy for binary-clean use, but it is not what makes this particular input test work.

An end-to-end hardware acceptance test should eventually bind a device key to `+send:\x81\x01+` and use a correctly installed Turbo table. The Linux result already isolates and proves the previously uncertain application side.

[id="4-proposed-compact-7xtgv-core-key-byte"]
== 4. Proposed compact 7xtgv core-key byte

The proposed single-byte form is:

[source,text]
----
bit       7   6 5 4   3 2 1 0
meaning   1   C A S   core key
----

`+C+`, `+A+` and `+S+` are the Ctrl, Alt and Shift bits. INI binding names retain their readable canonical spelling order `+ctrl_shift_alt_+`; the compact byte's bit positions are independently defined by the following normative table. This gives eight modifier states over sixteen core physical keys:

[source,text]
----
0x80..0x8F  no modifier
0x90..0x9F  Shift
0xA0..0xAF  Alt
0xB0..0xBF  Shift+Alt
0xC0..0xCF  Ctrl
0xD0..0xDF  Ctrl+Shift
0xE0..0xEF  Ctrl+Alt
0xF0..0xFF  Ctrl+Shift+Alt
----

The low-nibble assignments from the marked keyboard are:

[cols=">,",options="header",]
|===
|nibble |physical/core key
|`+0+` |Up
|`+1+` |Left
|`+2+` |Down
|`+3+` |Right
|`+4+` |Page Down
|`+5+` |Page Up
|`+6+` |End
|`+7+` |Home
|`+8+` |Delete
|`+9+` |Insert
|`+A+` |Tab
|`+B+` |Space
|`+C+` |Escape
|`+D+` |Backspace
|`+E+` |Enter
|`+F+` |deliberately open: candidate extension prefix; alternatively Context / `+x+` / `+&+` or the physical ISO key left of `+Z+`, marked ++`++
|===

The `+F+` position is intentionally open. The preferred current candidate is to reserve only the unmodified byte `+0x8F+` as an extension prefix. A second byte could then identify non-core editing/system actions such as the semantic operations currently reached through WordStar `+^Q+` and `+^K+` prefixes. This does not mean that the generic protocol should encode literal WordStar commands: profiles should translate semantic actions to `+^Q...+`, `+^K...+` or another application's native sequence.

Reserving only `+0x8F+`, rather than the complete low-nibble-`+F+` column, leaves `+0x9F..0xFF+` available for modified forms of a future physical `+F+` key if that proves useful. The plain physical key could instead remain normal text, use an ordinary INI binding, or receive an extended code.

Do not choose `+0xFF+` as the generic extension prefix merely because it is the last byte. In the inspected TP3 command table, a one-byte `+FF+` entry denotes TINST's `+Nothing+`. An `+0x8F+` prefix avoids that known application-specific sentinel and is easier to recognize as “unmodified slot F”. The extension grammar and action-number allocation remain unsigned design work.

The original compact design note, retained in INI-comment form, is:

[source,ini]
----
; 7xtgv KBD CORE KEYS CONTROL
;
; - PHOTO OF PC-104 KBD WITH CORE KEYS 0-F RED MARKED
;
; - main 16 special keys on keyboard as lower nibble
;   0=up 1=left 2=down 3=right
;   4=pgdn 5=pgup 6=end 7=home 8=delete 9=insert
;   A=tab B=space C=escape D=backspace E=enter F=context/x/&
;   as F is probably best THE "|\&*" key next to CTRL+SHIFT !!!
;
; - general modifiers: CTRL SHIFT ALT as upper nibble +0x80
;   8 = 1000 = no modifier
;
;   9 = 1001 = SHIFT
;   A = 1010 = ALT
;   B = 1011 = ALT+SHIFT
;   C = 1100 = CTRL
;   D = 1101 = CTRL+SHIFT
;   E = 1110 = CTRL+ALT
;   F = 1111 = CTRL+SHIFT+ALT
;
; - "SIMPLEST ONE-BYTE" CONTROL FOR 7xtgv-terminal MAIN KEYS
----

[id="5-boundaries-and-collision-policy"]
== 5. Boundaries and collision policy

These bytes are an *application-facing input encoding*. They are distinct from the existing host-to-embedded-terminal private event:

[source,text]
----
CSI >70;1;<base>;<modifiers>;<fallback>v
----

That longer CSI form preserves host key identity through Konsole/Kitty. The embedded terminal may then apply the selected global/bank INI binding and emit a compact `+0x80..0xFF+` byte to the guest. A native embedded keyboard or later top-level 7xtgv OS shell can produce or consume the compact form directly.

Terminal-owned global chords still have precedence and may be consumed rather than delivered to an application. Profile overrides remain necessary for applications that expect ANSI, VT52, WordStar or their own historical byte sequences.

The range overlaps ISO C1 byte values, notably `+0x9B+` for CSI. Direction and layer therefore matter:

* an output decoder may interpret `+0x9B+` as C1 CSI;
* the compact core-key byte is guest *input*, after the terminal has already resolved the physical key;
* a guest or shell opting into this private keyboard protocol must not also reinterpret the same input byte as an unrelated C1 command;
* paths that strip bit 7, use parity in bit 7, or perform text-codepage conversion are incompatible with the compact form.

[id="6-tp3-fand-and-broader-use"]
== 6. TP3, FAND and broader use

For TP3, TINST can assign the compact bytes directly to any of its configurable editor actions. The controlled test proves that a two-byte private sequence also works, so applications are not restricted to the proposed single-byte core-key form.

FAND is expected to follow the same general installation model: its installer configures byte sequences consumed by the application, and the installed program/chain files—not merely the installer's definition data—must be the ones subsequently executed. The exact FAND target file and matcher still need independent verification; TP3 evidence must not be presented as binary proof about FAND internals.

The compact encoding is intended to be generic 7xtgv infrastructure, not a TP3-only convention. Planned users include:

* the embedded 7xtgv terminal;
* configurable CP/M applications such as TP3 and potentially FAND;
* later non-Linux embedded environments;
* a future top-level 7xtgv shell or OS input layer.

This keeps physical core keys and all Ctrl/Shift/Alt combinations compact and stable while application profiles remain free to translate them into legacy protocols.

[id="7-device-hardware-acceptance"]
== 7. Device hardware acceptance

Petr subsequently configured about 90% of TP301's editor controls with the one-byte `+0x80..0xFF+` scheme through ordinary profile `+send:\xNN+` bindings. On the physical 7xtgv RunCPM device, those keys reached TP301 and invoked the installed actions correctly once TINST had patched the same `+TURBO.COM+` that was being executed.

This confirms the complete practical path:

[source,text]
----
physical PC key and modifiers
        -> 7xtgv key event and selected profile binding
        -> one private 8-bit input byte
        -> RunCPM console input
        -> TP301 installed command table
        -> editor action
----

The earlier failure was an installation-target mismatch rather than loss or masking of the private byte. The low-nibble `+F+` physical identity is still a naming/design choice; on Petr's Czech keyboard the likely key is `+Z1+`, the ISO key immediately left of `+Z+`. That open choice does not affect the tested `+0..E+` core-key layout or its modifier encoding.
