= Structured feature registry design
:source-highlighter: highlight.js

Status: signed and implemented on 260922. The canonical ASCII TSV contains 116 migrated feature records; its validator, selectable reports and generated Markdown ledger passed host tests. Miller 6.21 TSV and custom-pipe proofs also passed locally.

== Purpose

The dated Markdown documents remain the complete narrative and evidence history. A small structured registry adds sortable/filterable overview data without replacing those documents.

The registry must support at least:

* grouping by a short feature-area code;
* first idea/mention date;
* design and signed-plan dates where they exist;
* first implementation or explicit rejection date;
* first real-hardware test date;
* current lifecycle state and partial-delivery qualification;
* links back to every relevant source document;
* generated Markdown, command-line queries and later CP/M FAND demonstration data.

== Canonical and derived files

The recommended source of truth is:

[source,text]
----
docs/features.tsv
----

It is 7-bit ASCII, IANA-style tab-separated text, with one header line and one physical line per feature. Literal `+|+`, comma and double-quote characters are ordinary field content and need no quoting. Literal TAB, CR and LF bytes are forbidden inside fields, so record and column boundaries remain unambiguous. Use Miller's `+--tsv+` reader rather than a custom CSV separator.

The format is suitable for Git diffs, ordinary text tools, LibreOffice Calc and Miller. Dates remain fixed six-character `+YYMMDD+` text, so lexical and chronological order are identical.

Derived views are:

[source,text]
----
docs/FEATURES.md             human-oriented grouped ledger
build/features-*.csv        optional exports, including later FAND input
build/features-*.txt        optional fixed-width/display exports
----

No SQLite layer is needed. Miller operates directly on the canonical text records and can emit pretty terminal tables, Markdown, CSV, JSON or other derived formats.

== Initial schema

[source,text]
----
feature_id
group
title
state
qualifier
idea_date
design_date
plan_date
impl_date
reject_date
hw_test_date
docs
summary
boundary
next_gate
last_reviewed
----

Rules:

* `+feature_id+` is stable, human-readable and unique, for example `+inp-key-first-chord-names+`; do not rename it when the title or group changes.
* The header and all field contents are printable ASCII. TAB, CR, LF and non-ASCII bytes are invalid inside fields. This makes later CP/M exchange and fixed-position reporting predictable.
* Dates use exactly six ASCII digits in `+YYMMDD+`. Leave an unknown or unreached milestone empty; never invent precision for historical ideas.
* `+impl_date+` and `+hw_test_date+` mean the first proven milestone. Later corrections/tests remain in the linked dated documents.
* `+state+` uses `+B+`, `+D+`, `+P+`, `+I+`, `+H+`, `+X+`, or `+R+` as defined in `+FEATURES.md+`.
* `+qualifier+` carries compact distinctions such as `+partial+`, `+deeper-test+`, or `+deferred-until-evidence+`; do not overload the state code.
* `+docs+` contains semicolon-separated repository-relative paths. Complete discussion stays in those files rather than being copied into cells.
* No field contains a literal tab or newline. Use short single-line prose; the validator rejects malformed records. Pipes and quotes require no special handling in TSV.

Initial group codes:

[cols=",",options="header",]
|===
|Code |Area
|`+RUN+` |RunCPM, targets, HAL and host tooling
|`+OUT+` |Terminal output, display and graphics
|`+INP+` |Keyboard input, profiles, history and completion
|`+CFG+` |Configuration, persistence and diagnostics
|`+NAT+` |Native 7xtgv architecture
|`+APP+` |Application and historical compatibility
|`+DEV+` |Development tools, workflow and repository process
|===

These codes are presentation categories, not ownership boundaries. Changing a group must not change the stable feature ID.

== Tooling

The dependency-free repository tool is `+src/feature_registry.py+`. It validates ASCII and schema rules, identifiers, dates and referenced documents before it emits any report or updates the ledger:

[source,sh]
----
# Validate the source store and every public document link
python3 src/feature_registry.py check

# Select columns, order by group then introduction date, and print aligned text
python3 src/feature_registry.py report --format text \
  --fields group,idea_date,state,title,next_gate \
  --sort group,idea_date,title

# Make a Markdown report for only the input group
python3 src/feature_registry.py report --format markdown \
  --where group=INP --fields idea_date,title,state,qualifier,next_gate

# Deterministically replace only the marked tables in the human ledger
python3 src/feature_registry.py update-ledger
----

`+report+` accepts `+markdown+`, `+text+`, or `+tsv+`, arbitrary selected fields, comma-separated sort fields, repeatable exact `+FIELD=VALUE+` or `+FIELD!=VALUE+` filters, and `+--output+`. Unknown dates sort after known dates within a group. The generated region is ordered by the declared group order, `+idea_date+`, then title. The hand-written ledger preamble, current gate, evidence map, drift notes and maintenance rules remain outside that region.

Miller remains the richer optional interactive record engine. Direct operations are simple:

[source,sh]
----
# All records ordered by first-idea date
mlr --itsv --opprint \
  sort -f idea_date docs/features.tsv

# Designed but unfinished features, rendered as an aligned Markdown table
mlr --itsv --omd-aligned \
  filter '$state == "D"' then sort -f group,idea_date docs/features.tsv

# Select columns for a compact terminal view
mlr --itsv --opprint \
  cut -f feature_id,group,state,title,next_gate docs/features.tsv

# Transform a record on stdout; redirect only after reviewing the result
mlr --itsv --otsv \
  put '$state = "H"; $hw_test_date = "260922"' \
  then filter '$feature_id == "inp-key-first-chord-names"' docs/features.tsv
----

Validation checks ASCII-only content, TSV structure, unique IDs, known enums, date syntax, physical one-line records and referenced public document paths. It deliberately does not reject real history merely because implementation preceded a later formal design document.

Markdown generation replaces only the marked generated region inside `+FEATURES.md+`. Its explanatory preamble, current gate, maintenance rules and reference notes remain hand-authored.

Optional interactive tools remain conveniences rather than dependencies:

[source,sh]
----
# Interactive terminal spreadsheet
vd -f tsv docs/features.tsv

# GUI spreadsheet already installed on this host
libreoffice --calc docs/features.tsv
----

When opening TSV in Calc, choose TAB as the separator, import every identifier/date column as text, and save back with the same settings. ODS may be a disposable analytical view, never the canonical registry.

If multiple implementation/test events later become analytically important, add an append-only `+feature_events.tsv+` keyed by `+feature_id+`. Do not add that second table before the single registry proves insufficient.

== Miller format proof and decision on 260922

Miller 6.21 was extracted temporarily without a system install and exercised against small ASCII fixtures. TSV sorting, filtering and output conversion passed. A custom pipe-separated CSV experiment additionally confirmed:

* header recognition with `+--icsvlite --ifs pipe+` for fields without literal pipes;
* lexical sorting by `+idea_date+`;
* filtering by state and group;
* aligned terminal output;
* aligned Markdown-table output;
* ordinary CSV export;
* full `+--icsv --ifs pipe+` parsing and round-trip output of a quoted field containing a literal `+|+`.

The same test confirmed that `+--quote-all+` can emit every pipe-separated field inside double quotes and doubles a literal quote. This is valid, but it adds escaping and uses a project-selected separator. Canonical TSV was selected instead; pipe-separated and always-quoted files remain possible derived exports.

Miller's NIDX format provides delimiter-separated positional fields named `+1+`, `+2+`, and so on. It is not a fixed-width schema like FAND's declared `+A+`-type fields. Pretty-printed Miller output is an aligned view, likewise not a canonical fixed-width database. If FAND needs `+A20+`, `+A40+`, or similar records, generate a separate width-checked export from TSV.

== FAND demonstration path

The registry is a strong future FAND demo because its fields, selection, sorting and report views are recognizably database-oriented while remaining small enough for CP/M.

The first FAND experiment should be read-only:

[arabic]
. export a limited ASCII/CP-M-friendly subset from the canonical TSV;
. import or define it in FAND;
. demonstrate group/state/date filtering and sorted reports;
. compare the report with host-generated Markdown/CSV;
. do not let FAND write back into the canonical registry until its data and encoding behavior are understood.

== Implementation result

The migration retained all 116 feature rows from the hand-written ledger. Dates were populated only where a dated source filename or this 260922 implementation supplied direct evidence; unknown milestone dates remain empty rather than being guessed. The generated tables expose introduction date, feature, state, summary and document links, ordered by group and introduction date.

`+src/feature_registry_test.py+` covers canonical validation, group/date ordering, filters, Markdown pipe escaping and preservation of hand-written ledger regions. Miller remains optional; the temporary non-installing proof was sufficient to establish interoperability.
