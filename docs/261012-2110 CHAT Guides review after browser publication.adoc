== Findings and possible edits

and the entrance; later items improve navigation without a general rewrite.

=== a. README: make the published page the first action

The link:../README.adoc[README] opens with MCU/native desktop use. Its browser
paragraph links to developer setup and calls publication an optional workflow;
most first-use space is occupied by Linux/Windows setup and target folders.

Propose a prominent direct browser link, a sentence explaining what runs, and
a short sequence: wait for the CP/M prompt, click the display, type `VTINFO`
or `LS /`, then learn how to retain changes. Link a graphical exercise from
UG. Keep a compact choice of native desktop and physical hardware next.
Move detailed prerequisite/launcher duplication to the existing BG owners.
Keep the screenshot and the distinction between today's testbed and native
7xtgv intent. Put optional local AsciiDoc viewing setup after reading links.

=== b. Guide index and BG: installation becomes a chosen route

link:../guides/README.adoc[Guide index] currently sends everyone to BG for
clone/setup. Route browser visitors directly to UG; give builders BG.
Old guide moves/bookmark migration and local renderer customization can remain

link:../guides/01-BG-build-guide.adoc[BG 1] starts with native desktop setup.
Keep its detailed working recipes, but add an opening pointer for readers who

=== c. UG: browser start, first exercise and card survival

link:../guides/02-UG-user-guide.adoc[UG] starts with native mirror terminology.
Its browser subsection requires a local build and launcher. Replace that
entrance with the public URL; link local browser development separately.
Give browser and native input locations explicitly before shared CP/M tasks.

A compact first exercise could use `VTINFO`, `7XF` and `LS /`, then link to
the existing xterm256 demonstration in UG 4. The card contains its referenced
`BROT_BS.SUB` and program. Rehearse the chosen demonstration against the
published card before promising it as a universal first experience; small
panels clip fixed-position graphics. The current text mentions only TFT/SDL
output and recommends EP4_10 desktop; include the browser canvas appropriately.

Explain three user-visible distinctions at their points of use:

* Display scale enlarges the rendered panel. Terminal glyph zoom/pan changes
  its viewport. Logical terminal size is a third, independent setting.
* Save a document in its CP/M application before target switching or restart;
  keeping card contents does not keep unsaved application memory.
* Browser INI/history/file saves reach the memory card, not durable browser
  storage. Stop cleanly and download its ZIP; reload/close loses unexported
  changes. Native host-card changes persist directly instead.

Add browser entries to UG 4 for focus, reserved keys, startup failure and card
export. Keep technical worker/isolation details in the browser developer README.

=== e. Laptop controls: a useful application proposal

Petr's extra column is feasible within the current two-column layout. Recommend
an optional, collapsible strip between controls and display on wide windows,
and a compact drawer/row on narrow windows. A permanently visible third column
would reduce the available display area, especially for EP4_10 on a laptop.
No layout or input implementation is included in this review.

Candidate content:

* A recognizable six-key block: Ins/Home/PgUp above Del/End/PgDn.
* Named terminal actions for glyph zoom, pan/viewport scan, previous/next
  profile and brightness. Bare PgUp/PgDn buttons alone do not replace the
  modifier combinations used for these actions.
* Expandable Ctrl/Shift/Alt modifiers and function keys if application use
  demonstrates the need; modifiers need visible, predictable reset behavior.
* Keep configured application exit distinct from an emergency COM abort.
  Profile-sensitive guest keys should still use the existing C++ bindings.

Implementation direction if adopted: share the existing key/control encoder
and ordered input queue, rather than synthesizing DOM keyboard events or
building another profile interpreter. Account for the current blur handler,
which cancels pending input, and disabled/stopped runtime states. Mouse/touch
use should permit returning to typing; keyboard activation of buttons should
retain usable focus. Test that each activation sends once and modifiers cannot
remain accidentally latched. Do not couple this small proposal to a full virtual
keyboard, new native shortcuts or a firmware protocol redesign.

=== f. Linux, Windows and macOS: promise browser capabilities precisely

The delivered page executes Wasm locally and needs no native macOS launcher.
It is a reasonable cross-platform entrance, but “any browser anywhere” would
overstate the evidence. The Pages startup needs HTTPS, service workers and
cross-origin-isolated shared memory. Browser support for the underlying shared
memory facility is broad; that alone does not qualify this application or keys.
See https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer[MDN shared-memory requirements].

Record tested browser + OS + version separately from expected compatibility.
Existing notes establish Linux Chromium automated checks and Petr's earlier
Chromium/Chrome/Edge report; that report does not identify every OS or establish
Safari/macOS testing. Publication success also is not that compatibility matrix.

Apple documents Fn+Left/Right for Home/End, Fn+Up/Down for PgUp/PgDn and
Fn+Delete for forward Delete. These are useful candidates, not proof that
their modified combinations reach our input module. See
https://support.apple.com/en-us/102650[Apple keyboard shortcuts].
Keep Control distinct from Command; our encoder leaves Meta/Command events to
the browser. Option-generated characters, left/right Option, national layouts,
Fn keys and OS-reserved combinations need real MacBook testing. Insert still
needs an explicit accessible route; do not invent a universal Mac substitute.
