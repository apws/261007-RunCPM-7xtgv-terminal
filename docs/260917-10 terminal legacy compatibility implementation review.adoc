= Terminal legacy compatibility: signed implementation plan
:source-highlighter: highlight.js

*Date:* 260917

*Status:* signed off by Petr on 260917; legacy-mode and profile features not yet implemented. At sign-off, the separately requested default-ink correction was already in source; its firmware rebuild precedes this plan's implementation.

*Source:* `+docs/260916_7xtgv_terminal_legacy_compatibility.adoc+` (Petr {plus} Lyra). Preserve that source note; this document records the repo-grounded decisions and implementation order.

== Decision to retain

Application output decoding and application key encoding are independent. ANSI/VT100 and VT52 use the same screen model and rendering path. Explicit bank selection applies that profile's mode default and zoom-dependent logical geometry once; the existing effective-bank rule continues to select its input preset, key overrides, history and line-editor adapter. An application can then switch its output language in-band. None of this creates a second screen engine. Local 7xtgv controls (zoom, backlight, history/profile, deliberate host reflash) remain available independently of screen language. The reserved GCLS/xterm256 transaction is accepted even while VT52 is selected, without permanently switching the terminal to ANSI.

Use one `+Terminal::feed()+` state machine with small mode-specific branches. VT52 commands should directly call the existing cursor, erase, and scroll operations. Do not implement a VT52-to-ANSI byte translator or a large parser refactor: generating and re-parsing ANSI bytes adds work to precisely the small, fast legacy protocol.

== Corrections to the source note

[arabic]
. `+Terminal+` already decodes VT52 (`+terminal.cpp+`, `+ansi == false+`, `+ESC A/B/C/D/H/I/J/K/Y/Z/F/G/=/...+`). This work is to expose and test that existing decoder as a profile choice, not implement it from zero. ADM-3A is not present and remains optional.
. The source note's blanket “private 7xtgv CSI only in ANSI” rule is too broad. Keyboard-side private controls are local and already independent of the application's output parser; the guest `+CSI >64v+` host-reflash prefilter also remains available. Accept the reserved application-output `+CSI > ... v+` grammar in VT52. GCLS's subsequent xterm256 SGR stream is recognized only while its plot transaction is armed. Do not mistake the two directions of control for one parser.
. GCLS currently calls `+Terminal::beginPlot()+`, which sets `+ansi = true+`; that would silently switch a VT52 application to ANSI. Remove this side effect. The graphics receiver must recognize the _small subset_ of SGR used by its pixel stream while armed, without changing the selected output language; restore ordinary VT52 interpretation when the plot ends or aborts.
. RunCPM's `+mask8bit+` is applied on console *output* (`+console.h+`), not generally to keyboard input. `+0x9B+` CSI will be lost with `+0x7f+`, so test with `+CONSOLE8+` (`+0xff+`) first. Keep Console7 as the normal default in this delivery; a global change to Console8 requires a separate policy decision. `+Terminal::put()+` currently renders ordinary bytes ++>++= `+0x80+` as `+?+`; 8-bit-clean transport is not Czech glyph/codepage support.
. The current INI uses `+[global]+`, `+[display:HALID]+`, and `+[bankN]+`, not the source note's illustrative `+[terminal]+` and `+[profile name]+`. Extend the existing grammar; avoid parallel configuration systems.
. The temporary _effective history bank_ can become bank 0 on a recognized CCP prompt, while `+selectedBank+` remains the user's selected app bank. This is intentional for *input*, history and line-editor adapters: CCP receives bank-0 bindings, and the app receives its own bank bindings. Preserve it. The output decoder must *not* follow that effective-bank change. However, an *explicit* Alt{plus}number selection of `+selectedBank+` applies that profile's configured default output `+mode=+` once, as a user action. A manual `+VT52.COM+`/`+VT100.COM+` or application mode command remains in effect until another explicit mode command or profile selection; no CCP-prompt-triggered ANSI reset.
. Input is already flexible through bank-specific key bindings. `+input=vt52+` and `+input=wordstar+` should only supply convenient defaults, not add a competing encoder. Explicit bindings take precedence; TE's current key choices already differ from a generic WordStar table. FAND's exact editor keys still need a real test. Prefer `+input=custom+` over ambiguous `+literal+` for the existing explicit per-key mapping.
. The proposed PTY/SDL replay harness does not exist in this repo. Deterministic byte-stream tests can be added to the existing C{plus}{plus} terminal/runtime tests; raw serial capture is optional if an application disagrees. A new display harness is not a prerequisite.
. `+CSI 0 m+` resets all SGR attributes. Compact three-byte FANDINST fields using `+9B 0 m+` must be checked against FAND's _actual_ attribute combinations; do not assume it independently disables bold, blink, or reverse.

== Configuration contract

[source,ini]
----
[global]
mode=ansi
console_bits=7

[bank7]
mode=ansi
input=wordstar
zoom1_terminal=80x24
# Existing explicit key bindings in this bank override the preset.

[bank8]
mode=vt52
input=vt52
----

* `+[global] mode=ansi|vt52+` is the boot default output language, not a TFT hardware mode. ANSI is the normal default. `+[bankN] mode=+` is a *selection default* applied once on an explicit Alt{plus}number profile switch. The default for a bank without its own key is the global mode. It is not reapplied when the effective input/history bank changes on an `+A0>+` prompt. `+CSI ?2l+` already enters VT52 and `+ESC <+` already returns to ANSI dynamically; `+VT52.COM+` and `+VT100.COM+` may emit those controls as explicit transient changes, including in SUB files. An explicit mode change does not erase or reset color attributes. Defer `+adm3a+` until a concrete application needs it.
* `+[bankN] zoom1_terminal+` through `+zoom4_terminal+` optionally override that selected profile's *logical* columns and rows at each physical zoom, using the existing `+[display:HALID]+` key names. This is a profile view, not a per-program execution mode; the same geometry drives terminal cursor, wrapping, scroll, mirror and CP/M app output. It is applied on explicit profile selection and physical zoom changes, never merely on the temporary effective-bank change. An absent key uses the global `+[display:HALID]+` geometry for that zoom. Validate against the physical row fit and existing maximum dimensions; no vertical pan is implied. An override such as `+zoom1_terminal=80x24+` on ES3++_++5 leaves unused TFT pixels outside the logical grid. The physical gutter width is computed from panel/zoom fit, *not* from how narrow the profile's grid is; unused area is default background, not a huge grey gutter. Normal cell redraws ignore it; `+CLS+` clears it. These profile overrides are INI definitions, but selecting them does not create new persisted runtime state.
* `+[bankN] input=custom|ansi|vt52|wordstar+` supplies default navigation-key bytes to that bank's existing mapping. Explicit INI key entries override the preset, independent of file line order. The *effective* history bank selects those bindings, so CCP retains bank-0 input while an app uses its bank. Printable keys and intentional Ctrl combinations pass through; existing `+input_adapter+` for line editing is a different layer and stays intact.
* `+[global] console_bits=7|8+` sets RunCPM's console-output mask at boot, defaulting to 7 when absent. Keep `+CONSOLE7+`/`+CONSOLE8+` and BDOS function 230 as immediate, unsaved runtime overrides. A per-bank width setting is not part of this delivery: 8-bit transport is not a screen language, color choice, or glyph-set choice. It can be reconsidered only if a real application requires a different mask when launched.
* Keep the current `+[bankN]+` framework. This work must not bake a new assumption that ten is a permanent profile limit; use the existing bank count wherever required. Raising that count later is a separate RAM/INI/UI change, not part of legacy protocol decoding.
* Omit `+extensions7x=+` in the first implementation. Private 7xtgv commands stay enabled in all output/input combinations; a broad “disable extensions” switch conflicts with the required local capabilities. If a collision appears later, narrow the control by command, not by screen personality.
* Keep `+selectedBank+` as the user's profile choice and the effective history bank as the current input/history/adapter context. The output decoder follows *explicit profile selection* or in-band application commands, never the prompt heuristic. No auto-detection from application bytes.
* Firmware initialization reads the INI before the boot banner. Do not persist transient `+VT52.COM+`/`+VT100.COM+`, application-emitted `+CSI ?2 h/l+`/`+ESC <+`, or an Alt{plus}number selection into `+[global] mode=+`. Edit the INI to change the boot/profile defaults. Existing zoom/backlight persistence is separate. This distinction needs a concrete test.

*Mode transition contract:* `+VT52.COM+` emits `+ESC[?2l+`; `+VT100.COM+` emits `+ESC<+`. A recognized CCP prompt does *not* reset the decoder, so either command can be used in SUB files before launching an application. An explicit Alt{plus}number profile selection does apply that profile's `+mode=+` default once; this deliberately supersedes any preceding manual mode. A visual `+A0>+` is a useful input/history heuristic, not program-exit truth. No RunCPM app-lifecycle hook or wrapper is needed for this initial contract. A future desktop terminal can implement the same profile-selection action without knowing about CCP.

== Decoder contract

`+ESC [+` and `+0x9B+` enter the same bounded CSI scanner in ANSI mode. C1 is the _class_ of 8-bit controls: `+0x9B+` is CSI, while `+0x98+` is the unrelated SOS control. In VT52 mode, use the scanner only for reserved `+ESC [ > ... v+` controls and the minimal plotting SGR while GCLS is armed; otherwise do not apply ordinary ANSI cursor/clear commands to VT52 output. Preserve VT52 `+ESC Y+` row/column bytes before recognizing any new control: `+0x9B+` would encode column 123 in a 132-column extension, though it cannot be a valid address byte on the original 80-column VT52. Invalid/incomplete sequences must not leak printable fragments, change personality, or hang the parser.

*Console width is not an exclusive CSI-prefix selector.* `+ESC [+` works in both 7- and 8-bit console modes. With RunCPM's current mask, 7-bit mode strips `+0x9B+` to `+0x1B+` before terminal parsing, so a program emitting compact `+0x9B+` CSI cannot work in that mode. In 8-bit mode, both `+ESC [+` and `+0x9B+` can work. The USB/serial byte link, keyboard input, and file-transfer transport must not be globally reduced to seven bits: today `+CONSOLE7/8+` masks CP/M _console output_ only, and blindly extending it to input or raw transfers could corrupt binary data. “Whole path” here means an INI/profile-selected console-output policy plus a matching terminal interpretation, not 7-bit physical framing.

No separate `+c1_csi=+` setting is required for the first FAND test: in 7-bit CP/M output, `+0x9B+` cannot reach the parser, while in 8-bit ANSI output it is recognized. Keep the C1 recognition decision explicit in the parser so a later upper-half character-set policy can separate “8-bit text allowed” from “interpret `+0x9B+` as CSI” if those needs conflict.

The shared private-command dispatcher is a small extraction from the existing `+dispatch()+` prefix-`+>+` branch. Keep one bounded CSI recognizer and only the mode-specific dispatch decision. There are currently two different _directions_ of private CSI: application-output `+>4+`/`+>63+`/`+>68+` for graphics, backlight and zoom (plus the separate `+>64+` host-reflash prefilter), and host-keyboard `+>10+`/`+>11+`/`+>65+` etc. for history/profile actions. They need not be combined into one dispatcher merely because their wire syntax looks similar. Group screen/HAL controls separately from history/profile controls if that keeps dependencies clean; do not build two output CSI parsers, nor redesign history/keyword completion for this work. The latter has its own plan, `+docs/260915-21 history tokens and editing surfaces.adoc+`. Local keyboard controls keep their present path. Keep `+ESC [+` as the normal project encoding; add `+0x9B+` as an accepted short form for historical applications, not as a wholesale rewrite of configs or helpers. Document that a literal printable `+0x9B+` conflicts with C1 CSI in modes that enable it; future codepage design must resolve that explicitly.

*C1 boundary for this delivery:* FAND needs `+0x9B+` with ANSI output; recognize that byte as CSI only in ANSI ground state when Console8 lets it through. VT52 receives the reserved 7xtgv controls via unambiguous `+ESC[>+`, not C1 `+0x9B+`. Never mistake a VT52 `+ESC Y+` address byte for CSI. A later codepage design may revise this policy explicitly.

== Compatibility and performance cautions

* The historical VT100 control is already in this code: `+ESC[?2l+` enters VT52, and `+ESC<+` returns to ANSI. The https://www.vintagecomputer.net/digital/VT100/vt100_manual/chapter3.html[original DEC VT100 user guide] documents this as DECANM. The base ANSI/VT52 setting changes byte interpretation, not the TFT driver, framebuffer, geometry or palette.
* Plain printable bytes already take the same `+Terminal::put()+` path in both modes; the `+ansi+` branch is reached after `+ESC+`. VT52 commands are shorter and simpler, but any whole-screen speedup must be measured. TFT flushing and CP/M output cadence are likely larger costs than this branch.
* VT52 does not natively specify ANSI SGR color. Current `+setMode(false)+` does not reset `+ink+`, `+paper+` or rendition, and this is the chosen behavior: an explicit output-language switch preserves colors and existing cells. An application or SUB file may issue `+CSI 0m+` separately if it wants a fresh default; mode switching itself must not inject it.
* The current graphics flag and `+graphicsRow()+` implement DEC/VT100-style special graphics for bytes `+0x5F..0x7E+`; the original VT100 guide warns its VT52 graphics differ. Test `+ESC F/G+` with a real VT52 app before claiming glyph-perfect compatibility. `+Terminal::put()+` presently maps ordinary bytes `+>=0x80+` to `+?+`; a future 256-glyph font and codepage need a separate design, including the printable-`+0x9B+` versus C1-CSI collision. Neither console width nor decoder mode automatically supplies color or 256 glyphs.
* FANDINST's examined capability fields do not provide a general app-start/app-exit hook. It can describe VT52 cursor and erase controls, but may not be able to enter VT52 or restore ANSI itself. Choose the appropriate profile explicitly or run `+VT52.COM+`/`+VT100.COM+` around the application; no fake `+A0>+`-based auto restore is proposed. Existing `+[bankN]+` input/history behavior is unaffected.
* Future keyword lists should stay separate from the `+.BUF+` history as planned in `+docs/260915-21 history tokens and editing surfaces.adoc+`. They do not change the effective-bank input rule or justify coupling output mode to history-bank selection.

== Current geometry, prompt and palette audit (260917)

* On the 800x480 ES3++_++5, the HAL/INI geometries are 132x48 at 1x, 80x24 at 2x, 44x16 at 3x and 32x12 at 4x. At 2x only 66 of the 80 logical columns fit at once, so the existing *horizontal* pan is used. `+applyDisplayProfile()+` sets one `+Terminal::cols/rows/visibleCols+` model for output, cursor movement, scrolling, mirror and redraw; there is no app-only shadow geometry or vertical pan. `+setGeometry()+` preserves the overlapping rectangle and clears excluded cells. A profile's 80x24 override is feasible at 1x or 2x, but 24 rows do not fit at 3x/4x; give those zooms their own smaller overrides or fall back to their global geometry. No app-lifecycle boundary is involved. On 1x 80x24, the 320 physical pixels beyond the 80-column text width must not be painted as one giant gutter. The current code computes gutter as _all_ residual width, so implementation must decouple its physical edge width from the profile's logical text width and make the remainder an ignored/default-background area, cleared by CLS. The mirror reports the logical 80x24 view.
* `+cpmPromptEndColumn()+` currently accepts drive `+A..P+`, then *one or two* characters from `+0..9+` or `+A..F+`, then `+>+`; it can also skip up to four leading spaces. It does *not* recognize bare `+A>+`. The internal CCP prints decimal user number with `+%u+`, such as `+A0>+` or `+P15>+`. The screen recognizer can still be fooled by an application rendering that same pattern; preserve it for history heuristics, not program-exit truth.
* The four paper colors are white, pale pink, pale green and pale lavender; ANSI SGR backgrounds `+40..47+` and `+100..107+` are intentionally mapped into those four rather than a CRT-like black background. The sixteen inks are eight even/odd pairs; `+bold+`/SGR 1 turns an even normal ink into its darker odd companion, and SGR `+90..97+` directly selects those darker companions. The shared `+src/7xtgv-palette.h+` is *not obsolete*: this terminal and the native 7xtgv demos read the same values. The source default had been index 1 = RGB(0,0,0) on white, an inconsistency with the intended normal ink. Petr requested changing reset, SGR 0, SGR 39 and freshly blanked cells to index 0 = RGB(100,100,100), so black index 1 is the emphasized companion; this source edit is pending a firmware rebuild. SGR 7 reverse video truly swaps ink and paper, so an app can temporarily show a dark background even though its selected `+paper+` remains one of four pale entries.

ECMA-48 defines the eight SGR *color names*, and specifies default color `+39+` as implementation-defined; it does not prescribe RGB values. The `+90..97+` bright names are the later aixterm/xterm extension. Our darker emphasis and pale papers deliberately differ from a conventional dark-background xterm. For a concrete RGB reference, this project's separate GCLS `+xterm565()+` table uses xterm-style sample colors 0..7: `+#000000 #CD0000 #00CD00 #CDCD00 #0000EE #CD00CD #00CDCD #E5E5E5+`, and 8..15: `+#7F7F7F #FF0000 #00FF00 #FFFF00 #5C5CFF #FF00FF #00FFFF #FFFFFF+`. That table is for xterm256 _graphics samples_, not ordinary text cells. Sources: https://ecma-international.org/publications-and-standards/standards/ecma-48/[ECMA-48], https://invisible-island.net/xterm/ctlseqs/ctlseqs.html[xterm control sequences].

* `+CONSOLE7/8+` currently change only RunCPM's mask on *console output*. Keeping 7 as the initial global default is conservative; 8 preserves `+0x9B+` for FAND and is already required by some binary-console use such as XMODEM. It does not enable Czech characters: ordinary bytes `+>=0x80+` currently render as `+?+`. Later Czech/codepage work needs a glyph map and an explicit choice about whether `+0x9B+` is a C1 control or a printable codepoint. Do not mask the host serial link or keyboard input merely because console output is configured as 7-bit.

== Historical comparison: ANSI attributes and PC VGA text colors

ANSI/ECMA-48 names eight foreground colors with SGR `+30..37+` and the corresponding eight background colors with `+40..47+`. In a conventional palette-based terminal, the foreground/background pair for a color name normally selects the same color entry, but the standard does *not* prescribe RGB values or the default ink/paper colors (`+39+`/`+49+`). The later aixterm/xterm extension adds `+90..97+` bright foregrounds and `+100..107+` bright backgrounds. SGR 1 means _bold or increased intensity_; it does not intrinsically brighten the background. Thus bright background is an explicit extended-color selection, not a consequence of bold text. Sources: https://ecma-international.org/wp-content/uploads/ECMA-48_5th_edition_june_1991.pdf[ECMA-48&#44; SGR], https://invisible-island.net/xterm/ctlseqs/ctlseqs.html[xterm control sequences].

PC VGA text mode instead packs a character and one *8-bit attribute* into each screen cell. Attribute bits `+0..3+` select one of 16 foreground colors; bits `+4..6+` select one of eight background colors; bit `+7+` is a display-wide choice between per-cell *blink* and a fourth *background-intensity* bit. With blink enabled, the background is limited to colors `+0..7+`. With blink disabled and background intensity selected, backgrounds `+0..15+` (including bright white) are available, but hardware character blinking is lost. The mode choice is global, not independently selectable per cell. For example, `+F1h+` can be blue text on bright-white paper in intensity mode; in blink mode it is blinking blue text on ordinary white/light-grey paper. This explains why a light PC-FAND theme could have felt constrained, but its actual choice needs inspection of that program's video code. Source: https://bitsavers.trailing-edge.com/pdf/ibm/pc/ps2/42G2193_PS2_Hardware_Interface_Technical_Reference_Video_Subsystems_Sep92.pdf[IBM PS/2 VGA technical reference].

The *numeric order also differs*: ANSI color numbers run black, red, green, yellow, blue, magenta, cyan, white; traditional PC VGA attribute indices run black, blue, green, cyan, red, magenta, brown, white/light grey. A DOS ANSI driver must translate color names to VGA indices rather than copy the SGR digit into the attribute nibble.

[cols=",>,>",options="header",]
|===
|ANSI color family |VGA normal index |VGA intense index
|Black |0 black |8 dark grey
|Red |4 red |12 light red
|Green |2 green |10 light green
|Yellow |6 brown |14 yellow
|Blue |1 blue |9 light blue
|Magenta |5 magenta |13 light magenta
|Cyan |3 cyan |11 light cyan
|White |7 white/light grey |15 bright white
|===

The ANSI protocol and VGA hardware are separate layers. A modern software terminal can store foreground, background and blink independently; VGA's one-bit tradeoff need not apply. Conversely, VGA hardware's 16-background option does not guarantee that a particular DOS ANSI driver recognizes extended SGR `+100..107+`. https://bitsavers.trailing-edge.com/pdf/ibm/pc/ps2/42G2193_PS2_Hardware_Interface_Technical_Reference_Video_Subsystems_Sep92.pdf[IBM's compatible-color table] and the https://invisible-island.net/xterm/ctlseqs/ctlseqs.html[xterm extension] describe these different layers.

Blink and reverse need similar separation. VGA hardware blink normally makes the *glyph pixels* alternate with the fixed cell background; merely exchanging foreground/background color indices in software does not make the whole paper blink. ANSI SGR 5 (blink) and SGR 7 (negative image) may be combined, but ECMA-48 does not specify their precise pixel-level phases. A real DEC VT100 dimmed ordinary blinking glyphs and made *reverse-blinking* cells alternate between normal and reverse video, so the apparent paper changed too. This is a VT100 implementation detail, not a universal ANSI promise. Source: https://bitsavers.computerhistory.org/pdf/dec/terminal/vt100/EK-VT100-TM-002_VT100_Series_Technical_Manual_2ed_198009.pdf[DEC VT100 Technical Manual&#44; section 4.6.3.8].

Native 7xtgv has no blink attribute. Its present VT-emulation layer nevertheless stores ANSI SGR 5 as a compatibility flag: `+drawCell()+` suppresses glyph dots in the off phase and, with reverse set, leaves the already-reversed cell background fixed. It therefore does *not* reproduce the VT100's reverse/paper-flashing behavior. This is an explicit fidelity distinction to retain in tests and documentation, not a request to add native 7xtgv blinking or to change the renderer in the first legacy-compatibility stage.

== Staged implementation and gates

[arabic]
. *Parser baseline / C1 entry.* Add `+0x9B+` entry for the existing ANSI CSI scanner, preserving `+ESC [+` and all current 7-bit behavior. Test byte-by-byte and split chunks, malformed/overlong CSI, VT52 address bytes, GCLS pixel stream, and all existing tests. Exercise FAND's three-byte attribute fields under `+CONSOLE8+` without changing the RunCPM default. Confirm the intended negative case: the same compact bytes cannot survive `+CONSOLE7+`.
. *INI/profile policy.* Parse global `+mode=+`/`+console_bits=+` and bank-local `+mode=+`, `+input=+` and zoom-specific geometry in the existing atomic INI load; preserve current bindings and global display geometries by default. Resolve input preset first and explicit per-key overrides second. Preserve effective-bank selection for keys, history and editor adapters. Apply a bank's `+mode=+` and geometry only on explicit profile selection, and its geometry again on physical zoom change. Remove only the `+Keyboard+` fallback's accidental dependence on `+Terminal::ansi+`; verify mixed pairs such as ANSI output {plus} VT52 keys and ANSI output {plus} WordStar keys. Decouple gutter width from reduced logical-grid width; make CLS clear the physically unused area to default paper without treating it as terminal cells.
. *VT52 integrity and private controls.* Test the already-existing dynamic `+CSI ?2l+`/`+ESC <+` decoder transition, not a new renderer. Share the reserved application-output `+ESC [ > ... v+` grammar across modes; let GCLS recognize its required SGR/pixel stream only while armed, without changing the saved output personality. Keep local zoom/backlight/history/profile and host reflash functional in both modes. Verify ordinary ANSI screen commands do _not_ accidentally act as VT52 commands.
. *Mode defaults and explicit utilities.* Apply configured global mode and console-output width at boot (defaults ANSI and Console7); keep runtime `+CONSOLE7/8+` unsaved overrides. Add `+VT52.COM+`/`+VT100.COM+` and test them in ordinary CCP and SUB flows. Verify that a prompt or effective-history-bank flip does not restore ANSI, while explicit Alt{plus}number profile selection does apply that profile's mode default once without resetting color. Test cold boot, dynamic VT52 entry/exit, fake `+A0>+` from an app, profile selection, and app-issued mode/mask changes that must remain transient. The saved INI mode defaults change only when the INI is edited.
. *FAND acceptance.* Configure FAND first for ANSI output with `+CONSOLE8+` run explicitly or `+[global] console_bits=8+` selected for that experiment, plus measured editor-key mappings; use short `+0x9B+` CSI where its setup fields require it. Also test its VT52 capability table with explicit profile selection or `+VT52.COM+`. Verify screen and keyboard interactions on hardware. Keep Console7 the normal global default after the experiment unless there is a separately signed policy change; test a 7-bit-dependent program and XMODEM under the appropriate mode. ADM-3A has not yet been designed or justified against a concrete program; do not promise it in this delivery. Generalized PTY replay likewise stays out of this first delivery.

Use existing host C{plus}{plus} tests for each stage; batch edits before one target build. Keep the current working firmware archived/available while a candidate is staged as `+new+`. Hardware gates belong to Petr's short interactive checks, not an automated long RunCPM session.
