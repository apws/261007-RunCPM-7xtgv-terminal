= RunCPM CP/M drive/user, PIP, and internal-CCP quirks
:source-highlighter: highlight.js

== Purpose

This note records several easy-to-misread details of the current RunCPM setup. They matter because the internal CCP presents the current *drive* and *CP/M user area* together in prompts such as `+A6>+`, while ordinary CP/M programs still see those as two separate pieces of state.

The most important rule is:

____
`+A6>+` means *drive A, user area 6*. It does *not* mean a drive named `+A6+`.
____

Likewise:

[source,text]
----
A0>  = drive A, user 0
A4>  = drive A, user 4
A6>  = drive A, user 6
B3>  = drive B, user 3
----

This distinction explains the earlier PIP `+INVALID FORMAT: A6:+` / `+A0:+` errors.

'''''

[id="1-cpm-drives-and-user-areas-are-separate"]
== 1. CP/M drives and user areas are separate

Classic CP/M file specifications know drive prefixes such as:

[source,text]
----
A:
B:
C:
...
P:
----

A normal CP/M filename can therefore be written as, for example:

[source,text]
----
A:FILE.TXT
B:ASM.COM
----

But a normal transient CP/M program does *not* interpret:

[source,text]
----
A6:FILE.TXT
A4:ASM.COM
A0:LOAD.COM
----

as "drive A, user 6/4/0".

`+A6:+` is a convenience syntax implemented by this RunCPM internal CCP for changing the current drive and user area. It is not part of normal CP/M filename grammar.

A useful mental model is to read the RunCPM prompt:

[source,text]
----
A6>
----

as:

[source,text]
----
A [USER 6]>
----

rather than as a single drive identifier.

'''''

[id="2-the-internal-ccp-accepts-combined-driveuser-switching"]
== 2. The internal CCP accepts combined drive/user switching

The current RunCPM internal CCP accepts standalone drive/user-change commands such as:

[source,text]
----
A:
6:
A6:
----

The combined form is a RunCPM shell convenience.

Examples:

[source,text]
----
A0>A6:
A6>A4:
A4>A0:
----

After `+A6:+` the current CP/M state is simply:

[source,text]
----
drive = A
user  = 6
----

Normal programs launched afterwards see that standard CP/M state.

Do not assume that the CCP shorthand can be embedded in filenames or program names passed to transient commands.

For example, avoid thinking of these as ways to select CP/M user areas:

[source,text]
----
A4:ASM
A0:LOAD
A6:FOO.COM
----

A drive-qualified executable such as `+B:FOO+` is meaningful because `+B:+` is a real CP/M drive prefix. `+A4:+` is not the equivalent syntax for user area 4.

'''''

[id="3-why-pip-rejected-a6-and-a0"]
== 3. Why PIP rejected `+A6:+` and `+A0:+`

Commands such as:

[source,text]
----
PIP A6:ASM.COM=ASM.COM
PIP A0:ASM.COM=ASM.COM
----

fail because classic CP/M PIP parses `+A6:+` / `+A0:+` as malformed file specifications.

The failure is *not* evidence that this PIP is too old to understand ordinary drive-qualified filenames.

CP/M 2.2 PIP supports normal drive prefixes. Typical valid forms include:

[source,text]
----
PIP B:ZOT.COM=A:
PIP B:=A:GAMMA.BAS
PIP A:=B:ZAP.*
----

The problem is specifically that `+A6:+` is a RunCPM CCP notation, not a CP/M PIP drive notation.

'''''

[id="4-cpm-22-pip-uses-gn-for-source-user-areas"]
== 4. CP/M 2.2 PIP uses `+[Gn]+` for source user areas

The important PIP feature for this setup is the CP/M 2.2 *G option*:

[source,text]
----
[Gn]
----

where `+n+` is the source CP/M user number.

Conceptually:

[source,text]
----
DESTINATION = SOURCE[Gn]
----

means:

____
Copy SOURCE from user area `+n+` into the currently selected user area.
____

For example, when currently in A6, copy `+ASM.COM+` from A4 into A6 with:

[source,text]
----
A6>PIP ASM.COM=ASM.COM[G4]
----

Then verify:

[source,text]
----
A6>DIR ASM.COM
----

Another example, copying `+TEST.TXT+` from user 2 into current user 7:

[source,text]
----
A7>PIP TEST.TXT=TEST.TXT[G2]
----

The practical rule is:

[arabic]
. switch to the *destination* user area;
. use `+[Gn]+` to select the *source* user area.

For example:

[source,text]
----
A6:
PIP FILE.EXT=FILE.EXT[G4]
----

Do not try to express the destination user as `+A6:+` inside the PIP filespec.

=== Different source and destination filenames

The destination filename does not have to equal the source filename:

[source,text]
----
A6>PIP NEWNAME.COM=ASM.COM[G4]
----

This copies `+ASM.COM+` from user 4 into current user 6 under the name `+NEWNAME.COM+`.

'''''

[id="5-the-current-internal-ccp-searches-a0-for-shared-commands"]
== 5. The current internal CCP searches A0 for shared commands

This RunCPM internal CCP has a useful executable-search extension.

For an external command without an explicit drive prefix, it first tries the current drive/current user. If the program is not found there, it can search *A: user 0* as a shared command area. The repository layout intentionally uses A0 for core tools such as `+PIP.COM+` and `+LOAD.COM+`.

This means that while the prompt is:

[source,text]
----
A6>
----

a command such as:

[source,text]
----
A6>PIP ASM.COM=ASM.COM[G4]
----

can work even when `+PIP.COM+` itself is stored only in A0.

Conceptually the CCP does this:

[source,text]
----
current environment: A6
        |
        +-- look for PIP.COM in A6
        |
        +-- if absent, find shared PIP.COM in A0
        |
        +-- load PIP.COM
        |
        +-- restore the original current user/drive environment
        |
        +-- execute PIP while current CP/M user is still 6
----

Therefore the program location and the program's working CP/M user area are two different things.

This is particularly convenient for shared utilities.

'''''

[id="6-do-not-prefix-shared-a0-tools-unnecessarily"]
== 6. Do not prefix shared A0 tools unnecessarily

Because the internal CCP already searches A0, this is normally enough:

[source,text]
----
A6>LOAD VTSTART
----

There is no need to write:

[source,text]
----
A6>A0:LOAD VTSTART
----

and that notation is misleading because `+A0:+` is not a standard CP/M drive prefix.

The same applies to PIP and other shared utilities:

[source,text]
----
A6>PIP ...
A6>LOAD ...
----

Let the CCP find the command in A0 while keeping the current CP/M environment at A6.

'''''

[id="7-asmcom-and-source-file-location"]
== 7. ASM.COM and source-file location

The DRI-style assembler is simplest to use when `+ASM.COM+` and the source are available in the current user area.

For the current benchmark sources stored in A6, the straightforward setup is:

[source,text]
----
A6>PIP ASM.COM=ASM.COM[G4]
----

After that:

[source,text]
----
A6>ASM VTSTART
A6>LOAD VTSTART
A6>ASM VTSTOP
A6>LOAD VTSTOP
----

`+ASM+` conventionally takes the source basename and supplies `+.ASM+` itself:

[source,text]
----
ASM VTSTART
----

reads:

[source,text]
----
VTSTART.ASM
----

and produces the usual assembler outputs, including a `+.HEX+` file for LOAD.

`+LOAD VTSTART+` then reads `+VTSTART.HEX+` and produces `+VTSTART.COM+`.

Because `+LOAD.COM+` is shared from A0 through the internal-CCP search fallback, there is no need to copy LOAD into A6 merely to build the program.

'''''

[id="8-tested-benchmark-tool-workflow"]
== 8. Tested benchmark-tool workflow

With:

* `+VTSTART.ASM+` in A6
* `+VTSTOP.ASM+` in A6
* `+ASM.COM+` originally in A4
* `+PIP.COM+` shared in A0
* `+LOAD.COM+` shared in A0

use:

[source,text]
----
A6>PIP ASM.COM=ASM.COM[G4]
A6>DIR ASM.COM

A6>ASM VTSTART
A6>LOAD VTSTART

A6>ASM VTSTOP
A6>LOAD VTSTOP
----

After successful assembly/loading:

[source,text]
----
A6>DIR VT*.COM
----

can be used to verify the generated transient commands.

'''''

[id="9-quick-reference"]
== 9. Quick reference

=== Switch user area

[source,text]
----
A6:
----

RunCPM internal-CCP shorthand: switch to drive A, user 6.

=== Copy from another user area

Current destination user is 6; source is user 4:

[source,text]
----
A6>PIP ASM.COM=ASM.COM[G4]
----

=== Copy from another CP/M drive

Classic drive syntax remains normal CP/M syntax, for example:

[source,text]
----
PIP LOCAL.TXT=B:REMOTE.TXT
----

=== Run a shared A0 command

Simply:

[source,text]
----
A6>PIP ...
A6>LOAD ...
----

The internal CCP can locate the executable in A0 while retaining A6 as the working environment.

=== Wrong mental model

[source,text]
----
A6:FILE.TXT
----

is *not* a CP/M filename meaning "FILE.TXT in user 6".

=== Right mental model

[source,text]
----
A6>
----

means:

[source,text]
----
current drive = A
current user  = 6
----

and PIP user-area access is expressed separately with `+[Gn]+`.

'''''

[id="10-runcpm-specific-vs-cpm-standard-behavior"]
== 10. RunCPM-specific vs CP/M-standard behavior

It is useful to keep these categories separate.

[id="standard-cpm--cpm-22-behavior"]
=== Standard CP/M / CP/M 2.2 behavior

* drives are `+A:+` through `+P:+`;
* user areas are numbered separately;
* PIP uses `+[Gn]+` to obtain a source file from another user area;
* `+ASM name+` conventionally processes `+name.ASM+`;
* `+LOAD name+` processes `+name.HEX+` into `+name.COM+`.

=== Current RunCPM internal-CCP conveniences

* prompt combines drive and user, e.g. `+A6>+`;
* standalone `+A6:+` can switch drive{plus}user together;
* external-command search can fall back to shared commands in A0;
* therefore a program found in A0 can still execute while the active working environment remains another user area such as A6.

These conveniences should not be mistaken for extensions to the filename syntax understood by ordinary CP/M programs.

'''''

[id="11-correction-to-the-earlier-vtstart--vtstop-note"]
== 11. Correction to the earlier VTSTART / VTSTOP note

The earlier note `+260912-21 VTSTART VTSTOP CP-M assembly and PIP quirks.adoc+` interpreted the PIP errors as a limitation of an old PIP filename/drive parser. That diagnosis was incorrect.

The correct explanation is:

* `+A6>+` / `+A4>+` / `+A0>+` are combined *drive {plus} user* representations produced by the RunCPM internal CCP;
* PIP sees `+A6:+` or `+A0:+` inside a filespec and rejects them because they are not legal CP/M drive names;
* CP/M 2.2 PIP already provides the correct cross-user mechanism through the `+[Gn]+` option.

For the concrete case that triggered the investigation, the correct command is:

[source,text]
----
A6>PIP ASM.COM=ASM.COM[G4]
----

This behavior has now been tested successfully on the device.
