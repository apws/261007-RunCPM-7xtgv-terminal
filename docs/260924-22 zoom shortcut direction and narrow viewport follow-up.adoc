== Logical width is not physical viewport width

The failed VTGET case had a 40-column LOGICAL terminal, wrapping the protocol's
69-character data rows. An 80-column logical terminal with a physically narrower
viewport retains the complete rows in terminal memory and in the PC mirror.
The host transfer reads that logical mirror, not the physically clipped TFT.
Thus a small display does not itself block transfer, nor does it require zoom 1
when the chosen zoom is configured with sufficient logical width. Use 80 columns
as the established safe transfer geometry; height must also fit the protocol page.

== Stepped panning and optional indicator: ideas only

Current pan key routes call pan(0) and pan(viewportLimit()), i.e. left/right
edge jumps. With 80 logical columns and 26 visible, these show columns 0..25
and 54..79; columns 26..53 cannot be reached with those two jumps. The underlying
pan(offset) already clamps arbitrary offsets, so the missing part is incremental
navigation policy/key routing, not a different cell-memory format.

A future page-step policy could advance by visible width and clamp at the last
offset (for example 0,26,52,54), or choose an intentional overlap. Agree whether
to change the existing modified Home/End meaning or add separate step controls;
ordinary application Home/End should not be silently stolen. Automatic cursor
following remains a separate decision. No pan behavior changed here.

Petr also suggests optionally hiding the gutter cue and filling that strip with
paper color. At present the renderer only has a gutter when physical width leaves
residual pixels; W535 at 2x has none. An optional indicator policy is recorded,
not implemented, and need not alter logical geometry or pan availability.
