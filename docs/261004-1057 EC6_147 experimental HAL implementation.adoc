== Scope and current state

Petr approved implementing the non-touch Waveshare ESP32-C6-LCD-1.47 as
EC6_147. Source implementation and host tests are prepared; no firmware build,
device flash or CP/M file transfer has been performed. This remains experimental.
See link:261004-0030%20ESP32-C6%20single-core%20integrated%20runtime%20feasibility.adoc[feasibility findings].

One uniformly sectioned board header contains identity, geometry, shared
SPI initialization, display construction, SRAM history allocation, backlight
and reboot. The target name/profile is esp32c6-lcd-1-47 and the runtime INI
display ID is EC6_147. No INI is edited or sent automatically; a later device
configuration edit must begin by fetching Petr's live file.

== Shared SPI and ownership

Existing integrated modules do not have two independent owners of the card.
RunCPM owns all SdFat activity, including delayed terminal INI/history writes;
the terminal task publishes requests rather than writing the filesystem.
Existing dual-core modules also use separate display/SD peripherals. CPU task
priorities do not substitute for protecting a shared physical bus.

C6's LCD and SD share GPIO6 MOSI and GPIO7 SCK, with GPIO5 MISO, GPIO14 LCD
CS and GPIO4 SD CS. This HAL creates exactly one SPIClass(FSPI) object.
Arduino_HWSPI receives that same object with shared-interface mode, and the
existing XtgvSdSpiDriver receives it for SdFat SHARED_SPI mode.

The installed Arduino 3.1.0 SPIClass holds its parameter mutex from
beginTransaction to endTransaction. Arduino_HWSPI deasserts LCD CS before
ending its transaction; SdFat deselects the card and clocks its release byte
before deactivating the transport. Consequently only one task can configure
or transfer on this object at a time. Arduino_ESP32SPI is deliberately not
used here: its private low-level bus object would not share the SPIClass lock.
No new lock framework or library fork is added.

Clarification: FreeRTOS supplies the mutex primitives and schedules a waiting
task, but does not automatically lock arbitrary hardware access. Arduino's
SPIClass transaction methods take/release those mutexes; our HAL deliberately
connects the two libraries through the same instance. CONFIG_DISABLE_HAL_LOCKS
must remain disabled. Direct-register backends or nontransactional access
would bypass this guarantee. Neither the scheduler nor this bus lock replaces
one-task filesystem ownership. The manual's technical reference now records
this distinction and the experimental single-core runtime arrangement.

Panel initialization precedes launching RunCPM. The card is deselected before
panel initialization. Integrated SD startup must not reset/toggle the LCD CS
while the terminal could already be drawing; serial-only startup initializes
that deselect state separately. Both device clocks initially request 20 MHz;
the existing sdfat_spi INI policy and CARDMARK backend remain available for
SD trials. Hardware must verify arbitration and initialization under traffic.

== Single-core scheduling

runtime.h selects runtime_esp32_integrated_single.h when the SDK defines
CONFIG_FREERTOS_UNICORE. The dual-core runtime is unchanged. The single-core
runtime creates a priority-1 RunCPM task with a 16 KiB stack; Arduino's terminal
loop task is also priority 1 in the installed core. They time-slice one CPU.
After each terminalLoop, the terminal task blocks for one RTOS tick.

Petr approved using the existing HAL-owned abort-check seam for guest
cooperation. runcpm_hooks.h adds a single-core-only tick check to
_xtgvAbortRequested: after at least 25 ms since the previous yield it blocks
for one tick, then performs the normal forced-return check. CPU1 already calls
this seam every 65536 emulated instructions; the existing BDOS checks also
call it. Actual yield cadence therefore depends on the next seam invocation,
not a guaranteed 25 ms deadline. Watchdog protection is not disabled.

CPU, BDOS/BIOS, CCP, globals, disk and common RunCPM abstraction files are not
edited for this port. runcpm-config.h only adds the new selector to its
exactly-one-board validation. No helper externally suspends a task that could
be holding the shared SPI transaction lock. The task deletes itself when
runCPM returns; failed task creation releases terminal startup blanking and
reports the failure.

This policy needs busy-guest, busy-rendering and idle/watchdog hardware tests.
Do not infer that dual-core performance carries over, or that task priority
alone ensures idle time. First verify scheduler behavior and stack usage on
the installed C6 SDK before adjusting cooperation frequency.

== Initial panel and memory policy

The ST7789 is configured as native 172x320 with rotation 3 and controller
offsets 34/0, giving a landscape 320x172 panel, matching the existing RP2_147
layout. Initial logical backing plane is 80x24; visible columns at zoom 1 are
52, and the panel fits 16 full ten-pixel rows. Rotation, offsets and colors
remain hardware-unverified.

History uses ordinary new(nothrow), not ps_malloc: C6 has no onboard PSRAM.
The shared 100-entry-per-bank history budget is retained. Memory placement,
IRAM fit, allocator headroom and stack high-water marks require a real build
and hardware validation. CPU1 uses the existing ESP32 IRAM attribute policy,
without a function-local O2 override.

The initial 32-level backlight curve is deliberately capped at duty 127,
approximately 50% of the 8-bit range, following the vendor thermal warning.
Physical writes are capped too. This is a conservative starting curve, not
Petr-calibrated brightness. The existing boot-warning mechanism reports the
cap. Treat future recalibration and maximum brightness as an explicit decision.

== Approved heap diagnostics (pending rebuild)

Petr approved C6-only heap reporting. The single-core runtime captures a
baseline immediately before terminalSetup. The C6 board's existing boot-extra
hook prints that baseline plus a current snapshot when the RunCPM banner runs,
after RunCPM task creation, SD mount attempt and INI/history startup, but before
the CPU estimate and CCP. No new sketch/core hook is added.

[source,text]
----
Heap before: free=... largest=... B
Heap startup: free=... largest=... B
----

Both queries use MALLOC_CAP_INTERNAL | MALLOC_CAP_8BIT and report actual
allocator bytes, not the Arduino 320 KiB reporting ceiling. Largest is the
largest single allocatable block, not total free space. Each snapshot contains
two separate allocator queries; other task activity can change the heap between
them. These are startup snapshots, not peak-memory or stack high-water readings.
No additional heap buffer is allocated for reporting. Serial-only C6 builds,
which do not run the integrated capture, show only the startup snapshot.

Other boards' banner hooks are unchanged. Host single-core runtime tests verify
baseline capture precedes terminalSetup. The compiled 261004-1103 image predates
this diagnostic and must be rebuilt on request before the diagnostic is flashed.
