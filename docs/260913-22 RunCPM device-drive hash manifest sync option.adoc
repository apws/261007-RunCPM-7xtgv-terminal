= RunCPM device-drive hash manifest sync option
:source-highlighter: highlight.js

Status: design note only. Nothing described here is implemented or enabled.

== Motivation

The repository `+cpmdrive+` tree should remain the primary source of truth, but files may also be edited interactively on the device with CP/M tools such as TE. It should be possible to discover those changes before a later deployment overwrites them.

Timestamps are not a reliable basis for this comparison:

* CP/M 2.2 directory entries do not provide standard modification times.
* RunCPM stores files in FAT directories such as `+A/0+` and `+A/6+`, but the RP2350 build has no RTC callback configured for SdFat.
* Without that callback, SdFat uses a recognizable compile-year placeholder date and does not provide meaningful modification times for later writes.
* A single persistent dirty bit could report that something changed, but not which file was created, modified, renamed, or deleted.

== Possible design

Generate a device inventory containing one record per file:

[source,text]
----
drive, user, CP/M 8.3 name, exact or record-padded size, CRC32
----

Store the last synchronized inventory as a JSON baseline on Linux. A later scan compares three states: the baseline, the current device inventory, and the current repository mirror.

* Device changed only: retrieve the file into a review/staging location.
* Repository changed only: offer it for one-way deployment.
* Both changed: report a conflict; never choose a winner automatically.
* Present only in the new inventory: report a newly created file.
* Missing relative to the baseline: report a deletion without propagating it automatically.

Text files need a defined comparison form because repository files use normal host line endings while CP/M uploads use CR/LF, trailing Ctrl-Z, and 128-byte record padding. Binary files should always be compared byte-for-byte in their device representation.

== Efficient scan option

Extending the device with a read-only manifest command would avoid transferring every file at 115200 baud. It could scan the underlying RunCPM drive/user directories, calculate sizes and CRC32 values on the device, and send only the small manifest to the Linux tool. The existing transfer protocol would then retrieve only explicitly selected changed files.

The scanner should cover configured RunCPM drives and user areas, while keeping documented archive-only repository areas excluded. The saved baseline should also identify the physical device/card so inventories from different cards are not compared accidentally.

== Safety rules

* Scanning is read-only and must use the same exclusive serial/SD ownership as existing transfer operations.
* Never overwrite the repository directly from a device scan.
* Never upload, delete, or resolve a conflict without explicit review.
* Keep the repository mirror authoritative after reviewed device changes are imported.
* Hashes and the previous baseline are sufficient; an RTC and a full change history are not required.
