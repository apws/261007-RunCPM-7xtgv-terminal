Only the generated card location changes. The executable and evidence logs stay
on W: in both cases. These end-to-end timings establish a substantial storage
location penalty in this VM. The output test includes loading its approximately
11-KiB COM program, so its ratio must not be presented as pure rendering speed.
No SDL drawing occurs in this headless comparison. Local Windows remains slower
than the preceding Linux fixture; this test does not isolate every residual cost.

Source inspection explains a plausible amplification mechanism: the shared
Arduino abstraction opens, seeks and closes for each 128-byte sequential record.
The desktop storage adapter resolves/canonicalizes paths and checks metadata on
open; directory enumeration opens each entry. This combination entails many
small filesystem operations. Individual call costs have not yet been profiled.

Practical option: retain sources, executable and logs on W: while using an
explicit local Windows card. To improve direct W: card use, investigate repeated
filesystem work in desktop/storage.cpp, preserving path containment, persistence
and external-file behavior. No adapter/core changes or automatic card relocation
were made. Live sessions, INI/history and unrelated work remain untouched.
