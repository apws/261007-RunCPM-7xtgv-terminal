== 3. Ari: first review response

Good morning, Petr :-) Yes—I understand the intended direction, and **your mirror-driven, output-only SDL window is the simplest next step**. I reviewed the implementation and both documents against your comments. The existing work is a usable foundation, but several parts need adjustment.

First, a correction to yesterday’s report: all four headless tests still pass, but saying “the first four acceptance stages are implemented” was too broad. We have working proofs across those stages; the planned full visual fixtures, persistence recovery and representative card-content tests are not all covered yet.

**a) `cpmcard` and a mounted real SD card**

The adapter already accepts an arbitrary existing directory as its root. That can be either:

- Your copied `cpmcard` tree.
- The mount point of the real FAT32 card in a USB reader.

The operating system handles the underlying filesystem. However, copying FAT32 files onto an ordinary Linux filesystem does **not** preserve case-insensitive lookup. Our current adapter inherits that difference.

This matters with your actual copy: I found mixed-case filenames such as `Fand.com`. RunCPM can list such a name in uppercase, then attempt to open `FAND.COM`; our current Linux adapter can fail there.

The correction belongs entirely in the host storage adapter: case-insensitive lookup for each path component, consistently applied to open, existence checks, creation, removal and rename. If a Linux directory contains both `TEST.COM` and `test.com`, we should report that ambiguity rather than choose arbitrarily.

I would select the card root at launch, with an optional default in the launcher—not require recompilation or put your machine-specific mount path into every board header. The selected root stays fixed during the run. Ordinary INI/history saves would then reach that selected card, just as on hardware.

**b) Separate SDL boards versus reusing existing boards**

Both are possible. For your intended testing, I now prefer **selecting an existing board plus a desktop-build mode**.

There is already a useful boundary in every board header: its constants and defaults precede the `XTGV_HAL_IMPLEMENTATION` section. We can reuse those definitions while supplying desktop implementations of storage, display creation, backlight and runtime.

Importantly, we should reuse more than resolution:

| Board information | Why it matters on desktop |
|---|---|
| Physical width/height | Exact framebuffer and visible viewport |
| `display_id` | Selects the same existing INI section |
| Logical limits and zoom defaults | Reproduces terminal sizing and panning |
| Indicator offsets and rendering settings | Reproduces relevant visual behavior |

Your copied INI already has sections for all six physical display IDs. Yesterday’s new `SDL_1280` identity does **not** select `[display:EP4_10]`, even though both have 1280×800 pixels. Reusing the real board’s display identity fixes that mismatch.

The running application should still identify its **backend as desktop**, separately from the display configuration it models.

One detail needs deliberate handling: some physical boards draw directly and do not require a framebuffer `flush()`. The SDL presenter must still notice their completed drawing. We cannot blindly reuse every physical-driver setting and rely solely on yesterday’s Canvas flush counter.

Dedicated `SDL_1280x800` or `SDL_480x320` configurations remain useful for arbitrary layouts later. They need not duplicate the entire desktop implementation.

Window scaling is separate: a 1280×800 emulated framebuffer can be displayed in a smaller window without changing its terminal geometry.

**c) The remaining W535 SD_MMC code**

You are right: it is a retained legacy comparison route, not a dependency of this emulator.

It remains in the alternate board header, board selection, `--w535-sd-mmc` build option, CARDMARK condition and associated tests. Current normal board configurations use SdFat/SPI.

It can be removed from active code and tooling, while leaving the historical measurements in documentation. CARDMARK should depend simply on whether the selected backend provides raw-card access; it should not need a W535-specific exception.

**d) What the “Arduino emulation” actually does**

Your description is accurate: this is a limited desktop implementation of the Arduino services our application uses.

| Service | Current implementation |
|---|---|
| Graphics | Real Arduino_GFX and real `Arduino_Canvas` |
| Files | Our host adapter supplies the required `SD`/`File` operations |
| Serial | Minimal input queue; output currently discarded |
| Time | Native monotonic clock and thread sleeps |
| Runtime | Main terminal/rendering thread plus RunCPM worker |

One C++ distinction: these replacements do not all rely on abstract base classes. Arduino_GFX provides virtual graphics operations, but our storage replacement works primarily by exposing the same names and methods at compile time. It does not derive from a universal SdFat filesystem interface.

Consequently, **the desktop build currently uses a SdFat-compatible application interface, not the real SdFat filesystem implementation**. The real SdFat library would expect a block device containing FAT structures; a no-op SPI implementation would not turn a host directory into that device.

We could provide dummy SPI calls if some remaining caller needed them, but currently none does. Adding them would not improve compatibility with the code we actually run.

**e) Existing mirror as input and parallel output**

This is the strongest simplification in your proposal.

The terminal runtime already produces its mirror from the terminal’s cell state. We can retain that exact path:

```text
Existing Konsole/Kitty mirror ↔ desktop Serial transport
                                      ↕
                             Existing terminal runtime
                                ↕              ↓
                              RunCPM      Arduino_GFX
                                               ↓
                                          SDL window
```

That reuses our existing keyboard translation, Czech-layout handling, chords, profiles and mirror reconstruction. SDL initially needs only display presentation and window events.

For Linux, a **PTY—a local virtual terminal endpoint—looks like the smallest transport change**. The existing tools already operate on terminal file descriptors. There is one verified incompatibility: their serial setup unconditionally sets DTR; I checked a local PTY and that operation returns “inappropriate ioctl.” We therefore need an explicit desktop transport mode that skips physical serial controls and handles connection/snapshot state.

This is a small transport adaptation, but not literally zero changes. Serial output buffering, backpressure and mirror reconnect behavior also need implementation. Windows will need its own transport decision later.

My revised recommendation is therefore: **reuse the selected real board’s display configuration, use the host SD/File adapter with case-insensitive lookup, connect the existing mirror through a desktop Serial endpoint, and make SDL the framebuffer viewer.** That exercises substantially more of our current product with fewer new input-handling paths.

I made no implementation changes during this review and did not run against your `cpmcard` contents. The next work should follow this revised direction, with the documentation’s completion claims tightened accordingly.

== 5. Ari: second review response

[listing,subs=none]
----
Yes, Petr—these comments make the direction clearer. I agree with the revised scope, with two important corrections about refresh frequency and what a desktop card benchmark can measure.

**a) Uppercase card contents and root selection**

Agreed: we can keep the host adapter case-sensitive and require canonical uppercase names in CP/M drive/user directories. That removes the case-insensitive lookup machinery I proposed.

A separate normalization tool can first report proposed renames and collisions, then apply them explicitly. It should handle case-only renames reliably and refuse collisions such as `TEST.COM` alongside `test.com`. We need not rename unrelated material outside the CP/M drive/user tree.

The desktop launcher selects either `cpmcard` or a mounted reader’s directory. This is independent of the selected board. Both use the same host filesystem adapter, and the selected board’s existing `display_id` chooses its existing INI section.

**b) Preserve both direct drawing and explicit flushing**

Yes—we can preserve those application-level behaviors. The current HAL already describes them:

| Existing setting | Current effect | Desktop behavior |
|---|---|---|
| `XTGV_DISPLAY_NEEDS_FLUSH = false` | Drawing becomes visible without explicit `flush()` | Present changes after drawing, without waiting for a flush |
| `XTGV_DISPLAY_NEEDS_FLUSH = true` | Terminal schedules `gfx->flush()` | Publish framebuffer changes when that flush occurs |
| `XTGV_DISPLAY_FULL_FRAME_BUDGET` | Controls how much the terminal draws per batch | Retain the same drawing budget |
| INI `render_flush_hz` | Limits pending flush frequency | Retain the same scheduling |

The direct-drawing boards are currently the RP2350 modules and C6. The W535, W550 and P4 use explicit flushing.

For buffered mode, SDL must keep showing the last published image while subsequent drawing modifies the Canvas. Its texture can hold that published image; there is no need to copy another complete framebuffer merely for this distinction. For direct mode, the presenter uploads changed pixels after a terminal drawing batch. Backlight changes and window repainting can still update presentation independently.

Two corrections:

- **15 ms means approximately 66.7 Hz**, which is more frequent than 10 Hz—10 Hz means 100 ms.
- Current buffered-board defaults are **30 Hz** in the headers I inspected, although INI can override them. The parser currently accepts `render_flush_hz` from 0 to 60; zero removes the interval delay. Unchanged content does not cause continuous flushes.

This will reproduce our drawing policy and visible update cadence. It will not reproduce physical SPI transfer duration, panel scanout, DMA contention or tearing. Those still require hardware measurements.

And agreed: drop the dedicated `SDL_1280x800`/`SDL_480x320` board direction. Select an existing board and enable desktop mode. Ordinary future changes to geometry, gutters, indicators and terminal drawing should then carry across automatically. A genuinely new HAL operation may still require a corresponding desktop implementation.

**c–d) SD_MMC cleanup and CARDMARK**

The SD_MMC removal is now an agreed cleanup: remove the alternate implementation, build option and special-case tests/conditions; preserve the historical explanation in docs.

For CARDMARK, I recommend **adding a file-level mode while retaining the existing raw mode**. You valued CID/CSD decoding, and raw reads still answer a different question from filesystem reads.

For example:

- `CARDMARK ...` — existing raw-sector test and card information on supported hardware.
- `CARDMARK FILES` — common read-only file scan on hardware and desktop.

The file mode can use only the shared `SD`/`File` API. It can traverse the selected card root, read files with a fixed-size buffer, count files/bytes, calculate checksums and optionally repeat the pass to check agreement. It remains native code called by the same CP/M helper. No fake SPI is needed.

That is a moderate extension, not a rewrite of the whole diagnostic. Raw-card capability would restrict only the raw commands; CARDMARK itself could remain available on desktop.

However, **desktop throughput will not necessarily reduce to the card’s physical speed**. Ordinary file reads pass through the operating system’s cache. A repeated scan may read mostly RAM, even when the root is a real mounted SD card. Linux provides advisory cache controls, but they are not a portable guarantee that every read reaches the card. [Linux cache-advice documentation](https://man7.org/linux/man-pages/man2/posix_fadvise.2.html)

So the useful first version should report **file-read throughput through the selected backend**, with host caching explicitly identified. Using the same files and buffer size makes comparisons informative, but does not make desktop results equivalent to the existing raw SPI benchmark. A cache-controlled physical-media benchmark would be a separate, more platform-specific task.

**e) Mirror input and an output-only SDL window**

Agreed. Keep keyboard focus in the mirror, retain its full output, and let SDL show the simulated physical display. This also preserves the distinction between the mirror’s logical terminal view and the panel’s smaller viewport.

We can request always-on-top and avoid activating the SDL window when it appears. A stronger “this window can never take keyboard focus, even when clicked” policy depends on the window manager/platform; that may need a small platform-specific addition. It does not affect the terminal architecture.

A **PTY** is a software-created pair of connected terminal endpoints. On Linux, one end appears as a path such as `/dev/pts/7`. Our mirror can open that end much as it opens `/dev/ttyACM0`; the desktop Serial implementation owns the other end. Bytes travel between them without USB hardware. Raw mode prevents terminal echo and character processing from changing our protocol. [Linux PTY documentation](https://man7.org/linux/man-pages/man7/pty.7.html)

**ConPTY** is Windows’ facility for hosting console applications through communication channels. It has a related purpose, but is not a drop-in `/dev/pts` replacement or virtual COM port. We do not necessarily need it between our two programs—a pipe or local socket may suit that byte transport better. Also, our current mirror uses POSIX terminal APIs, so native Windows support requires more than changing one endpoint name. [Microsoft’s ConPTY documentation](https://learn.microsoft.com/en-us/windows/console/creating-a-pseudoconsole-session)

**Where the desktop code belongs**

I agree with renaming the runtime to `runtime_desktop.h`. It describes the alternative execution environment accurately.

I would still keep the `desktop/` directory. The runtime header should coordinate startup, the RunCPM worker and shutdown. The directory holds the substantial implementations: host files, Serial transport, SDL presentation, Arduino compatibility and native build/tests.

Putting all of those into one runtime header would mix several independent responsibilities into a large file. This is different from keeping each board’s configuration together: the real board header remains the single source of its display definition, while `desktop/` implements the reusable platform underneath it.

The settled direction therefore needs no separate SDL board definitions and no new keyboard translation layer. The substantive additions are desktop platform services, presentation respecting existing HAL policy, and the optional file-level CARDMARK mode. I have kept this turn to review; no files or card contents were changed.

== Final decisions (editorial index, not another chat message)

* Canonical uppercase CP/M names; no case-insensitive host resolver.
* Select real board plus desktop mode; no separate SDL geometry boards.
* Preserve direct/flush policy and existing per-display INI settings, including 10 Hz.
* Output-only SDL panel and complete existing mirror over desktop Serial transport.
* Separate `runtime_desktop.h` coordinator and reusable desktop platform sources.
* Remove W535 SD_MMC active support; preserve historical evidence.
* CARDMARK remains useful on hardware; desktop unsupported. The proposed FILES mode is dropped.
* New CHAT/PLAN/DONE filenames include minute precision; resume from PLAN plus later DONE evidence.
