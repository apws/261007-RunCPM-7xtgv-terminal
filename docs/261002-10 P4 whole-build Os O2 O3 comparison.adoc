== Controlled settings and build scope

All three builds use CPU1 Z80run in IRAM, 20 MHz SdFat SPI, LDO4 power,
360 MHz P4 and the same terminal configuration. No P4 function-specific
optimization override is enabled. The baseline is 261002-1005, not the earlier
12 MHz / flash-resident interpreter builds.

The target-aware build tool now accepts `--optimization O2` and `O3` for
P4 using Arduino ESP32's `compiler.optimization_flags` property. RP2_147
retains its existing `build.flags.optimize` property. Normal rebuilds still
use the profile default; neither trial changes that default to O2/O3.

Both trial builds passed. Their compile databases each contain 203 source
compilation entries, all using the requested -O2 or -O3 respectively.
This covers sketch, source libraries and Arduino core; Espressif's supplied
precompiled SDK archives are not rebuilt or reoptimized. The five build-property
tests pass. No firmware was flashed during this comparison.

DRAM1 initialized data, IRAM data/BSS, flash TLS data, RTC force/noinit
sections and exception-frame header are zero in these images.
The `.flash_rodata_dummy` reservation is 393216 / 393216 / 458752 bytes:
it models address-space alignment/overlap, NOT additional code/data to sum
with flash text. Debug sections and ELF metadata account for the large ELF
file sizes; the application `.bin` is the relevant deployed application file.
Runtime heap allocations, task stacks, DSI framebuffer/PSRAM usage are NOT
measured by these static totals.

Placement from ELF:

* All three Z80run symbols are at `0x4ff0031c` in `.iram0.text`.
* IRAM text starts at `0x4ff00000`.
* DRAM0 initialized data starts at `0x4ff19480` for Os and `0x4ff1a100`
  for O2/O3, after aligned IRAM code.
* DRAM1 BSS starts at `0x4ff40000` in all three.
* Flash text starts at `0x40000020`; read-only data starts at `0x40060120`
  for Os/O2 and `0x40070120` for O3.

Arduino reports 21512 bytes (6%) of globals for all three, omitting
DRAM1 BSS. Do not use that figure as the complete RAM footprint.
O2/O3 consume 3200 more bytes of aligned internal instruction RAM than Os;
static data size is unchanged. O3's interpreter is slightly smaller than
O2's, but O3 grows flash code substantially elsewhere.

== O2 results and hardware-SPI check

Petr reports O2 active CPU 402351 us / 32.35 MHz, quiet 401906 us /
32.38 MHz; VTDRV W write 5914956 us / 5.41 KiB/s, read 2450710 us /
13.06 KiB/s, verify PASS. Like O3, these CPU samples are slower than Os;
disk rates remain essentially unchanged.

The P4 storage path really uses hardware SPI. Arduino's global SPI is
SPIClass(FSPI); P4 FSPI index 0 maps to hardware SPI2. SPI.begin maps
CLK43/MISO39/MOSI44 to that controller. GPIO calls for unused SD inputs
and chip select do not implement bit-banging. SdFat receives that SPIClass
pointer. DEDICATED_SPI describes bus ownership, not DMA or batching.

However, inspection of pinned SdFat 2.3.0 reveals a significant difference:
SdFatConfig.h defaults USE_SPI_ARRAY_TRANSFER to 2 on ARDUINO_ARCH_RP2040,
but to 0 otherwise, including ESP32. No project override exists. With zero,
SdSpiLibDriver.h loops over SPIClass::transfer(byte), even for sector payloads.
Arduino then starts/waits for individual hardware transactions. This is
hardware SPI with per-byte software overhead, NOT software-generated clocking.

Array-transfer mode 1 is a possible ESP32-compatible trial: it calls the
existing transfer(buffer, count) API, with a temporary buffer for writes.
Arduino's buffer path processes up to 64 bytes per hardware operation and
polls completion; this still is not DMA. A consistent compile-time setting
must reach SdFat's compiled sources too, not only the sketch's header.
This is a source-confirmed difference and plausible contributor, not a
measured attribution of the entire RP2350/P4 throughput gap. No driver or
configuration change was made during this inspection.

== Approved P4 buffer-transfer trial, pending rebuild

Petr approved trying buffer transfers. The P4 target now adds
`-DUSE_SPI_ARRAY_TRANSFER=1` to build-wide flags, covering both sketch and
SdFat source compilation. No installed library, RunCPM core, SPI controller,
clock or other board's target flags were changed. The board header documents
why a header-local define would not suffice.

Mode 1 uses Arduino's in-place transfer(buffer, count). For reads, SdFat
fills the receive buffer with 0xff before transfer; for writes it uses a
512-byte temporary buffer so received SPI bytes do not overwrite the caller's
data. Arduino services these buffer requests in up-to-64-byte hardware chunks,
polling completion, not DMA. Command/status single-byte transfers remain.

A native test compiles the actual installed SdFat 2.3.0 driver against a
mock Arduino SPI API: a 512-byte read uses the buffer overload, a 513-byte
write exercises the scratch-buffer boundary and preserves the caller's data.
That test, six build-property tests and six target-metadata tests pass.
This does not test hardware timing or actual throughput.

Rebuild/reflash remain pending. For a controlled comparison with the currently
flashed O2 baseline, the next trial build should explicitly use
`--optimization O2`; ordinary profile builds still default to Os. Current
staged/device images are unchanged and still use byte-at-a-time payloads.

== Requested 50 MHz experiment (not built or flashed)

Petr requested a read-only boot/read trial with the P4 SPI ceiling raised to
50000000 Hz. Only the board constant and its native test expectation changed.
The installed Arduino divider calculation uses a 90 MHz reference: a 40 MHz
request selects divide-by-three, and 50 MHz selects divide-by-two. These imply
30/45 MHz only if the peripheral input matches that reference; actual clock
source registers or SCK measurement remain to be checked. Earlier benchmark
clock labels describe requested speeds, not measured SCK.

No CMD6 High-Speed negotiation or persistence behavior was changed. A normal
boot/interactive session is not guaranteed read-only: terminal INI/history
persistence can write independently of VTDRV. Before deploying a genuinely
read-only experiment, agree on write prevention (or use a disposable card).
The verified 40 MHz-request firmware remains on the device and staged unchanged.
