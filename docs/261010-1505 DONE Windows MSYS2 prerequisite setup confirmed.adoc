== One MSYS2 installation

The official installer created the MSYS2 installation. Project setup.cmd does
not install another MSYS2: windows.cmd calls Bash in the selected installation,
setup.sh runs that installation's pacman for MSYS and UCRT64 packages, and MSYS
Python downloads pinned GFX into the project's build dependency directory.
MSYS /usr and native /ucrt64 tools are parts of the same installation. Project
setup neither installs nor enables WSL or Hyper-V.

== WSL alternative discussed, not selected

WSL could reuse the Linux executable, PTY and mirror path, with WSL2 providing
the closest kernel compatibility. Current Linux setup is broader than a desktop
setup: it also installs Arduino MCU dependencies. WSL deployment has not been
validated by the project.

WSL1 avoids a managed VM; WSL2 uses Virtual Machine Platform, a subset of
Hyper-V architecture. Inside a Windows VM, WSL2 needs suitable nested
virtualization. VirtualBox documents nested virtualization with limitations;
do not infer supported nested Hyper-V merely from a checked VT-x/AMD-V box.
WSLg requires WSL2 and a sufficiently recent Windows build. LTSC alone does
not identify that build. None of these alternatives was enabled or installed.

Keep the current MSYS2 native-Windows build experiment as the next step.
Working card and sessions remain untouched. Feature evidence updated; no
runtime change, compilation, deployment or commit in this checkpoint.
