= RP2_2 INI cache pressure and Os trial
:source-highlighter: highlight.js

== Report and evidence

RP2_2 build 261003-2159 boots but prints `INI RAM cache unavailable; autosave
will retry.` Its profile geometry is applied, while the SPI summary remains
20 MHz. Petr requested a red-paper error marker and investigation, then
authorized fetching the live INI and suggested an Os optimization trial.

The live A0:7XTGVTRM.INI was fetched to a temporary inspection folder:
15,232 bytes, with global sdfat_spi=40 and an RP2_2 display section. Fetch
succeeded; the device file was not changed and the visible mirror was restored.
This rules out an oversized current file and demonstrates later readability,
but does not prove the original boot-time block read succeeded.

The RP2_2 profile selects Optimize3 (O3). Its build reports 170,204 bytes of
static globals out of 524,288 SRAM bytes, leaving 354,084 before runtime heap
and stack consumption. LineHistory contains ten banks of 255 entries and is
allocated by the board during terminal initialization. Native sizeof gives
326,944 bytes, leaving approximately 27,140 bytes before other allocations
and stacks. The INI cache additionally requests roughly 15 KiB, rounded in
256-byte increments. RAM pressure is therefore a strong allocation-failure
candidate, not yet a measured boot-time free-heap diagnosis.

The earlier generic warning cannot distinguish opening, allocation, size-limit
or incomplete-read failures. Startup can parse the INI by streaming when the
full cache fails; the subsequent SPI policy conservatively uses 20 MHz unless
the full cache is valid. Thus the geometry and clock output are consistent
with this failure path. This investigation does not change that clock policy.

== Changes and next hardware check

The cache loader now records the attempted byte count and distinguishes
allocation failure, exceeding the 64 KiB cap, and an incomplete file read.
The boot warning uses the existing ANSI red-paper helper, resets attributes
after the line, and retains plain text for non-ANSI profiles. Tests cover
short-read, unavailable-file and oversized-file diagnoses. History depth and
device configuration are unchanged.

The build wrapper accepts Os alongside O2/O3 and permits the same trial for
RP2_2 as RP2_147. A requested RP2_2 Os candidate is prepared; no automatic
flash is part of this trial. Os primarily reduces program code; it cannot
shrink the fixed history object. Any benefit to the remaining SRAM must be
checked in build/link results and on hardware, not assumed from flash savings.

After an authorized flash, record whether caching succeeds, or the specific
red diagnostic. If allocation failure is confirmed, review history depth or
allocation ordering separately; no history reduction is silently applied.

== 2245 approved history reduction

Petr approved reducing history, then preferred a common limit because the
BUF file is shared between modules. All modules now retain 100 entries per
bank instead of 255; ten banks and the 127-character entry limit are unchanged.
This is one constant in the terminal's LineHistory class, not another HAL
switch. Keyword-list capacity remains a separate future design question.

The host-measured history object shrinks from 326944 to 128544 bytes, saving
198400 bytes (193.75 KiB). The INI cache remains in ordinary RAM. RP2_2 has no
onboard PSRAM in the
https://files.waveshare.com/wiki/RP2350-Touch-LCD-2/RP2350-Touch-LCD-2.pdf[Waveshare schematic];
the ESP32 boards already allocate history in PSRAM.

The BUF v1/v2 format and checksum rules are unchanged. The loader appends
oldest first, so a larger saved history retains the newest 100 entries per
bank. The next normal save writes only those retained entries: older entries
will be dropped from that saved file. No device BUF has been overwritten or
transferred by the agent. Tests cover importing 255 entries into every bank
and recalling across wraparound with the new limit.

The earlier Os candidate 261003-2237 has 239376 program bytes and 169096 static
SRAM bytes, compared with 308152 and 170204 respectively in the preceding O3
build. It predates this history reduction: another requested rebuild is needed
before flashing the smaller-history implementation. No flash was performed.

== Future compact history storage (not implemented)

RP2_2's SRAM pressure makes variable-length storage worth considering later.
Human-paced input and recall do not require every command to reserve the full
127-character slot. C++ can use a vector of strings, but each string can add
allocation overhead and heap fragmentation; vector growth can temporarily
require both old and new allocations. A vector of the current fixed-size
entries alone would not remove the wasted space inside short commands.

The preferred candidate is a bounded packed text buffer with an index of
entry offsets and lengths. Store only the actual command bytes, maintain ten
bank identities and chronological order, and evict oldest commands when the
byte budget is full. Ordinary functions can handle insertion and occasional
compaction; this does not require a new RunCPM hook or HAL macro. Define and
test per-bank fairness, index capacity and full-buffer behavior before changing
the implementation. Future keyword dictionaries need a separate budget and
must not silently consume the history allocation.

Such storage could use PSRAM on the equipped ESP32 modules, while RP2_2 uses
internal SRAM. Keep the editable BUF v1/v2 on-disk representation unchanged;
in-memory layout need not match the file. This is a documented option, not an
implemented dynamic allocator: the requested rebuild still uses fixed
100-entry banks.

and VTDRV under matching card, INI clock and display conditions. In particular,
the earlier cache failure used the 20 MHz fallback while the successful
