= Host SAK, NTFS recovery and Codex CWD incident report
:source-highlighter: highlight.js

Recorded 260922 by Petr and Ari after the host and project were recovered. This report preserves the evidence relevant to 7xtgv development without treating the host incident as a terminal-firmware defect.

== Executive summary

* No 7xtgv repository loss or corruption was found. Before this report was added, `+main+` was clean at `+e3dc01e+` (`+260922-0016+`, `+terminal: add configurable keys and diagnostics+`), matched `+origin/main+`, and `+git fsck --no-dangling+` reported no problem.
* Petr's suspected chord was identified precisely. At `+260922-010457+` and again at `+260922-010536+`, `+systemd-logind+` recorded `+Secure Attention Key sequence pressed on seat seat0+`. The installed systemd catalog identifies that built-in SAK as *Ctrl{plus}Alt{plus}Shift{plus}Esc*.
* SAK did not directly request a reboot. On both presses SDDM created a new X11 greeter, first on VT1 and then on VT3. Petr successfully authenticated into a new Plasma X11 session after each press.
* The incident boot's journal ends abruptly at `+260922-010628+`, and the next boot starts at `+260922-010745+`. There is no intervening system shutdown or reboot transaction. `+last -x+` therefore labels the open sessions as `+crash+`. This is consistent with an uncontrolled reset or power interruption, but the retained logs do *not* establish that SAK caused it.
* The external 2 TB NTFS volume at `+/_/drv/e+` was reported by Petr as dirty, with slight MFT damage. Windows `+chkdsk /f+` repaired it and Petr found no lost data. At report time it is accessible, but Linux has it mounted *read-only*; see the storage-status section below.
* The long Codex conversation was not lost. Its session was created with CWD `+/home/falken+`, so the normal CWD-filtered resume picker did not show it when Codex was launched from either spelling of the repository path. The recorded tool calls nevertheless show that project work was done in only this repository.

== What the keyboard chord actually does

The SAK behavior is supplied by current `+systemd-logind+`; it is not a custom Petr key binding. Local systemd documentation says that Ctrl{plus}Alt{plus}Shift{plus}Esc emits `+org.freedesktop.login1.SecureAttentionKey+`, requesting a secure login dialog or greeter. The effective default is visible in `+/etc/systemd/logind.conf+`:

[source,ini]
----
#HandleSecureAttentionKey=secure-attention-key
----

The two journal sequences match this exactly: each SAK event is followed by `+sddm: Adding new display+`, a new X server and an SDDM greeter. Messages saying `+Reached target Shutdown+` in these sequences belong to the short-lived SDDM *user manager* after successful login; they are not system shutdowns.

The current KDE global shortcuts are distinct:

[cols=",",options="header",]
|===
|Chord |Current KDE action
|`++Ctrl+Alt+Del++` |Show Logout Screen
|`++Meta+Ctrl+Esc++` |Kill Window
|`++Meta+Shift+Esc++` |Disable Active Input Capture
|reboot actions |unassigned (`+none+`)
|===

No `++Ctrl+Alt+Shift+Esc++` reboot mapping was found in the KDE shortcut files. The XKB options are only `+shift:breaks_caps,caps:none+`; the X-server termination option `+terminate:ctrl_alt_bksp+` is not enabled.

At the lower system layer, the vendor `+/usr/lib/systemd/system/ctrl-alt-del.target+` points to `+reboot.target+`, as is normal for console Ctrl{plus}Alt{plus}Delete. A local override created at approximately `+260922-0655+` currently masks `+/etc/systemd/system/ctrl-alt-del.target+` to `+/dev/null+`. This prevents that separate low-level route. It does not change the SAK chord described above. This mask appears to be post-incident remediation; this report does not attribute who created it.

=== Causal conclusion

The chord and its immediate effect are proven: Ctrl{plus}Alt{plus}Shift{plus}Esc invoked SAK twice and created two additional greeter/session transitions. A direct reboot mapping is disproven by both configuration and the journal. The final reset was not orderly, but its cause is unproven. Possible relationships include an X/SDDM/session failure exposed by repeated SAK, a later manual hard reset, or an independent hardware/kernel/power event. The retained evidence does not justify selecting one of these as fact.

== Storage layout and current status

Petr intentionally uses two drive-like namespaces:

* physical external filesystems are mounted under `+/_/drv/+`, analogous to drive letters for real volumes;
* semantic, SUBST-like working routes live under `+/home/falken/_/drv/+` and are bind mounts into selected directories on the internal Btrfs filesystem.

They are related conventions, not a requirement that every physical drive has an identically named semantic alias. The current `+fstab+` evidence is:

* NTFS volumes `+e+`, `+f+` and `+g+` mount at `+/_/drv/e+`, `+/_/drv/f+` and `+/_/drv/g+`;
* semantic `+x+`, `+w+`, `+v+`, `+t+` and `+i+` bind selected directories from `+/home/falken/_/+` into `+/home/falken/_/drv/+`;
* there is currently no `+/home/falken/_/drv/e+` alias.

The project’s preferred full path is:

[source,text]
----
/home/falken/_/drv/v/260906-7xtgv
----

An equivalent route used previously is:

[source,text]
----
/home/falken/_/drv/w/ver/260906-7xtgv
----

Both resolve through Btrfs bind/subvolume routes to the same directory object. At report time each has device number `+52+` and inode `+5724319+`. They are not symbolic links, so `+readlink -f+` preserves the spelling even though they refer to the same object. The repository is on internal Btrfs, not on the damaged NTFS `+e+` volume.

== Codex CWD, aliases and `+/resume+`

The conversation itself was intact. Local Codex state records the long thread as:

[source,text]
----
thread: 01a09a8f-e318-7042-908b-a26152602fd8
CWD:    /home/falken
start:  260913-133836 local time
----

All nine locally recorded September threads have `+/home/falken+` as their session CWD. That explains why launching Codex from `+/home/falken/_/drv/v/260906-7xtgv+` or the equivalent `+w/ver+` route produced an empty ordinary resume list: the picker uses recorded CWD/project context, not filesystem inode equivalence. The two path spellings further cannot be assumed equivalent by a text-based CWD filter even though `+stat+` proves they share an inode.

This is consistent with the official Codex documentation: the directory where the CLI starts is treated as the project, chats record their working directory, and `+/resume+` resumes a previous conversation. The configuration reference also documents `+[tui].resume_cwd+` for choosing the resumed chat's working directory when it differs; this is separate from asking the picker to include all projects.

The reliable recovery commands are:

[source,sh]
----
# Run from the repository and show sessions from every recorded CWD.
codex resume --all

# Resume this exact thread while setting the new working root explicitly.
codex resume -C /home/falken/_/drv/v/260906-7xtgv \
  01a09a8f-e318-7042-908b-a26152602fd8
----

Official references:

* https://learn.chatgpt.com/docs/projects?surface=web&translationFallback=es-419[Codex projects and working directories]
* https://learn.chatgpt.com/docs/config-file/config-sample?translationFallback=es-419[Codex configuration sample (`+resume_cwd+`)]

The rollout history for `+260921+` contains execution workdirs only under:

[source,text]
----
/home/falken/_/drv/v/260906-7xtgv
/home/falken/_/drv/v/260906-7xtgv/src/7xtgv-vt100-runcpm

Thus no second project repository was used during the relevant development day. The session metadata says “started in `+/home/falken+`,” while individual tools were deliberately run with the real repository as their workdir. These statements are compatible.

Codex’s local JSONL rollout files retain timestamps for individual events even though the current rendered conversation does not show a timestamp beside each turn. They can be used for later chronology reconstruction.

== Operational lessons

* Treat Ctrl{plus}Alt{plus}Shift{plus}Esc as a reserved host SAK on this machine. It is not a safe arbitrary chord for 7xtgv input testing.
* Keep host-global chord experiments separate from the serial terminal's own key encoder. Inspect KDE shortcuts and systemd/logind behavior before trying a four-modifier combination on the live desktop.
* Use `+codex resume --all+` after starting from a different CWD, or resume the known thread ID with `+-C+` to relocate it deliberately.
* Prefer the canonical project spelling `+/home/falken/_/drv/v/260906-7xtgv+` in commands and reports. The `+w/ver+` spelling is valid but makes textual CWD histories look like separate trees.
* Keep external physical mounts and semantic internal aliases conceptually distinct. A fault on `+/_/drv/e+` did not imply damage to the Btrfs-hosted repository.
* Before returning `+e+` to normal work, verify separately that it has genuinely regained read/write mount state; this report only establishes readable access.

== Evidence boundaries

This report intentionally does not claim:

* that SAK itself rebooted or crashed the kernel;
* that the NUC fan condition caused the reset;
* that the NTFS damage preceded rather than resulted from the uncontrolled reset;
* that read-only access proves remaining NTFS corruption;
* or that the battery work had any connection to the computer incident.

Those would require evidence beyond the retained journal and current configuration. The verified outcome is narrower and encouraging: the machine, the repository, the Codex history and Petr's external data were recovered, with `+/_/drv/e+` read/write status still needing an explicit later check.
