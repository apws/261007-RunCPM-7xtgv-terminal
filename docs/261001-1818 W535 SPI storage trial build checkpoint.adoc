== Hardware trial and recovery, 261001-1857

Petr requested `++reflash++`. The connected firmware identified as
`++jc8048w535++` build `++261001-1611++`, and esptool flashed and verified the
SPI candidate. Instead of reaching CP/M, it reboot-looped on the ESP-IDF
assertion `++spi_hal_setup_trans: spi_ll_get_running_cmd(hw) == 0++`.
Decoding the SPI candidate's backtrace located the failing transaction in
`++Arduino_ESP32QSPI::writePixels++`, called from the display canvas flush.

The conflict is concrete: Arduino's global `++SPI++` on ESP32-S3 is
`++SPIClass(FSPI)++`; FSPI maps to the SPI2 peripheral. The installed
Arduino_GFX `++Arduino_ESP32QSPI++` also defaults to `++SPI2_HOST++`. The
trial initialized both card SPI and display QSPI on the same hardware host
through independent drivers/tasks. This image is *not deployable as built*.
A next source trial should give the card its own ESP32-S3 `++SPIClass(HSPI)++`
(SPI3) on the same card GPIOs, then compile and test again. This is not a
generic request to change the RunCPM core or the display transport.

The previous `++261001-1611++` SD_MMC image was restored through the guarded
reflash dispatcher. Because the crashing firmware could not answer identity,
recovery used the one-shot `++--allow-unidentified-target jc8048w535++` after
the same physical USB port/chip had been identified before the SPI upload.
The restored SD_MMC image is now `++current++`; the SPI candidate was kept at
`++261001-1855 rejected-new++`, and no `++new++` candidate remains. It reached
the SD_MMC boot banner but could not initialize the card before a physical
power cycle; the card may still be latched in SPI mode. Recovery of the card
mount remains to be verified after power is removed and restored.

The same-card `++VTDRV++` gap remains unexplained by this failed trial:
RunCPM still opens, seeks and closes the FAT file for each 128-byte record.

== 20 MHz result and 40 MHz build, 261001-2012

On the 20 MHz direct-SdFat W535 image, Petr's `++VTDRV RW++` measured
6.56 KiB/s write and 15.99 KiB/s read for 32 KiB; verification passed.
Compared with 12 MHz direct SdFat (5.82/13.99 KiB/s), the gains are modest.
His `++VTCPU++` reported 17.49 MHz active and 17.51 MHz quiet. The VTCPU
quiet pass suspends the terminal task; VTDRV currently has no quiet mode.

The W535 display uses `++Arduino_Canvas++` as a full 320x480 RGB565 buffer.
Its `++flush()++` sends the whole frame, but our terminal only requests a
flush for dirty cells, cursor blink, disk indicator or other visible changes.
The configured 10 Hz is a cap on pending flushes, not a constant scanout.
The 307200-byte canvas allocation uses `++aligned_alloc++`; PSRAM placement
is likely given the size, but the allocation call does not explicitly request

activity indicator can cause display flushes even without new text.

with no other firmware behavior changed. Installed SdFat accepts this clock
request; actual signal quality and card reliability on this board are

`++ccb5ec61bf6a4585a5e56eac30b578ae51776ca566ed7c272f987cc67c2ed771++`.

== W/Q modifier implementation staged in source, 261001-2046

With Petr's approval, `++W++` is now the documented write-and-read modifier;
`++RW++` remains a legacy alias. `++Q++` is independent and may appear before
or after `++W++`. `++VTDRV Q++` remains read-only; `++VTDRV W Q++` quietly
times *both* write and read, then resumes the terminal for verification.
The CP/M tail parser now consumes length-bounded whole tokens and rejects
duplicates or glued trailing text, addressing the observed `++RW Q++` and
`++Q RW++` misinterpretation.

The private host port adds quiet-write begin/end commands 11/12. Firmware
capability `++IN 7Eh++` now returns `++B++` for both quiet passes; the running
build `++261001-2036++` returns `++Q++` for quiet reads only. The updated
COM accepts either value for `++Q++` alone, but requires `++B++` before
`++W Q++` touches the retained fixture. Thus installing the COM ahead of the
firmware does not silently run an untimed write or overwrite the test file.

SLR Z80ASM assembled the updated COM; disposable native RunCPM tests passed
`++W++`, legacy `++RW++`, plain read and verify. They confirmed old-firmware
rejection for `++Q++`, `++W Q++`, `++Q W++` and malformed/duplicate options,
without changing the fixture. The updated binary is in the local A0/A6
mirrors only. The firmware source and COM still need Petr's next explicit
rebuild/transfer/reflash cycle before quiet write can be measured on device.

== Quiet write/read hardware result, 261001-2110

Petr ran `++VTDRV Q W++` on W535 build `++261001-2101++` at the requested
40 MHz SPI clock. The 32 KiB quiet write took 4024960 us (7.95 KiB/s), the
quiet read took 1622683 us (19.72 KiB/s), and full verification passed. The
earlier active write/read on the same board had measured 7.29/17.86 KiB/s;
these short, non-paired runs suggest roughly 9-10 percent benefit from
pausing the terminal task, not raw-card speed.

The on-screen disk indicator appeared red throughout the quiet run. This is
consistent with the existing implementation: `++W++` deletes the old fixture
before starting quiet timing, which can light the indicator; its 75 ms pulse
is cleared only when the terminal task polls again. `++terminalPause(true)++`
stops that poll and display flush, so the last red pixels can remain frozen
until the task resumes. The measurement does not include a continuing LED
redraw. This is a cosmetic paused-frame quirk, not evidence of a failed write
or read. No LED behavior change was requested or made.
