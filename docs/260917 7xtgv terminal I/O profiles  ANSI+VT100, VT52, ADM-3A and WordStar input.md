# 7xtgv terminal I/O profiles: ANSI/VT100, VT52, ADM-3A and WordStar input

**Date:** 260917
**Status:** design note / compatibility architecture
**Supersedes:** earlier `mode=` / `legacy=` proposal in this note

## 1. Purpose

7xtgv already uses an ANSI/VT100-style output parser and also has private 7xtgv CSI extensions. CP/M compatibility work now gives a good reason to make the terminal architecture more explicit:

- keep **ANSI/VT100 + 7xtgv CSI** as the native mode;
- optionally decode **VT52** and perhaps **ADM-3A** output for old CP/M applications;
- configure **keyboard/input encoding independently** from display/output decoding;
- allow a **WordStar input profile** for applications which expect the classic CP/M editor control keys;
- keep all protocol personalities isolated from the common terminal/screen engine.

The key new conclusion is:

> **Terminal output protocol and keyboard/input protocol are independent axes.**

This is not only a clean modern design. Borland Turbo Pascal `TINST` provides a historical example: its supplied **ANSI screen definition** uses ANSI output commands, while its cursor-key input entries use the compact **VT52-style `ESC A/B/C/D` sequences**.

---

## 2. Recommended architecture

```text
                         CP/M / host application
                           |              ^
                           | output bytes | input bytes
                           v              |
                  +----------------+  +----------------+
                  | OUTPUT DECODER |  | INPUT ENCODER  |
                  +----------------+  +----------------+
                    |      |      |      |    |     |
                  ANSI    VT52  ADM-3A  ANSI VT52 WordStar
                    |      |      |      |    |     |
                    +------+------+
                           |
                           v
                 COMMON TERMINAL OPERATIONS

                 PutCharacter()
                 CursorMove()
                 CursorSet()
                 ClearScreen()
                 ClearEOL()
                 ClearEOS()
                 Scroll()
                 SetAttribute()
                 Bell()
                 ...
                           |
                           v
                    7xtgv screen model
```

The invariant should be:

> **Output protocols decode bytes into terminal operations. Input profiles encode key events into application bytes.**

No legacy protocol should be implemented by generating synthetic ANSI sequences and feeding them back into the ANSI parser.

For example:

```text
VT52: ESC Y row col
      -> CursorSet(row, col)
```

not:

```text
VT52: ESC Y row col
      -> generate ESC [ row ; col H
      -> feed generated bytes into ANSI parser
```

This keeps protocol state independent and prevents accidental interaction with private 7xtgv CSI commands.

---

## 3. Native 7xtgv output mode

The normal 7xtgv terminal remains:

```text
ANSI / VT100-compatible output
        +
7xtgv private CSI extensions
```

The ANSI parser therefore owns:

```text
ESC ...
CSI ...
```

and CSI dispatch should preferably be centralized:

```text
CSI dispatcher
    |
    +-- standard ANSI / ECMA-48 / VT100-compatible commands
    +-- intentionally supported DEC/xterm commands
    +-- 7xtgv private CSI commands
```

Private 7xtgv CSI commands belong **only** to this output path. VT52 or ADM-3A decoders should never generate, reinterpret, or implicitly enable them.

---

## 4. Independent profile settings

The earlier idea of one `mode=` plus a `legacy=` switch is less expressive than separating output and input explicitly.

Recommended INI vocabulary:

```ini
[terminal]
output=ansi
input=ansi
extensions7x=yes
```

Suggested values:

```text
output = ansi | vt52 | adm3a
input  = ansi | vt52 | wordstar | literal
```

`keyboard=` could be accepted as an alias for `input=`, but `input=` is more symmetric with `output=` and makes clear that this controls the byte protocol sent **to the application**, not the physical keyboard hardware.

### Meaning of the input modes

```text
input=ansi
    special cursor/navigation keys emit ANSI/VT100-style sequences

input=vt52
    cursor keys emit ESC A / ESC B / ESC C / ESC D

input=wordstar
    special keys are translated to WordStar-compatible control commands

input=literal
    ordinary characters/control characters are passed as entered;
    no application-specific WordStar translation is imposed
```

Printable characters and explicit Ctrl-key combinations should normally pass through unchanged in every mode. The `input=` mode mainly determines how non-character keys such as arrows, Home, End, PgUp, PgDn, Insert and Delete are encoded.

## 5. Profiles as presets

Profiles can simply set the independent fields above.

Example native 7xtgv profile:

```ini
[profile 7xtgv]
output=ansi
input=ansi
extensions7x=yes
```

Strict generic ANSI profile:

```ini
[profile ansi]
output=ansi
input=ansi
extensions7x=no
```

Historical VT52 profile:

```ini
[profile vt52]
output=vt52
input=vt52
extensions7x=no
```

ADM-3A compatibility profile:

```ini
[profile adm3a]
output=adm3a
input=literal
extensions7x=no
```

A CP/M application profile may intentionally mix protocols:

```ini
[profile cpm-ansi-vt52keys]
output=ansi
input=vt52
extensions7x=no
```

This seemingly odd combination is historically legitimate and is directly motivated by the Turbo Pascal `TINST` ANSI definition discussed below.

Profiles should remain presets rather than hardwired terminal types. The explicit `output=`, `input=` and `extensions7x=` fields are the actual architecture.

## 6. Why output and input must be separate: Turbo Pascal TINST

The examined Turbo Pascal `TINST` ANSI definition makes this separation unusually clear.

### 6.1 ANSI screen/output definition

`TINST` displays the command bytes in **decimal**, not hexadecimal.

Examples:

```text
CURSOR LEAD-IN:
    <ESC> [
    decimal: 27 91
    hex:     1B 5B

between line and column:
    ;
    decimal: 59
    hex:     3B

after line and column:
    H
    decimal: 72
    hex:     48
```

Thus cursor addressing is the expected ANSI form:

```text
ESC [ row ; column H
```

Other supplied ANSI commands include:

```text
Clear screen       ESC [ 2 J     decimal 27 91 50 74
Home               ESC [ f       decimal 27 91 102
Delete line        ESC [ 1 M     decimal 27 91 49 77
Insert line        ESC [ 1 L     decimal 27 91 49 76
Erase to EOL       ESC [ K       decimal 27 91 75
Highlight on       ESC [ 1 m     decimal 27 91 49 109
Highlight off      ESC [ 0 m     decimal 27 91 48 109
```

So the **display side is plainly ANSI**.

### 6.2 The same TINST definition uses VT52-style cursor-key input

In the separate `CONTROL` section, the cursor movements are configured as:

```text
Character left     ESC D
Character right    ESC C
Line up            ESC A
Line down          ESC B
```

These are the compact VT52 cursor-key sequences.

Therefore this historical Turbo Pascal profile is effectively:

```ini
output=ansi
input=vt52
```

This should not be interpreted as saying that ANSI itself defines `ESC A/B/C/D` as cursor-key input. It demonstrates that CP/M software often treated **screen output capabilities** and **keyboard command sequences** as separate configuration problems.

That is exactly the model 7xtgv should preserve.

## 7. VT52 output support

VT52 is a particularly attractive legacy output protocol because the decoder is small and many commands map directly to existing terminal operations.

Core commands worth implementing first:

```text
ESC A       cursor up
ESC B       cursor down
ESC C       cursor right
ESC D       cursor left
ESC H       home
ESC J       erase to end of screen
ESC K       erase to end of line
ESC Y rc    direct cursor position, row/column encoded with +32
```

Additional genuine VT52 commands can be supported if needed:

```text
ESC I       reverse line feed
ESC F       enter special graphics character set
ESC G       return to ASCII character set
ESC =       enter alternate keypad mode
ESC >       exit alternate keypad mode
ESC Z       identify terminal
```

The implementation should distinguish **core compatibility required by CP/M applications** from optional VT52 completeness. We do not need to emulate every historical terminal behavior until a real program needs it.

### VT52 input mode

For special cursor keys:

```text
Up       -> ESC A
Down     -> ESC B
Right    -> ESC C
Left     -> ESC D
```

Other special keys can remain unmapped initially unless a real application requires a specific sequence.

## 8. WordStar input profile

The classic WordStar/Turbo-Pascal-era movement diamond is an **application keyboard convention**, not a terminal output protocol:

```text
        ^E
         ^
    ^S <- -> ^D
         v
        ^X
```

A selectable 7xtgv input profile can translate modern special keys approximately as follows:

```text
Up       -> ^E
Down     -> ^X
Left     -> ^S
Right    -> ^D
Home     -> ^Q ^S
End      -> ^Q ^D
PageUp   -> ^R
PageDown -> ^C
Insert   -> ^V
Delete   -> ^G
```

This translation belongs **only to the input encoder**. It must not affect output decoding.

The resulting profile can therefore be mixed freely with any screen protocol:

```ini
output=ansi
input=wordstar
```

or:

```ini
output=vt52
input=wordstar
```

The latter is a very plausible CP/M-era combination for software whose screen is configured for VT52 while its editor still expects WordStar control commands.

---

## 9. ADM-3A as an optional second legacy output protocol

ADM-3A/Kaypro-style terminal control also appears frequently enough in CP/M software to justify a small optional decoder.

The especially important direct cursor-position sequence is:

```text
ESC = row+32 column+32
```

A number of other ADM-3A operations use simple control characters.

ADM-3A support should remain optional and independent from VT52. The protocols overlap enough that recognizing the full ANSI + VT52 + ADM-3A languages simultaneously is unsafe.

For example:

```text
VT52:       ESC H   = HOME
ANSI/VT100: ESC H   = HTS (horizontal tab set)
```

Therefore 7xtgv should select one explicit `output=` personality rather than trying to auto-detect everything from one byte stream.

An eventual `output=auto` mode, if ever useful, should recognize only a deliberately audited set of non-conflicting sequences. It should not be the fundamental design.

## 10. Related historical case: CP/M FAND 1.0 / FANDINST

FAND is relevant here because the surviving CP/M version is itself a Turbo Pascal application, and `FANDINST` uses a terminal-capability model strongly reminiscent of Turbo Pascal `TINST`.

This should be treated as a **related compatibility case**, not as the architectural model for 7xtgv.

### 10.1 FANDINST is mainly an output-terminal capability table

Its fields correspond to familiar terminal concepts:

```text
terminal name
columns / rows
alternate video / highlighting
blink
reverse video
cursor-position prefix
row/column separator
cursor-position suffix
column-first flag
row/column offsets
binary vs ASCII cursor coordinates
clear screen
home
clear to end of line
operation delays
```

The `3H` and `5H` labels are FANDINST input-field formats: fixed numbers of bytes entered in hexadecimal. They are not CP/M terminal terminology.

The supplied machine definitions are mostly **computer + CP/M console-driver personalities**, not standard terminal brands. Examples include Robotron R1715 under SCP versus MIKROS, TNS variants, A5130/HUVOLE and Sharp MZ-821. The same physical machine can therefore have different FAND terminal records when its CP/M console driver exposes different control codes.

### 10.2 The local profiles are not ANSI/VT52/ADM-3A definitions

Examples reconstructed from the supplied definitions include:

```text
R1715/SCP:
    cursor prefix ESC
    binary row/column with +128 offsets
    clear screen 0C
    erase EOL 16

R1715/MIKROS:
    cursor prefix ESC
    binary row/column with +32 offsets
    clear screen 1C
    erase EOL 1E

Sharp MZ-821 profile:
    cursor prefix ESC
    binary row/column with +128 offsets
    clear screen 0C
    erase EOL 16
```

These are best understood as the control protocol exposed by the machine's CP/M console implementation, not necessarily the raw hardware protocol of its display.

### 10.3 FANDINST does not contain a general keyboard mapping table

The examined computer record describes display/output behavior but does not provide a Turbo-Pascal-style general `CONTROL` table for cursor keys and editor commands.

Therefore FAND's keyboard expectations must be determined separately from the screen profile. Its Turbo Pascal ancestry and surviving command messages make a WordStar-like input convention plausible, but the exact FAND 1.0 editor key map should still be verified from the executable/editor chain before being treated as final.

### 10.4 Why VT52 may be a useful FAND compatibility target

FAND's screen-description format naturally accommodates short VT52 sequences:

```text
cursor prefix      ESC Y
row offset         32
column offset      32
binary addressing  yes
clear screen       ESC H ESC J
erase EOL          ESC K
```

By contrast, FAND's attribute fields are only `3H`, while common ANSI SGR attributes such as:

```text
ESC [ 1 m
ESC [ 0 m
ESC [ 5 m
ESC [ 7 m
```

need four bytes. FAND 1.0 is monochrome in this context, so omitting unsupported highlighting/blink/reverse attributes is acceptable for an initial compatibility profile.

An experimental first profile for the surviving CP/M FAND could therefore be:

```ini
[profile fand-cpm]
output=vt52
input=wordstar
extensions7x=no
```

with the important caveat that `input=wordstar` remains provisional until the actual FAND editor key dispatch is fully verified.

### 10.5 Why testing this FAND matters

This surviving CP/M FAND is a particularly interesting historical target because it already contains the declarative database concepts later associated with PC-FAND: file/record definitions, edit screens, reports, merge/stream processing and procedure/script sections.

The later PC-FAND is a direct PC full-screen application and is no longer a terminal-emulation case. The older CP/M version therefore gives us a rare opportunity to exercise essentially the same database philosophy through a genuinely CP/M-era terminal interface.

## 11. Do not emulate every historical terminal

There is no present reason to add complete emulations of Hazeltine, Soroc, Televideo, ADM-31, Osborne and every other CP/M-era terminal family.

Large commercial applications often have their own installation/configuration utility. For such programs, configure the application for one of the terminal personalities 7xtgv intentionally supports.

Current recommended compatibility set:

```text
OUTPUT
    ANSI/VT100     native/default
    VT52           first legacy protocol
    ADM-3A         optional second legacy protocol

INPUT
    ANSI           normal modern/VT100-style keys
    VT52           ESC A/B/C/D cursor keys
    WordStar       CP/M editor/application convenience mapping
    literal        no application-specific mapping
```

Additional protocols should be added only when a worthwhile real application requires them and cannot reasonably be reconfigured.

## 12. Testing architecture with RunCPM

RunCPM remains a useful primary CP/M test environment for 7xtgv. On Linux it can run as a separate process connected through a pseudo-terminal (PTY).

```text
              Linux RunCPM
           Z80 + BDOS + CCP
                  |
                 PTY
                  |
            terminal.py
          transport/logger
                  |
            7xtgv parser
                  |
             SDL2 display
```

`terminal.py` can provide:

```text
RunCPM -> raw bytes -> output decoder -> screen model
                     |
                     +-- raw byte log
                     +-- decoded ESC/CSI/VT52 log
                     +-- assertions
                     +-- screenshots

keyboard/script -> input encoder -> PTY -> RunCPM
```

Useful test options may eventually include:

```text
--record session.raw
--replay session.raw
--output ansi
--output vt52
--output adm3a
--input ansi
--input vt52
--input wordstar
--expect "A>"
--screenshot result.png
```

Captured sessions can be replayed without RunCPM, giving deterministic parser regression tests.

This is particularly useful for Turbo Pascal, FAND, dBASE, WordStar and future Commander programs: when a screen is wrong, the raw capture tells us whether the application emitted an unexpected sequence or the 7xtgv decoder interpreted a valid sequence incorrectly.

## 13. Current recommendation

Freeze the conceptual architecture as:

```text
7xtgv OUTPUT decoders
    ANSI/VT100
        + optional private 7xtgv CSI extensions
    VT52
    ADM-3A              optional

7xtgv INPUT encoders
    ANSI
    VT52
    WordStar
    literal

profiles
    simply select output + input + extensions
```

The immediate implementation priority should be:

1. make output parsing and input encoding explicitly separate modules;
2. centralize standard ANSI versus private 7xtgv CSI dispatch;
3. add the small VT52 output decoder;
4. add `input=vt52` and `input=wordstar` mappings;
5. keep ADM-3A available as a small later compatibility decoder;
6. exercise the combinations under Linux RunCPM through the PTY/`terminal.py` harness;
7. use the old CP/M FAND as one historically valuable compatibility test, not as a reason to distort the general terminal architecture.

The architectural rule to keep is simple:

> **`output=` describes what the application sends to the screen. `input=` describes what 7xtgv sends back for key events. They are independent.**
