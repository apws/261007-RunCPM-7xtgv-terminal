== Editorial cautions added at conversion

* The upstream/CP/M 3 migration mentioned below is not proven complete.
  The recovered approximately 260126 baseline and cleaned integration
  seams are documented in the link:../guides/technical-reference-guide.adoc#runcpm-baseline-and-upstream-roadmap[Technical Reference Guide].
* `7XF` is a CCP built-in; the original `7XF.COM` wording below is historical.
* An 80-column terminal on a 52-column viewport needs *horizontal*
  panning; the original VERTICAL wording below is preserved, not endorsed.
* Shortcut assignments, persistence scope and palette details must be
  checked against the current link:../guides/reference-guide.adoc[Reference Guide]
  and active INI. Coarse brightness controls were not removed merely
  because these notes call them obsolete. Keyword lists and other
  future ideas are not claims of implemented features.

== b) CONFIGURATION FILE = 7XTGVTRM.INI

* in CP/M A0: is placed this SINGLE config file from which
even during BOOT is RunCPM and "7xtgv-terminal" fetching
some initial settings, including later decribed THEME / PALLETE
also default module ZOOM level (1x 2x 3x 4x for now) and ALSO
logical terminal SIZE for EACH that zoom level - so these values
MAY be dynamic, although regular usage is probably BEST on standard
CP/M logical size 80x24 which stays the same also in AD-HOC zoom-in/out
from keyboard - is fully possible to ZOOM IN/OUT and to PAN over terminal
size, to be ALWAYS somehow (well) useable on ANY ZOOM

* INI dile defines these module specific things like palette/zoom/terminal-size
* it also defines some GLOGAL values
* it also defines so called APP PROFILES / BANKS which may affect/switch controls
for apps, which are not configurable in CP/M or in case some special handling is
necessry - these BANKS/PROFILE (0-9, named) also have each its OWN terminal HISTORY
** this has more complex design based on CCP or in-app state, but it is EXPLICITLY
selectable easily from keyboard, rather that some "app auto-detection"
* for some more complex apps, the 7xtgv-terminal has also builtin special handlers
of normal/modern editing - for example for MBASIC (local compose) and BBCBASIC ...
these things are CONFIGURABLE per APP BANK/PROFILE, and it is somehow extensible
(whole motivaiton for this was ability to work with CP/M from terminal in some
unified way, in case some APPS are in CP/M behaving specially in terms of CONTROLS)
* 7xtgv-terminal output is for CP/M APPS mostly ANSI VT100 style, with optional VT52
and interpreting also "DEC graphics" and very primitive xterm256/SGR rendering mode

=== editing of INI file

* for editing we use almost solely TURBO PASCAL editor (it is TINST configured for ANSI ourput, using short 8bit Controls)
INI bank/profile section of TURBO APP itself contains definitions of specific controls in THIS TP mode ...
(TE is unable to edit LONG files...)

== c) CCP-INTERNAL default, possibly switched to our "7XF shell"

* after terminal boots it is in NORMAL CCP-INTERNAL mode
having prompt "A0>"

* usually from here is possible (but ALSO anythime out of CCP, in running app)
to SWITCH APP BANK / PROFILES by:

* `ALT + PgDn` — next bank/profile (in CCP, may be issues "on_select" command to change DU/directory by DU: U: or cd "dir")
* `ALT + PgUp` — previous bank/profile
* `ALT + SPACE` — temporary SHOW of current bank/profile at "cursor line" (BRIGHT)

* when incorrect profile is selected in-app, then the control of app may be impossible, so this is time to SWITCH IT ...
special behavior related to CCP prompt, which ALWAYS uses definition of profile #0 (CCP), even that selected APP profile is different

* 7xtgv-terminal has intentionally GLOBAL and PER BANK / PROFILE configurable two special operationc:

* clear screen:
* `ALT + BS` — CLS (in CCP) or per application like MBASIC / BBCBASIC by emitting ANSI controls to CLEAR SCREEN

* exit app:
* `ALT + ESC` — in CCP nothing, but in APP profiles it has configured specific way to EXIT (MBASIC = system, BBCBASIC = quit)
** for BBCBASIC we have also PATCHED "bbclower" which is BBCBASIC using "lowercase keywords" during INPUT ...
(only convenience for me here mostly, as I have configured typewriter-style CAPS/SHIFT behavior, and it almost
impossible to work with UPPERCASE required by BBCBASI ... btw, I HATE UPPERCASE keywords, anywhere ...
if something in code is UPPERCASE, I treat it as CONSTANT mostly)

* 7XF command allows to acitvate "7XF shell" - this is something which lightly resembles UNIX prompt
** originally this commmand was added to internal CCP to change prompt to HEX DU> and to omit U so D> only
** when introducing UNIX-like paths to DRIVES and USERAREAS, this very simple "mimicking" for CCP/shell usage
was added option to change prompt quite heavily to show:

* `/[drive]/[useareaname]>`

* (this is activated by just running 7XF.COM or 7XF DN)

* other simple options of 7XF are:
* `7XF DD` (DEC> decimal, default)
* `7XF DH` (HEX>)
* `7XF D` — (only DRIVE>)

* In "7XF shell" mode is shown prompt reading data from:

* `A0:VOL.7XF` (descriptions of drives/volumes)
* `A0:DRV.7XF` (current selected useararea/director on each drive)
* `XX:DIR.7XF` (description of directory/userarea + descriptions = long names = for possibly EACCH file in directory, not )

* this "catalog" is used by "UNIX-like" commands as "ls" "ll" and "cd" - only these three are now implemented:

* info about set of drives/volumes and on directories/useareas on drive (they may be NAMED by catalog)
* `ls /` / `ll /`
* `ls /a` / `ll /a`

* alternative DIR/LDIR, more similar to UNIX-like ls/ll
* `ls xx*`
* `ls *.ex*`

* change directory in UNIX-style:
* `cd /a/xterm256`
* `cd /a/mbasic`
* `cd /a/tp`
* `cd /a/cpm`
...

=== some our simple commands added on A0

* `VTINFO` — prints module and terminal info
* `REBOOT` — reboots the 7xtgv-terminal with CP/M (so reboots entire module, ALMOST like reset)
* `SYNC` — as we have some LAZY writes, this ensures them (reboot uses internally, the same REFLASH)
* `REFLASH` — when module supports this (not necessary BOOTSEL power-up), then this sends REQUEST to tooling to REFLASH module
* `VTCPU` — CPU speedtest, originally it was more precise than boot banner info, this was later corrected, mostly
* `VTDRV` — FS speedtest from CP/M view, depends on SPI CLK speed, on SDK/MCU, is affected by underlying FAT32 simple handling
(by default is READ ONLY, using VTDRV W does READ/WRITE test)
* `CARDMARK` — detailed internal (so native code implemented) detection of SD/MMC CARD CID/CSD details + READD benchmark
(default is short, with CSD argument it decodes entire card CSD specific items - verbose)
* `CONSOLE8` — RunCPM switch to 8bit terminal (necessary for our 8bit short control codes for TurboPascal TP301)
(but it IS enable by default by INI settings also)
* `VTPUT` — our toolingg uses these commands instead of XMODEM (problematic, sometimes)
* `VTGET` — our toolingg uses these commands instead of XMODEM (problematic, sometimes)

=== command histroy

* per app bank/profile list of history commands (now 100 per profile) is persisted using 7XTGVTRM.BUF file

* `CursorUp` — recalls previous commands entered as new when you start typing some chars, that history is FILTERED
(I was at one time trying to extend this to some possible in-app entering "keywords" by prssing PREFIX and CursorUp
this is still affecting som ehistory behavior in some cases, and not probably too well ...
so LATER I decided that such in-app keywords completion support MAY be there, but using SEPARATE list from BUF, which is history)

* `CursorDn` — recalls previous command from history, either in regular order or FILTERED,
till now, some recalled existing commands ARE NOT placed at the TOP if history FIFO, which may be returned there
originally this was behviang more predictably, but we complicated it with our test for "keywords"
as I sed, app bank/profile specific "keywords" lists (alse few separate selected??) is good thin but it needs separate FILES

* each NEW entered command is added at top TOP of FIFO, recalledd commands are not (possible to reach tem by PREFIX letter(s)

=== history command deletion

* is possible to DELETE any ""weird"" mistyped command from history, by just recalling it and pressing CTRL+SHIFT+BS ...
** this is important feature, it works good

* the "keywords-lists" WILL be added also, having EDITABLE lists of arbitrary tokens/symbols/keywoards, possible to add by ENTER
and possible to be also DELETED ... just for SIMPLE editting of OFTEN used words by in-app profile currently selected

== d) COLOR THEMES/PALETTES

* although I personally wanted "7xtgv" initially in "positive"
WHITE PAPER mode mostly, when some features were tested, I
introduced also some alternative palletes for NORMAL/IMPLICIT INK
and NORMAL/IMPLICIT PAPER - 7xtgv chip is expected to have 16 INK
colors and 4 PAPER colors, so there IS ANSI CLASH, as I dont expect
to support FULL ANSI PAPER colors, the same as INKS, and also MEANING
of attributes intpreted by ANSI will be slightly different, intentionally

* 7xtgv-terminal code now STILL DOES NOT USES full 7xtgv "chip-like" spec
* we have that spec ready, and it will be implemented (7xtgv-terminal
exists also as TESTING platform for "7xtgv" chip-like HDL-friendly design

* for now we have some basic commands, which are in CP/M FS named usually with VT* prefix
(althouth, this will be changed probably to XT* to not confuse; it is NOT fully ANSI VT)

* basic palletes can be selected by "VTPAL n":
this basically selects/modifies ONLY normal/implicit INK and PAPER, other colors stay ste same
* basic INK colors are 8 normal + 8 emphasized (on WHITE paper, emphasis means DARK, on DARK modes, emphasis means BRIDGH)
* basic PAPER colors are 4: normal/implicit paper/background + 3 RGB "markers"
(on WHITE paper some pale/pastell markers, on DARK paper/crt, some darker TINTS of RGB also ... just for EMPHASIS related to TEXT APPs)

* `VTPAL 0` ... WHITE PAPER (moderny GUI/positive style/theme)
* `VTPAL 1` ... CRT green phosphor (appropriate ink and ALSO background "tint" used)
* `VTPAL 2` ... CRT amber phosphor
* `VTPAL 3` ... CRT white phosphor (BW)
* `VTPAL 4` ... PLASMA red
* `VTPAL 5` ... VFD cyan

== e) BACKLIGHT / BRIGHTNESS CONTROL

* each module has tuned its own array of 32 backight values, usually calculated using gama2.2 for linear perception of brightness
that backlight level is lazily persisted for module into INI and restored abter boot

* backlight control:
* `ALT+CTRL+SHIFT + PgUp` — higher backlight intensity (top is usually 100% duty/level)
* `ALT+CTRL+SHIFT + PgDn` — lower backlight intensity (low is usually set as something VERY DIM but useable in darkness)
* `ALT+CTRL+SHIFT + 0` — backlight OFF (totalyl black screen)
* `CTRL+SHIFT + 1-9` — former 10 level control, obsolete, 9 levels + 0 = OFF

== f) TERMINAL SIZE / PANNING

* each module has of course some native HI-RES possibilities which define VISIBLE viewport

* crucial for 7xtgv is FIXED FONT/GLYPH RASTER as 6x10px, ALWAYS - THIS IS THE CORE OF 7XTGV;
* you can calculate visible viewport on say 320x240 as 320/6 (round down to even cols #) and 240/10 => 52 x 24
so on common 320x240 displays (often 3inch, 3.5inch, also 2inch or smaller) only 52x24 is visible
and VERTICAL panning is necessary to view ENTIRE terminal logical size
terminal logical size is defined in INI file for each boot zoom specificall, even defualt 80x24 is preffered
* this means that MINIMAL NATIVE resolution for full 80x24 (80x32) terminal size are displays of 480x320
(usually these displays are 3.5inch and higher, as 4inch, 5inch ... THIS is also some border for SPI-RGB565-FRAMWBUFFER controllerrs)
(LARGER displays over 5inch usually DONT HAVE local VRAM memory in display controller and are nNOT connected over SPI RGB565)
(For these cases is used mostly MIPI DSI today, DMA transfers from MCU connected memory, usually QSPI PSRAM on esp32 ...)

* zoom control:
* `CTRL+SHIFT + PgUp` — ZOOM OUT
* `CTRL+SHIFT + PgDn` — ZOOM IN

* there is also command VTZOOM
(but it is still TEMPORARY - only persistend zoom is read from INI during boot)

* panning control:
* `CTRL+SHIFT + Home` — top/left corner or previous viewport (left-right / top-bottom)
* `CTRL+SHIFT + End` — bottom/right corner OR next viewport (left-right / top-bottom)
** for simple cases of HORIZONTAL PAN ONLY usually simple, 2 viewports, max 3 ... but it depends on ZOOM/SIZE

* `CTRL+SHIFT + Down` — pan down
* `CTRL+SHIFT + Up` — pan up
* `CTRL+SHIFT + Right` — pan right
* `CTRL+SHIFT + Left` — pan left
