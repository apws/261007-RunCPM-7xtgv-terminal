== Bounded stall diagnosis, not a fix

`terminalHistorySaveDue()` starts an autosave after2000ms;
`terminalConfigSaveDue()` starts after1500ms. This matches Petr's observed
delay and the two triggering operations. Both storage-poll functions in
`7xtgv-vt100-runcpm.ino` call `terminalPause(true)` across their complete
filesystem transactions. While paused, `terminalLoop()` returns before
input/render/cursor work. History writes, flushes, verifies CRC, rotates files
and removes the backup. Config copies/updates the INI, flushes, verifies its
tail and rotates files. Both only resume the terminal at the end.

This is a strong explanation of the freeze mechanism, not a measured
explanation of why this board takes4 seconds. The two RP targets use the same
150MHz ARM profile, Arduino-Pico5.4.4, SdFat2.3.0 and12MHz SD setting, but
different SD pin assignments/connectors. VTDRV bulk throughput does not
measure these metadata/flush/replacement transactions. No SD fault, fixed
timeout, history size or failing save has been established.

Next proposed diagnostic: per-stage timings of pause acquisition, write,
flush/close, verification and replacement, before changing persistence or
verification. No instrumentation, save-policy change, automated device
commands or SD transfers were performed in this task.

== Further read-only save-path review

After acceptance of260925-1419's backlight, Petr requests another stall check.
Confirmed the active Arduino compile commands use pinned SdFat2.3.0, not the
other SdFat copy bundled in Arduino-Pico. Both RP targets use the same save
functions, library version,150MHz ARM setup and configured12MHz SPI1 SD bus.

Concrete INI inefficiency: `writeConfigSettings()` alternates small reads
from the source file with small writes to the replacement. SdFat's
`FatPartition` has one shared data `FsCache`; its separate FAT cache, when
enabled, is not a second file-data cache. `FatFile::read/write` use that
shared cache for partial sectors. `FsCache::prepare()` syncs dirty data and
loads another sector on a cache miss. Thus source/output alternation causes
repeated sector traffic, potentially even at CR/LF boundaries. A brightness
change rewrites the full INI rather than a single sector/key in place.

This establishes an avoidable access pattern, not a measured4s contribution.
History serialization is different: it writes every retained entry across all
ten banks, then rereads for CRC verification. It does not have the same
two-file alternating copy loop, so the INI finding alone cannot explain the
reported Enter freezes. No present device history size was fetched or assumed;
the old local mirror is not evidence of current device contents.

No module-specific4s timer was found in the reviewed save code. The built-in
save delays are responsive debounce periods, not intentional UI stalls.
Actual blocking occurs during `terminalPause(true)` and synchronous storage.
Failure re-arms history after2s or config after1.5s; asked Petr whether stalls
repeat while completely idle to distinguish retry loops from successful saves.

Next useful measurement remains per-stage durations and success/failure for
history and config, reported only after terminal resume so the diagnostic
cannot block a paused output consumer. No firmware, library or device changes
were made during this review. Do not remove CRC/transaction safety or blame
the new module based on bulk VTDRV results alone.
