= RunCPM CP/M user areas, PIP `+[Gn]+`, and internal CCP quirks
:source-highlighter: highlight.js

== Why this note exists

While assembling `+VTSTART.ASM+` and `+VTSTOP.ASM+`, several commands looked as if CP/M `+PIP.COM+` did not understand drive-qualified filenames. The real issue was more subtle: the RunCPM internal CCP displays *drive and CP/M user number together*, while classic CP/M transient programs still treat them as separate concepts.

The important result is:

[source,text]
----
A6>
----

means:

[source,text]
----
drive A, user area 6
----

It does *not* mean a CP/M drive named `+A6:+`.

This distinction is essential when using original CP/M programs such as `+PIP+`, `+ASM+`, `+LOAD+`, MBASIC, etc.

'''''

[id="1-runcpm-prompt-notation"]
== 1. RunCPM prompt notation

The internal CCP used in this project prints the current drive and user number as one compact prompt.

Examples:

[source,text]
----
A0>   = drive A, user 0
A4>   = drive A, user 4
A6>   = drive A, user 6
B2>   = drive B, user 2
----

The internal CCP also accepts standalone drive/user selection commands such as:

[source,text]
----
A:
6:
A6:
----

where applicable to its parser.

This is a *CCP convenience syntax*. It is not a general CP/M filename syntax understood by transient programs.

So, for example:

[source,text]
----
A6>PIP A4:ASM.COM=ASM.COM
----

is wrong if `+A4:+` was intended to mean "drive A, user 4".

Classic CP/M programs see `+A4:+` as a malformed drive specification, because CP/M drive names are only:

[source,text]
----
A:
B:
C:
...
P:
----

'''''

[id="2-why-pip-reported-invalid-format-a6"]
== 2. Why PIP reported `+INVALID FORMAT: A6:+`

Commands such as:

[source,text]
----
PIP A6:ASM.COM=ASM.COM
PIP A0:ASM.COM=ASM.COM
----

produced errors such as:

[source,text]
----
INVALID FORMAT: A6:
----

This does *not* indicate that the installed `+PIP.COM+` is too old or lacks normal CP/M drive-qualified file syntax.

The problem is simply that `+A6:+` and `+A0:+` are RunCPM CCP shorthand for a *drive {plus} user-area selection*, while PIP expects only a single-letter drive specifier before `+:+`.

Normal CP/M PIP drive syntax remains valid, for example:

[source,text]
----
PIP B:FILE.COM=A:FILE.COM
----

if drives A and B really exist.

'''''

[id="3-cpm-user-areas-are-separate-from-drives"]
== 3. CP/M user areas are separate from drives

CP/M 2.2 user areas are numbered independently of the selected drive.

Conceptually, RunCPM's prompt:

[source,text]
----
A6>
----

should be mentally read as:

[source,text]
----
A:[USER 6]>
----

A file in user 4 and a file of the same name in user 6 are separate directory entries even though both live on drive A.

The current project deliberately uses user areas to organize software, for example:

[source,text]
----
A0  core/shared commands
A4  assembler/tooling area
A6  VTSTART/VTSTOP sources and benchmark work
----

The exact contents can change, but the important point is that these are *user areas on drive A*, not independent CP/M drives.

'''''

[id="4-pip-gn-copy-a-file-from-another-user-area"]
== 4. PIP `+[Gn]+`: copy a file from another user area

CP/M 2.2 PIP provides the `+G+` option specifically for reading a source file from another user area.

Syntax:

[source,text]
----
PIP destination=source[Gn]
----

where `+n+` is the source user number.

For example, while currently in user 6:

[source,text]
----
A6>PIP ASM.COM=ASM.COM[G4]
----

means:

[source,text]
----
read ASM.COM from user 4
write ASM.COM into the current user area, user 6
----

This is the correct way to copy `+ASM.COM+` from A/user 4 into A/user 6.

Afterward:

[source,text]
----
A6>DIR ASM.COM
----

should show the copied file in user 6.

Another generic example:

[source,text]
----
A3>PIP TEST.TXT=TEST.TXT[G7]
----

copies `+TEST.TXT+` from user 7 into the currently selected user 3.

=== Important limitation

`+[Gn]+` selects the *source* user area. The destination is the currently selected user area.

So to copy from user 4 to user 6, first select user 6, then use `+[G4]+`:

[source,text]
----
A6:
PIP ASM.COM=ASM.COM[G4]
----

or, once the prompt already shows `+A6>+`:

[source,text]
----
PIP ASM.COM=ASM.COM[G4]
----

'''''

[id="5-runcpm-internal-ccp-command-search"]
== 5. RunCPM internal CCP command search

This project's internal CCP has a useful command-search extension.

For an external command such as:

[source,text]
----
LOAD VTSTART
----

it first tries the current drive/current user. If the command is not found and no explicit drive was supplied, it can fall back to shared command locations, notably *drive A, user 0*.

Therefore, if `+LOAD.COM+` exists in A/user 0 and the current prompt is:

[source,text]
----
A6>
----

then:

[source,text]
----
A6>LOAD VTSTART
----

can work even though `+LOAD.COM+` itself is not stored in user 6.

The CCP loads the command from its fallback location, restores the caller's normal drive/user environment, and then runs the transient program.

This makes A/user 0 behave somewhat like a shared command area.

'''''

[id="6-do-not-confuse-ccp-command-lookup-with-program-file-lookup"]
== 6. Do not confuse CCP command lookup with program file lookup

The A0 fallback belongs to the *RunCPM internal CCP*.

It does not mean that all CP/M programs automatically search A0 for their own input files.

For example:

[source,text]
----
A6>LOAD VTSTART
----

may find `+LOAD.COM+` in A0 because the CCP searches there.

But once `+LOAD.COM+` is running, `+VTSTART.HEX+` is opened according to normal CP/M rules from the program's current drive/user environment.

Likewise:

[source,text]
----
A6>ASM VTSTART
----

may find `+ASM.COM+` through CCP command lookup if such fallback applies, but the assembler's source-file handling is its own CP/M file access logic.

For predictable operation, keeping the assembler together with the source user area is convenient:

[source,text]
----
A6>PIP ASM.COM=ASM.COM[G4]
----

then:

[source,text]
----
A6>ASM VTSTART
A6>ASM VTSTOP
----

'''''

[id="7-recommended-vtstart--vtstop-build-sequence"]
== 7. Recommended VTSTART / VTSTOP build sequence

With the sources in user 6, and `+ASM.COM+` originally in user 4:

=== One-time assembler copy

[source,text]
----
A6>PIP ASM.COM=ASM.COM[G4]
----

Verify:

[source,text]
----
A6>DIR ASM.COM
----

=== Assemble

[source,text]
----
A6>ASM VTSTART
A6>ASM VTSTOP
----

The DRI-style assembler expects the source basename and appends `+.ASM+` itself. It produces `+.HEX+` output.

[id="load-into-com"]
=== Load into `+.COM+`

If `+LOAD.COM+` is available through the internal CCP's shared A0 command search:

[source,text]
----
A6>LOAD VTSTART
A6>LOAD VTSTOP
----

There is normally no need to write a pseudo-qualified form such as:

[source,text]
----
A0:LOAD VTSTART
----

because `+A0:+` is not a classic CP/M transient-program path syntax meaning "user 0".

'''''

[id="8-practical-rules-of-thumb"]
== 8. Practical rules of thumb

When the RunCPM prompt says:

[source,text]
----
A6>
----

remember:

[arabic]
. `+A+` is the CP/M drive.
. `+6+` is the CP/M user area.
. `+A6:+` is useful to the RunCPM CCP as a drive/user selection shorthand.
. `+A6:+` is *not* a valid classic CP/M filename drive prefix.
. Use PIP `+[Gn]+` to read a source file from another user area.
. The current user area is the normal destination for PIP copies.
. The internal CCP may find external commands in A/user 0 automatically.
. That CCP command fallback does not change the normal file-search behavior of the transient program after it starts.

The most useful example for this project is therefore:

[source,text]
----
A6>PIP ASM.COM=ASM.COM[G4]
----

not:

[source,text]
----
A6>PIP A6:ASM.COM=A4:ASM.COM
----

'''''

[id="9-relationship-to-the-previous-investigation"]
== 9. Relationship to the previous investigation

The earlier note:

[source,text]
----
docs/260912-21 VTSTART VTSTOP CP-M assembly and PIP quirks.adoc
----

recorded the symptoms correctly, but its initial interpretation that the PIP binary had a restricted/old drive parser was incorrect.

The corrected explanation is:

* standard CP/M PIP supports normal drive-qualified filenames;
* the failing `+A6:+` / `+A4:+` forms were mixing RunCPM's CCP drive/user notation with classic CP/M drive syntax;
* cross-user copying on CP/M 2.2 is performed with PIP's `+[Gn]+` option;
* the RunCPM internal CCP's A0 fallback is a separate command-loading extension.

This distinction should be kept in mind for future work with original CP/M utilities inside the RunCPM environment.
