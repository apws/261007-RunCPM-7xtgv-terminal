261005-05 hi Lyra pls what is difference between RunCPM (for rp2350) and "pico z80" solution of cp/m emulation used in GEEK2350 ??

== Lyra

Hi Petr — the essential difference is **where the CP/M abstraction boundary is**.

**RunCPM** is basically a *CP/M-oriented virtual machine*. It contains a Z80 emulator, but it does **not primarily try to emulate a particular historical Z80 computer with real disk controllers, ROM, I/O ports, etc.** Instead, CP/M programs run on the emulated Z80 and RunCPM provides its own BIOS/BDOS-facing environment, mapping CP/M drives rather conveniently onto host directories/filesystems. The Pico/RP2350 ports simply bring that architecture onto the microcontroller.

The **Pico-Z80 style solution** is lower-level. It treats the RP2350 much more as a **Z80 machine emulator**: emulate the processor, give it 64 KB or banked memory, emulate I/O devices/storage, and then boot a more conventional CP/M 2.2 system *inside that machine*. In other words:

[cols="1,1,1",options="header"]
|===
|
| RunCPM
| Pico-Z80 / GEEK2350-style CP/M

| Main object being emulated
| CP/M execution environment
| Z80 computer

| Z80 instructions
| emulated
| emulated

| CP/M BIOS
| specially adapted to RunCPM
| ordinary/emulated-machine BIOS

| Disk model
| often directories/files on SD mapped directly to A:…P:
| usually sector/block/disk-image oriented

| I/O ports
| only what RunCPM needs/extensions
| actual emulated Z80 I/O model

| Hardware fidelity
| deliberately low
| much higher

| CP/M system image
| partially integrated/virtualized
| boots as guest software

| Best for
| running CP/M apps conveniently
| pretending the RP2350 actually is a Z80 computer
|===

That distinction is particularly relevant to what we've been doing with your **7XTGV RunCPM**.

RunCPM effectively says:

[source,text]
----
CP/M program
     ↓
emulated Z80
     ↓
RunCPM BDOS/BIOS glue
     ↓
FatFs / SD / terminal / RP2350 hardware
----

Whereas Pico-Z80 says approximately:

[source,text]
----
CP/M program
     ↓
real CP/M BDOS
     ↓
real CP/M BIOS for the virtual machine
     ↓
emulated Z80 + RAM + I/O ports + disks
     ↓
RP2350
----

So with Pico-Z80, something like:

[source,asm]
----
IN   A,(10h)
OUT  (20h),A
----

can represent a genuine emulated hardware interface. With RunCPM, arbitrary historical hardware ports normally **don't exist unless we deliberately implement an extension for them**.

And this explains one of the things you've encountered with **FAND/MZ-821**. RunCPM is wonderful for application-level CP/M compatibility, but as soon as software expects peculiar BIOS calls, exact disk geometry, special console behaviour, or machine-specific hardware, we start adding compatibility machinery. A full machine emulator naturally has a place for those things.

There is another subtle distinction: a modern Z80 emulator library can be **extremely faithful at CPU level**, including undocumented flags/instructions, while RunCPM doesn't necessarily need cycle-accurate hardware behaviour because CP/M application software generally doesn't care.

One thing I could **not verify publicly** is the exact source/architecture called **“GEEK2350 Pico Z80”** — searches find the Waveshare RP2350-GEEK hardware but not documentation tying that precise product/name to a particular Pico-Z80 CP/M implementation. So I don't want to invent details about *its exact* FDC, disk format, or Z80 core.

But architecturally, if the GEEK2350 package you're looking at says that it runs **Pico Z80 + CP/M 2.2**, the important distinction is almost certainly:

> **RunCPM emulates the environment needed to run CP/M software. Pico-Z80 emulates a Z80 machine capable of running CP/M.**

For our purposes, that also means **RunCPM is much easier to hack into the “7XTGV operating environment” we're building**, while Pico-Z80 would be the more interesting basis if we wanted an RP2350 to become a **generic virtual Z80 hardware platform**, with our own BIOS, banked memory, MMU-ish tricks, ports, DMA, etc.

And *that latter architecture is actually rather close philosophically to your VMEX/ASLIX thinking*. 🙂

Yes — I found it now, and it is much more concrete than I implied before. The GEEK2350 project is **open source**, and it is not some vague “Pico Z80” black box. It is Udo Munk’s **z80pack** port for the Waveshare RP2040-GEEK / RP2350-GEEK boards.

What it emulates is basically a **mid-1970s S-100 / Altair-class 8080/Z80 system**, not a specific later commercial CP/M computer.

The emulated machine has:

* switchable **Intel 8080 or Zilog Z80 CPU**
* on RP2350, **352 KB RAM total** arranged as **7 × 48 KB banked segments + 16 KB common memory**
* a tiny **256-byte boot ROM** at the top of memory
* **three MITS Altair 88SIO Rev.1 serial interfaces**
* another simple output-only printer port
* a **DMA floppy-disk controller**
* **four 8-inch, single-density IBM 3740-compatible floppy drives**
* a **Cromemco Dazzler** graphics adapter, displayed on the little LCD
* virtual disk images and configuration stored on microSD.

So this is actually a lovely little thing. Architecturally, think:

[source,text]
----
RP2350-GEEK
   |
   +-- Z80pack CPU emulator
   |      +-- Intel 8080
   |      `-- Zilog Z80
   |
   +-- 352 KB banked RAM
   +-- 256 B boot ROM
   +-- Altair 88SIO serial boards
   +-- DMA floppy controller
   +-- 4 x IBM 3740 8" floppy
   `-- Cromemco Dazzler
          |
          `--> 1.47" LCD
----

And **CP/M is then simply software booted from those emulated floppy disks**. It can run CP/M 2.2, banked CP/M 3, UCSD p-System IV, FIG Forth, and — on RP2350 — even banked **MP/M II with two terminals**.

That last part is especially interesting: the 352 KB arrangement isn't accidental. The RP2350 build exposes enough banked memory for genuine CP/M 3 / MP/M-style memory management.

=== And yes, source is available

The board-specific project is here:

`RP2xxx-GEEK-80`

and it uses Udo Munk's existing **z80pack** emulator.

The build instructions explicitly say to clone z80pack, select its `dev` branch, then build the GEEK frontend around it. There are also ready-made UF2 binaries for both RP2040 and RP2350, including ARM and RP2350 RISC-V builds.

So yes: **fully inspectable/hackable**.

One terminology trap: this is **not the same project as “picoZ80”** by Philip Smart. That is another current RP2350 project entirely — a rather wild **drop-in DIP-40 Z80 replacement**, using RP2350 PIO to reproduce actual Z80 bus cycles and plug into original Z80 hardware. That project is also open-source GPLv3 firmware.

For GEEK2350, the correct lineage is:

[source,text]
----
Udo Munk z80pack
        |
        +-- complete virtual 8080/Z80 computer
        |
        `-- RP2xxx-GEEK-80 frontend
                 |
                 `-- Waveshare RP2350-GEEK
----

rather than the Philip Smart picoZ80.

And yes, your observation about the **Dazzler** is exactly right: the little display isn't merely being used as a character terminal. It can display the actual **Cromemco Dazzler framebuffer**, while the machine's serial console remains via USB/UART. The LCD can also switch to register display, IMSAI-style front panel, disk status, I/O-port activity, memory dump, etc.

So compared with our RunCPM work, this is considerably more “real computer”:

> **RunCPM:** CP/M application environment with virtualized BDOS/BIOS/files.  
> **GEEK-80:** an emulated 1976-ish S-100 computer on which unmodified-ish CP/M boots from an emulated 8-inch floppy.

For **your experiments**, the GEEK-80 source may actually be very interesting to inspect, because its **banked 352 KB + common 16 KB + CP/M 3/MP/M implementation** is almost the opposite end of the design spectrum from the increasingly enhanced RunCPM environment we've been building.

Yes — **I think your instinct is right: for a Linux-native 7XTGV-terminal, porting/compiling your existing RunCPM stack with an SDL Arduino_GFX shim is probably the much straighter path** than grafting 7XTGV onto z80pack.

z80pack *can* expose host-backed services through emulated I/O ports, so in principle you could add your own “7XTGV device” exactly as an emulated peripheral. Its architecture already does this for things like serial ports, MMU/bank switching, disks, etc. But then your 7XTGV features become **guest-visible hardware/BIOS extensions**, rather than direct RunCPM host hooks.

For date/time specifically, z80pack absolutely has the concept of host/RTC-backed time. What I have *not* yet found is a canonical “read host monotonic milliseconds through port XX” service comparable to the kind of custom timing hook you can simply add in RunCPM. That would be trivial to add to z80pack, though: reserve one or several ports and have the host side return seconds, ticks, µs, whatever representation you want.

But the more important issue is your **CCP**.

Your current thing is roughly:

[source,text]
----
7XTGV extended CCP
       |
       +---- normal CP/M commands
       |
       +---- RunCPM-specific internal commands
       |
       +---- custom IN/OUT hooks
       |
       +---- terminal/history/editor/profile machinery
       |
       `---- Arduino_GFX
                |
                `---- physical LCD
----

RunCPM itself explicitly supports BIOS/BDOS handoff through its host side. So your architecture is already deliberately **half CP/M, half host application**.

With Linux + SDL, we can instead make:

[source,text]
----
                 SAME 7XTGV SOURCES
                         |
                  +------+------+
                  |             |
               RP2350         Linux
                  |             |
             Arduino_GFX   Arduino_GFX shim
                  |             |
                 TFT           SDL2
----

while leaving:

[source,text]
----
extended CCP
RunCPM
custom commands
history
profiles
host hooks
filesystem abstraction
----

almost untouched.

That is a very attractive property.

=== z80pack would mean moving the seam

To use your existing terminal with z80pack cleanly, I'd probably design an emulated **7XTGV peripheral**:

[source,text]
----
        CP/M / your CCP
              |
          IN / OUT
              |
       virtual 7XTGV ports
              |
    +---------+----------+
    |         |          |
 keyboard   display     timer
    |         |          |
    +---------+----------+
              |
          Linux/SDL
----

Perfectly feasible.

But then several things which are currently “free” because RunCPM itself owns CP/M become explicit interfaces:

* screen operations → virtual device protocol
* keyboard/events → virtual device protocol
* host timing → virtual device registers
* possibly files/host directory access → another virtual device or BIOS extension
* internal CCP commands which directly call RunCPM host functionality → need refactoring
* anything that assumes RunCPM's peculiar BDOS/BIOS implementation → has to be replaced or emulated
* your extended CCP would need to become a **real guest CCP/COM-ish CP/M component**, rather than code partly living in RunCPM's host program.

That last one is the killer. It doesn't mean impossible — actually it could be intellectually very nice — but you'd be converting 7XTGV from a **RunCPM-derived system** into an **actual CP/M machine/software distribution**.

Meanwhile z80pack itself is deliberately much more faithful. Its `cpmsim` literally boots a BIOS and disk images, and reports simulated T-states and effective CPU frequency. That's excellent if the goal is “7XTGV hardware exists as a Z80 machine.”

It is unnecessary friction if the immediate goal is:

> **run precisely our current 7XTGV-terminal on CachyOS in a normal resizable SDL window.**

So I'd split these as two different experiments:

=== 7XTGV/Linux — do this first

[source,text]
----
RunCPM
 + current extended CCP
 + all current hooks
 + Arduino compatibility layer
 + Arduino_GFX -> SDL2 backend
----

This should preserve an enormous percentage of your code. And since you already found that Arduino_GFX SDL-ish shim/library path, this isn't even a speculative architecture anymore.

=== 7XTGV/z80pack — interesting later

Treat it as another target:

[source,text]
----
7XTGV-VIRTUAL-HARDWARE
          |
       z80pack
          |
      real CP/M
----

Then we'd deliberately define perhaps:

[source,text]
----
E0-EF   7XTGV display/control
F0-F3   host timer
F4      keyboard status
F5      keyboard data
...
----

and make the terminal accessible to *any* CP/M program, not merely your CCP. That would actually be a quite cool end state — but it's a different project.

One additional advantage of trying native RunCPM/Linux now: **RunCPM itself already has a normal host executable architecture.** z80pack supports Linux/X11/SDL2 broadly, but that SDL support belongs to z80pack's machine/front-panel/display ecosystem, not magically to Arduino_GFX or your terminal rendering model. So z80pack having SDL does **not** save us the 7XTGV display-porting job.

Therefore my rough difficulty estimate is:

[cols="2,1",options="header"]
|===
| Target
| Relative effort

| **RunCPM + existing 7XTGV + SDL Arduino_GFX shim**
| **1×**

| RunCPM + manually rewritten SDL renderer
| ~1.5×

| z80pack + 7XTGV virtual peripheral + adapted CCP
| ~3–5×

| z80pack + fully “real” 7XTGV CP/M machine/BIOS
| ~5×+
|===

Not because z80pack is difficult — rather because **you'd intentionally throw away several convenient seams that we've already exploited in RunCPM**.

And there's a nice strategic result: if the SDL/RunCPM version works, it gives us a **desktop reference implementation of 7XTGV**. Later, if we want the z80pack experiment, that reference tells us exactly what the emulated 7XTGV peripheral has to reproduce.

So yes: **I would definitely try the Linux RunCPM + Arduino_GFX→SDL route first.** The z80pack route is the more “proper computer emulation” experiment, but not the shortest path to getting *your present terminal* running natively on Linux.

So conceptually:

[source,text]
----
z80pack cpmsim

CP/M CON:
   ↓
emulated SIO / console interface
   ↓
host terminal / tty
   ↓
xterm / Konsole / Kitty / etc.
----

while SDL is more like:

[source,text]
----
emulated machine graphics
       ↓
front panel / Dazzler / visual peripheral
       ↓
SDL window
----

That distinction matters a lot for **7XTGV**, because your terminal is not merely “some ANSI terminal around CP/M.” Your display/editor/history/UI is itself the interesting thing.

So enabling:

[source,make]
----
WANT_SDL=YES
----

would **not suddenly give cpmsim a graphical 80×25 SDL terminal** that you could easily replace with your 7XTGV renderer.

You’d still need to build one of two bridges:

[source,text]
----
CP/M console chars
      ↓
7XTGV terminal engine
      ↓
Arduino_GFX/SDL
----

or make 7XTGV an emulated hardware device.

That reinforces the attraction of the other route: with your current RunCPM tree, the **7XTGV renderer already sits in the right place**. Replace only the bottom graphics/input backend:

[source,text]
----
RP2350:
7XTGV → Arduino_GFX → ST7796/etc.

Linux:
7XTGV → Arduino_GFX-compatible shim → SDL

and RunCPM/CCP above it hardly needs to know.

One qualification: z80pack’s graphical emulations absolutely **can use SDL for a guest display device** — the Dazzler is the obvious example — so technically you could implement an SDL-backed terminal peripheral there too. It’s just **not what `WANT_SDL` already provides for the CP/M console**.

So my earlier phrase “machine/front-panel/display ecosystem” was intentional, yes. The console and SDL graphics paths are different beasts.

=== Where RunCPM really enters

The things that *are* RunCPM-specific are likely commands such as your added:

[source,text]
----
ls
ll
cd
...
----

depending on how we implemented them.

If an internal CCP command does:

[source,cpp]
----
if (!strcmp(cmd, "cd"))
{
    chdir(...);       // host filesystem
}
----

or invokes one of your custom RunCPM I/O hooks, then that piece is host/RunCPM-specific.

But that's very different from saying the **line editor** is RunCPM-specific.

Likewise:

[source,text]
----
Ctrl-Up
Alt-something
history recall
delete history entry
profile hotkey
editor movement
----

are just terminal events.

They can survive unchanged.

=== z80pack might therefore need surprisingly little

Potentially:

[source,text]
----
                7XTGV terminal
                /            \
         character out     keyboard in
              ↓                 ↑
          z80pack SIO / console device
----

Instead of letting z80pack's serial device send output to Unix `stdout`, we'd make its console callback feed:

[source,cpp]
----
Terminal.PutChar(c);
----

And instead of getting input from Unix `stdin`:

[source,cpp]
----
c = Terminal.GetChar();
----

Then the CP/M guest sees an ordinary serial terminal.

That alone could give us:

* 7XTGV renderer
* history
* editor
* profiles
* keyboard mappings
* terminal escape decoding
* MZ-821/FAND terminal profile
* all your display machinery

with **no CP/M awareness at all in that layer**.

That is actually rather elegant.

=== The CCP is the separate question

Your current internal CCP is more complicated because RunCPM owns it.

Some commands are probably ordinary enough to port into a genuine CP/M CCP; some are really host extensions.

So if we connected 7XTGV to z80pack tomorrow, initially we could simply run z80pack's normal CP/M CCP:

[source,text]
----
CP/M guest CCP
      ↓
   console
      ↓
7XTGV editor/display
----

The 7XTGV **history/editor would still work**, because it can intercept and edit keyboard input before giving characters to CP/M.

There's one subtlety here.

If 7XTGV performs line editing *outside* CP/M and only sends the completed line after Enter, then CP/M sees:

[source,text]
----
DIR<CR>
----

all at once.

That works beautifully for CCP commands.

But interactive CP/M applications such as editors, FAND, games, etc. need **individual keystrokes immediately**. Therefore I expect you already effectively have two behaviours:

[source,text]
----
line-edit/history mode
        versus
raw/application mode
----

or some equivalent distinction.

Again, neither requires RunCPM specifically.

=== So I would revise my earlier estimate

Instead of saying:

> z80pack + 7XTGV = 3–5× harder

I'd now distinguish two goals.

**Just use 7XTGV as z80pack's terminal:**

Probably quite modest work:

[source,text]
----
z80pack console output → 7XTGV PutChar()
7XTGV keyboard → z80pack console input
SDL/Arduino_GFX underneath
----

Maybe **~1.5× the Linux RunCPM port**, not 3–5×.

**Reproduce our whole modified RunCPM environment including its internal CCP and host commands:**

That's where the larger effort appears.

[source,text]
----
terminal/history/editor/profile    easy to transplant
terminal protocol decoders         easy
SDL renderer                       common work
keyboard handling                  easy/moderate

extended RunCPM CCP                needs adaptation
host filesystem commands           needs adaptation
RunCPM-specific I/O hooks          needs replacement
special BDOS/BIOS assumptions      investigate individually
----

And interestingly, z80pack could give us a very clean experiment:

[source,text]
----
              7XTGV
                │
       ┌────────┴────────┐
       │                 │
    RunCPM            z80pack
       │                 │
 virtual CP/M       "real" CP/M
----

**same terminal frontend, two CP/M backends.**

That would actually tell us exactly which parts of 7XTGV have accidentally become RunCPM-dependent.

Yes — **that is exactly the right abstraction to aim for**.

The cleanest design is not “bind 7XTGV to RunCPM” or even “bind it to z80pack.” It is:

> **make 7XTGV a generic terminal frontend with a tiny character-I/O seam.**

For classic CP/M, that seam is almost embarrassingly small because the BIOS already defines the basic console contract:

* `CONST` — is a character available?
* `CONIN` — read one character
* `CONOUT` — write one character
* optionally `LIST` etc.

So conceptually 7XTGV could expose something like:

[source,cpp]
----
bool ConsoleInputReady();
uint8_t ConsoleInput();
void ConsoleOutput(uint8_t c);

uint32_t Millis();      // host convenience, not CP/M-required
----

and everything above that remains yours:

[source,text]
----
keyboard events
history
filtered recall
line editor
profiles
terminal parser
ANSI / SGR / xterm-256 handling
screen model
renderer
----

Then the backend changes.

RomWBW is especially promising because it already has its own **hardware abstraction BIOS layer (HBIOS)** underneath the operating systems.

So in a RomWBW build you could conceptually hook 7XTGV either at:

[source,text]
----
CP/M BIOS CONIN/CONOUT
----

or even lower:

[source,text]
----
RomWBW HBIOS character-device layer
----

The latter is probably nicer if you ever wanted the same terminal to serve not only CP/M but also other RomWBW-hosted environments.

And yes, I'd call your `SGR256` feature something like **“xterm-256color / ANSI SGR 256-color support”**. More precisely, the thing being parsed is ANSI/ECMA-48-style SGR with the widely used xterm extension:

[source,text]
----
ESC [ 38 ; 5 ; n m    foreground
ESC [ 48 ; 5 ; n m    background
----

So internally I'd probably name it something boring like:

[source,cpp]
----
AnsiSgr256
----

or:

[source,cpp]
----
Xterm256Color
----

rather than tying it to RunCPM.

The interesting architectural point is that the terminal should know **nothing** about CP/M commands. It should only see:

[source,text]
----
bytes out
bytes in
key events
time/ticks
----

and perhaps a few optional capabilities.

Something like:

[source,cpp]
----
struct TerminalHost
{
    bool (*InputReady)();
    uint8_t (*ReadByte)();
    void (*WriteByte)(uint8_t c);

    uint32_t (*Millis)();

    // optional
    void (*Bell)();
    void (*SetClipboard)(...);
};
----

Then your existing history/editor/profile machinery lives entirely above this.

There is only one important distinction to preserve: **line-edit mode versus raw terminal mode**.

At a CP/M prompt, 7XTGV may want to intercept keys and provide its fancy history/editor.

But when running FAND, WordStar, games, editors, etc. physical keys should become immediate input bytes.

BDOS console functions

CCP or application

[source,text]

[source,text]

=== Why do BASIC handlers exist then?

That's the revealing part.

The distinction isn't really:

> CCP vs application

but rather:

> **line-oriented interactive program vs raw/key-oriented program.**

The CCP is very easy because it waits for a command line.

MBASIC and BBC BASIC also have interactive prompts and you quite reasonably want history there too.

But their console behaviour is not necessarily identical to CCP/BDOS buffered-input behaviour. They may use different BDOS calls, read characters themselves, implement their own editing, react differently to control characters, etc.

Hence your custom handlers are probably telling 7XTGV something like:

> “We're at an MBASIC command prompt, so treat this as an editable/history-aware line.”

rather than adding history *inside MBASIC*.

Conceptually:

[source,text]
----
                  7XTGV
                    │
           ┌────────┴────────┐
           │                 │
       LINE MODE          RAW MODE
           │                 │
 history/editor       immediate keys
           │                 │
       CCP prompt         WordStar
       MBASIC prompt      games
       BBC BASIC          FAND editor
       etc.               cursor apps
----

Why can't we simply use line mode always? Because WordStar expects cursor keys immediately.

So we need some concept of:

[source,text]
----
History/Edit mode
----

versus:

[source,text]
----
Raw/Application mode
----

but **that state can still belong almost entirely to the terminal**, not CP/M.

The CP/M side can remain almost ignorant.

One subtle issue is echo: if 7XTGV visually displays the line while editing locally and then feeds the whole line into BDOS at Enter, CP/M may echo it again. So somewhere the implementation must deal with that. That is probably the exact place worth inspecting in source.

[source,text]

                      ↓
             CP/M console interface
                      ↓
           BIOS / BDOS / application
----

And yes — **I now think “history belongs to the terminal” is the right mental model**, with only a small amount of cooperation needed to know when line mode is appropriate and perhaps to handle echo cleanly.

The key diagram on page 24 is really the whole story:

[source,text]
----
                    RomWBW HBIOS

                CIO character stream
                       │
          ┌────────────┴────────────┐
          │                         │
       UART/ASCI                  CRT pseudo-device
                                    │
                             terminal emulator
                              TTY / ANSI
                                    │
                                  VDA API
                                    │
                      ┌─────────────┼─────────────┐
                     VDU           TMS           Xosera ...
                      │
                 physical display
----

RomWBW explicitly says that ordinary OS code normally uses **CIO** byte streams. If the target is the special `CRT` character device, those bytes are routed through the built-in terminal emulator; the emulator interprets TTY/ANSI sequences and then calls the device-independent VDA operations.

That distinction is crucial for thinking about 7XTGV.

=== 1. VDA is not really a “terminal”

VDA is much more like a **generic character-video chip API**.

Its interface is already surprisingly close to what you could call a hypothetical **7XTGV chip**:

[source,text]
----
initialize display
query rows/columns
reset
set cursor shape
set cursor position
set attributes
set foreground/background colour
write character
fill region
copy characters
scroll screen

keyboard status
keyboard flush
keyboard read
read character+attribute from screen
----

So yes: a completely reasonable addition would conceptually be

[source,text]
----
VDADEV_7XTGV
    |
    +-- RP2350/ESP32 MCU
    +-- TFT
    +-- keyboard
----

with a tiny RomWBW Z80-side driver talking to it over I/O ports or a memory-mapped/banked interface.

The MCU could then implement the VDA operations and RomWBW would consider it simply another local video adapter.

That is **7XTGV-as-chip**.

=== 2. RomWBW's ANSI emulator sits ABOVE those chip drivers

The VDU/TMS/Xosera driver does **not** parse ANSI itself.

RomWBW does:

[source,text]
----
CP/M writes:

ESC [ 31 ; 1 m Hello

             ↓

        RomWBW ANSI emulator

             ↓

VDASCO red+bright
VDAWRC H
VDAWRC e
...
----

Chapter 9 explicitly says the emulator implements “TTY, ANSI, etc. escape sequences”, and then uses VDA for cursor positioning, scrolling and so forth; the emulation code therefore does not know which physical video adapter is underneath it.

The current source confirms this even more strongly. `term.asm` says that a **VDA driver attaches itself to the terminal layer**, and the terminal layer selects either the TTY or ANSI emulator. That resulting object is then registered as a **CIO terminal device**.

So:

[source,text]
----
physical VDA
     ↑
 ansi.asm
     ↑
 term.asm
     ↑
 CIODEV_TERM
     ↑
 CRT
----

This is quite elegant.

=== 3. Colours

The VDA itself has a full **4-bit RGBI foreground + 4-bit RGBI background** byte.

So it genuinely represents **16 foreground × 16 background = 256 combinations**.

But RomWBW's ANSI parser does not expose all of that through ordinary SGR.

It recognizes:

[source,text]
----
SGR 0       reset
SGR 1       bold/intensity
SGR 4       underline
SGR 5       blink
SGR 7       reverse

SGR 30..37  foreground
SGR 40..47  background
----

It does not currently parse bright foreground/background ranges or xterm-256/truecolor.

And this answers the brightness question precisely.

`SGR 1` is not stored as an attribute.

RomWBW maps it to foreground RGBI intensity.

Meanwhile the VDA attribute byte is only:

[source,text]
----
bit 2   reverse
bit 1   underline
bit 0   blink
----

So there is **no separate bold/brightness attribute in VDA**.

It is colour intensity.

The VDA can absolutely represent bright backgrounds because background has its own intensity bit, but the stock ANSI parser doesn't provide SGR 100–107.

Your current restriction of **4 background colours** would simply be a reduced-capability VDA implementation. Unsupported colours/attributes may simply be ignored.

=== 4. Keyboard handling is richer than ordinary CP/M CONIN

VDA keyboard read returns:

[source,text]
----
Scancode
Keystate
Keycode
----

not merely ASCII.

Keystate includes modifiers like Shift, Control, Alt, Windows/Super, lock states, etc.

This means RomWBW already has an interface capable of representing precisely things such as:

[source,text]
----
Alt + Up
Ctrl + Left
Shift + F5
----

at the VDA boundary.

That is extremely suitable for 7XTGV.

But the stock `ansi.asm` then converts special keys into VT-style escape sequences, losing some of the richer structure.

=== 5. Therefore there are really TWO sensible 7XTGV integrations

==== A. `7XTGV-VDA` — the “chip”

[source,text]
----
CP/M
 ↓
CIO CRT
 ↓
RomWBW ANSI emulator
 ↓
RomWBW VDA
 ↓
7XTGV VDA driver
 ↓
MCU + TFT + keyboard
----

Here 7XTGV is equivalent to a VDU/TMS/Xosera-like device.

==== B. `7XTGV smart terminal`

[source,text]
----
CP/M
 ↓
CIO byte stream
 ↓
7XTGV terminal
      ├─ ANSI/xterm parser
      ├─ screen model
      ├─ history
      ├─ line editor
      ├─ profiles
      ├─ filtered recall
      └─ keyboard policy
 ↓
TFT
----

Here we deliberately **do not want RomWBW ANSI emulation in between**.

RomWBW should think 7XTGV is effectively some kind of external terminal.

Then an application emits ANSI bytes and **our existing 7XTGV parser receives them intact**.

For **our existing project**, this is probably the more interesting architecture.

=== 6. Could the smart machinery live behind VDA anyway?

Yes, but then the original byte stream has already been translated into VDA operations.

That is fine for rendering but makes the 7XTGV terminal parser redundant.

So I’d call this device a **7XTGV VDA adapter** rather than 7XTGV terminal.

=== 7. History/profile/editor changes the choice

RomWBW's ANSI layer is basically a terminal protocol translator.

Your 7XTGV is:

[source,text]
----
terminal protocol translator
+
interactive keyboard policy
+
history
+
line editor
+
application profiles
+
filtered keyword/snippet system
----

That second category has no obvious equivalent in RomWBW's terminal emulator.

So I'd preserve those functions before keys are converted into ordinary VT sequences.

=== 8. A third option

The actual current `term.asm` contains:

[source,text]
----
VDAEMU == EMUTYP_TTY
or
VDAEMU == EMUTYP_ANSI
----

So architecturally, it is tempting to imagine:

[source,text]
----
VDAEMU == EMUTYP_7XTGV
----

with a parallel 7XTGV emulation module.

Conceptually neat, but practically backwards because it would mean porting substantial smart-terminal logic into Z80-side HBIOS.

=== 9. Clean hardware-module architecture

For an RP2350/ESP32 TFT module connected to a Z80 machine, two distinct modes are worth defining:

[source,text]
----
MODE 1: VDA DEVICE

Z80/RomWBW                RP2350
-----------               ----------------
VDASCP       ───────────► cursor
VDASCO       ───────────► colour
VDASAT       ───────────► attributes
VDAWRC       ───────────► character
VDASCR       ───────────► scroll
VDAKRD       ◄─────────── keyboard event

RomWBW performs ANSI
----

and:

[source,text]
----
MODE 2: SMART TERMINAL

Z80/RomWBW                RP2350
-----------               ----------------
CIOOUT byte  ───────────► 7XTGV parser
                          ANSI/SGR256
                          screen
                          profiles
                          history/editor

CIOIN byte   ◄─────────── 7XTGV keyboard engine

7XTGV performs ANSI
----

Mode 2 is essentially what your existing 7XTGV-terminal already is.

Mode 1 would be a new, elegant way to make your modules native RomWBW video hardware.

=== This already gives much more than “4 paper colours”

Logically you encode only:

[source,text]
----
4 paper hues × 16 paper levels

so potentially **64 visibly different paper RGB565 outputs per mode**, assuming the brightness LUT makes them distinct.

[source,text]

gives potentially **256 effective ink shades**.

[source,text]

=== The dual glyph planes give another trick

For `TEXT/WIND/INST`, the compositor is currently:

[source,text]
----
A=1          -> INK
A=0,B=0      -> PAPER
A=0,B=1      -> HARD DESKTOP
----

so there are actually **three possible pixel sources** inside a cell:

[source,text]
----
INK
PAPER
DESKTOP
----

with `CHAR_A` and `CHAR_B` independently defining the shapes.

Therefore nothing says “INK must visually look like text”.

For some demo or UI effect you could use paper as one background and ink as a second background and use `CHAR_A` as a spatial mask.

That opens things like:

[source,text]
----
gradients by stippling
checker/shading textures
beveled panels
two-tone window backgrounds
shadows
highlight strips
soft-ish corners
patterns exposing desktop underneath
----

And because the brightness of ink and paper is independent, subtle two-tone regions are possible without changing base color indexes.

Yes, perceptually.

A cell can use paper color + ink color with a dither mask to create apparent intermediate shades, while `CHAR_B` can independently expose the hard desktop.

So the physical truth is closer to:

[source,text]
----
per cell:
    1 of 16 ink families × 16 levels
    1 of 4 paper families × 16 levels
    + desktop
    + two independent spatial masks
----

=== SEMI is still the proper route for arbitrary colour graphics

The spec intentionally gives SEMI a completely different interpretation.

There we reconstruct two 10-bit masks and a **10-bit palette index**, and `SEMI_INDEXED4` gives each cell four arbitrary RGB565 colours.

So I wouldn't twist TEXT/WIND/INST too hard trying to become generic graphics.

=== About whole-cell brightness

The spec does **not** contain a native per-cell whole-brightness field.

Instead, for later smart-terminal window dimming we wrote:

[source,text]
----
Effective = round(CellLevel * WindowLevel / 15)
----

applied in software during window flattening.

So there are conceptually several intensity mechanisms:

[source,text]
----
InkLevel       4-bit, cell
PaperLevel     4-bit, cell

WindowLevel    software/compositor state
LED backlight  physical display state
----

That layering is quite clean.

204 × 80 = 16,320 cells
16,320 × 4 bytes = 65,280 bytes
----

[source,text]

65,536 - 65,280 = 256 bytes spare
----

At 6×10 pixels it gives exactly:

[source,text]

204 × 6 = 1224 pixels
80 × 10 = 800 pixels

on the 1280×800 display.

=== 32-bit interleaving

The current spec repeatedly says:

[source,text]
----
CHAR_A
CHAR_B
ATTR
EXTA
----

are four bytes per cell, but also says CHAR_A and CHAR_B must remain **conceptually independent planes**.

That does **not** require four physically separate arrays.

This:

[source,cpp]
----
struct Cell
{
    uint8_t CharA;
    uint8_t CharB;
    uint8_t Attr;
    uint8_t ExtA;
};
----

is entirely compatible with the specification.

And physically:

[source,text]
----
cell 0: A B ATTR EXTA
cell 1: A B ATTR EXTA
cell 2: A B ATTR EXTA
...
----

makes each cell a natural 32-bit quantity.

That is particularly attractive for overlapping windows and cell blits.

So I think we should distinguish:

> **conceptually two glyph planes** does not mean **physically planar memory**.

=== And yes — scrolling regions really are already there

The part we'd both forgotten is very explicit:

[source,cpp]
----
case 'r': {
    int a = param(0) - 1, b = param(1, rows) - 1;
    if (a >= 0 && b < rows && a < b) {
        top = a;
        bottom = b;
        move(0, origin ? top : 0);
    }
    break;
}
----

And movement/indexing actually uses `top` and `bottom`; `?6` origin mode changes coordinate interpretation relative to `top`. So this isn't merely a parsed-but-unused variable — **there is a real DECSTBM scrolling-region implementation**.

Likewise these really exist:

[source,cpp]
----
case 's':
    save();
    break;

case 'u':
    restore();
    break;

case 'n':
    if (params[0] == 5)
        send("\033[0n");
    else if (params[0] == 6) {
        ...
    }
----

and:

[source,cpp]
----
case 'c':
    if (params[0] <= 0)
        send("\033[?1;0c");
----

So our earlier uncertainty is now resolved from the code:

> **save/restore cursor — YES**  
> **DSR/DA responses — YES**  
> **scrolling regions — YES**  
> **insert/delete characters — NO**
