= 7xtgv signed zoom-in implementation plan
:leveloffset: +2
:source-highlighter: highlight.js

*Status:* signed plan; Phase A{plus}B implementation in progress +
*Date:* 2026-09-15 +
*Immediate scope:* display-policy/runtime-geometry Phase A and integer zoom-in Phase B

This document records the final repo-grounded implementation decisions made after review of `+docs/260914-23_7xtgv_generic_zoom_in_display_geometry_plan.adoc+`. That earlier Lyra/ChatGPT document remains the complete architectural source. This file is the execution contract for the first implementation and overrides its examples where the decisions below are more specific.

[id="1-delivery-boundary"]
== 1. Delivery boundary

Implement now:

* a common display policy with stable HAL identity;
* statically allocated maximum terminal backing with runtime active geometry;
* real 1x, 2x, 3x and 4x integer glyph zoom;
* runtime physical visible geometry;
* horizontal left/right edge panning only;
* black unused panel area and a computed grey hidden-content gutter;
* per-display INI configuration;
* deterministic TFT and PC-mirror reconstruction after a view change;
* the private zoom actions and PC keyboard mappings;
* geometry-related history, overlay and plot-row correctness fixes.

Defer as independent later work:

* bird's-eye/summary renderers;
* GCLS plot zoom and plot origin;
* runtime RGB-panel scanout-frequency selection and its boot-order refactor;
* sophisticated dirty cache-range optimization.

The view controller may be designed to accept the later bird's-eye levels, but the first implementation stops at 1x when stepping toward smaller text.

[id="2-display-hal-identity-and-policy"]
== 2. Display HAL identity and policy

Each compiled display HAL supplies at least:

[source,cpp]
----
struct DisplayHalDefaults {
    const char *id;       // stable INI/machine identity, at most 8 ASCII chars
    const char *name;     // unrestricted human-readable description
    int physicalWidth;
    int physicalHeight;
    int maxCols;
    int maxRows;
    int defaultZoom;
    Geometry zoomGeometry[4];
    int defaultRenderFlushHz;
    int defaultRgbRefreshHz; // zero/not applicable for controller-GRAM panels
};
----

Exact C{plus}{plus} names may differ, but the two identities remain separate. `+id+` is used for INI matching and concise diagnostics. `+name+` preserves the current descriptive module/controller text printed at boot.

Assigned IDs are:

[cols=",",options="header",]
|===
|Target |HAL ID
|RP2350 2-inch |`+RP2_2+`
|ESP32-S3 3.5-inch |`+ES3_35+`
|ESP32-S3 5-inch |`+ES3_5+`
|ESP32-P4 10-inch |`+EP4_10+`
|ESP32-C6 1.47-inch, future |`+EC6_15+`
|RP2350 1.47-inch, future |`+RP2_15+`
|===

HAL-ID matching in `+7XTGVTRM.INI+` is case-insensitive. A nonmatching `+[display:ID]+` section is inactive and does not produce an error, allowing one SD card to move between modules.

The display policy is the single source for terminal geometry defaults. Do not duplicate independently editable column/row values between RunCPM config and graphics setup.

[id="3-maximum-active-and-visible-geometry"]
== 3. Maximum, active and visible geometry

Keep maximum storage static:

[source,text]
----
MaxCols x MaxRows       compiled backing allocation and stable row stride
activeCols x activeRows current logical terminal seen by parser/applications
visibleCols x visibleRows cells physically visible at the selected zoom
----

Cell indexing always uses the maximum stride:

[source,text]
----
index = row * MaxCols + column
----

All parser and terminal bounds use the active dimensions. Presentation and dirty scanning use the visible dimensions plus the horizontal viewport.

For a 6x10 glyph at integer zoom `+z+`:

[source,text]
----
cellWidth   = 6 * z
cellHeight  = 10 * z
visibleCols = floor(physicalWidth / cellWidth)
visibleCols = visibleCols rounded down to the nearest even number
visibleRows = floor(physicalHeight / cellHeight)
----

The even-column rule deliberately leaves a usable physical remainder rather than an almost invisible gutter. It gives these examples:

[cols=",>,>,>,>",options="header",]
|===
|Panel |1x |2x |3x |4x
|800 px wide |132 |66 |44 |32
|320 px wide |52 |26 |16 |12
|===

Thus the 800-pixel panel leaves 8, 8, 8 and 32 pixels respectively, while the 320-pixel panel leaves 8, 8, 32 and 32 pixels.

Compiled/default active column counts are even. An otherwise valid odd INI active-column value is normalized downward to the nearest even value and reported as a configuration notice. It must never be rounded upward beyond the allocated or physical limit.

There is no vertical panning. An active row count which cannot fit at its zoom is invalid and falls back to that zoom level's safe HAL default.

The W550/`+ES3_5+` normal 1x active default becomes 132x48 rather than 133x48. Its maximum backing may remain 133x48 during the refactor; active geometry is still constrained by the policy above. Other zoom geometries retain the approved earlier-plan defaults unless hardware testing justifies a later documented change.

[id="4-physical-composition-and-horizontal-panning"]
== 4. Physical composition and horizontal panning

The terminal raster is top-left aligned. Physical pixels outside the raster are black.

If `+activeCols <= visibleCols+`, there is no hidden horizontal content and all unused right/bottom space remains black.

If `+activeCols > visibleCols+`, only two viewport positions exist:

* left edge: terminal begins at physical x=0 and the complete horizontal remainder is a grey strip at the right;
* right edge: the complete horizontal remainder is grey at the left and the terminal raster begins immediately after it.

The strip indicates the direction of hidden content. There is no partial panning and no automatic cursor-follow pan. The existing global edge actions remain responsible for selecting the two positions.

The current RP2350 fixed indicator macros are replaced by this computed composition. No larger display may accidentally inherit a target-specific fixed bar.

The 6x6 red disk-activity overlay remains a physical-pixel UI element. When it expires, restoration must redraw whichever composition lies beneath it: a scaled cell, black margin, or grey gutter.

[id="5-integer-glyph-renderer"]
== 5. Integer glyph renderer

Generate the existing 6x10 RGB565 cell first, then nearest-neighbour expand it into one reusable maximum 4x cell buffer:

[source,text]
----
24 * 40 * 2 bytes = 1,920 bytes
----

Submit one complete scaled bitmap for each dirty visible cell. Do not issue one generic Arduino++_++GFX draw call per expanded raster row.

This maps efficiently onto the existing backends:

* direct Arduino++_++TFT controller paths open one transaction, set one address window and write the complete bitmap;
* the `+ES3_35+` AXS15231B workaround writes the bitmap into its rotated `+Arduino_Canvas+`, then the existing deferred flush publishes the canvas;
* the `+ES3_5+` RGB path writes into its continuously scanned framebuffer and retains deferred cache/publish handling.

The 3.5-inch controller's unreliable hardware rotation remains isolated in its HAL: the panel stays native 320x480 and `+Arduino_Canvas+` exposes the tested 480x320 rotated client. Generic zoom code must not special-case it.

Rendering work is budgeted by approximate physical pixel area, not merely by the number of cells. A 4x cell represents sixteen times the pixel work of a 1x cell. Buffered and direct targets may retain different budgets.

[id="6-runtime-geometry-transition"]
== 6. Runtime geometry transition

A zoom change is a rare one-shot operation. It favors deterministic state over an incremental animated transition:

[arabic]
. pause incremental presentation;
. abort any active/retained plot transaction;
. select and validate the new zoom and active geometry;
. preserve cells in the intersection of old and new active geometry;
. blank cells excluded by a shrink and cells newly exposed by an enlargement;
. clamp cursor and saved cursor;
. reset scrolling margins, tab stops, wrap state, overlays and viewport to valid values;
. clear the complete physical client to black;
. invalidate and repaint the complete visible TFT composition;
. reset and rebuild the complete PC mirror;
. resume incremental presentation.

Returning to a larger geometry must never reveal stale text which was outside the smaller active surface.

[id="7-ini-behavior"]
== 7. INI behavior

Configuration precedence remains:

[source,text]
----
HAL compiled defaults
        -> [global] applicable display defaults
        -> matching [display:HALID]
----

Parse display settings into a temporary candidate and publish them only after validation. Parsing and publication must not expose a partially updated display policy to the other core.

Validation covers maximum backing geometry, zoom range, physical fit, the even-column policy and the no-vertical-panning rule.

* An invalid `+view_zoom+` falls back to the HAL default.
* An impossible geometry for one zoom falls back to that zoom's compiled HAL geometry.
* An odd but otherwise valid active width is rounded downward with a notice.
* Malformed active sections increment the configuration error count.
* Unknown/nonmatching display sections are ignored without errors.

Application/history-bank settings remain independent from display selection.

RGB scanout timing remains a compiled HAL value in this delivery. A runtime `+render_flush_hz+` may be applied after INI loading where supported. Runtime `+rgb_refresh_hz+` is deferred because the display currently starts before the RunCPM-owned SD card and INI are available.

[id="8-pc-development-mirror"]
== 8. PC development mirror

The mirror represents the complete active logical terminal; it does not follow the TFT's left/right viewport.

Keep the host side simple and reliable:

* do not resize Konsole, Kitty or tmux automatically;
* on every device zoom/geometry change, send a mirror reset/clear followed by one complete active-screen snapshot;
* monitor the local PC terminal size in `+terminal.py+`;
* after a debounced `+SIGWINCH+`/size change, request a complete device snapshot with the existing PC-mirror snapshot command;
* retain incremental dirty-row mirroring after the full snapshot.

The user may reduce the host font with Ctrl{plus}- until the active logical surface fits. The resulting host resize must itself trigger the new snapshot, so a manual CP/M `+CLS+` is no longer needed merely to fill newly visible host rows or columns.

If the host is smaller than the active surface, clipping is accepted for this development mirror. It must not alter TFT state or reduce the device's active logical geometry.

Mirror buffering must be sized or streamed from `+MaxCols+`; do not assume that the present fixed row representation remains sufficient for future 10-inch HALs.

[id="9-history-overlays-and-row-tracking"]
== 9. History, overlays and row tracking

The command-history limit remains 127 characters per line. It is intentional and is not enlarged as part of zoom support.

Screen-row capture is a separate concern and receives storage sufficient for the compiled `+MaxCols+` (and uses `+activeCols+` as the runtime length). It must not silently inherit the command-history limit.

All temporary row-sized arrays, history notices, tab stops, dirty arrays and mirror row flags are allocated for maximum geometry and iterated using the appropriate active/visible dimension.

Replace the current 32-bit `+plotActiveRows+` mask with storage covering every compiled `+MaxRows+`, preferably a simple boolean array. This is required now for the 48-row W550 and later for the planned 80-row ESP32-P4 panel.

[id="10-controls"]
== 10. Controls

The canonical embedded actions are:

[source,text]
----
CSI > 66 v    one view level toward larger real glyphs
CSI > 67 v    one view level toward smaller glyphs
----

In this first delivery the smaller direction stops at 1x; later bird's-eye levels can extend the same controller without changing these commands.

PC Ctrl/Alt/Shift chords are configurable adapters which emit these CSI actions. They are not the embedded protocol. Preserve a prefix-command fallback suitable for Czech and other keyboard layouts where pass:[<code>+</code>] is not a simple physical key.

[id="11-required-first-delivery-tests"]
== 11. Required first-delivery tests

Host tests cover:

* maximum-stride indexing with several active geometries;
* every parser erase/insert/delete/scroll bound after resize;
* cursor, saved cursor, margins, tabs and viewport transition state;
* shrink then enlarge without stale cells;
* 1x through 4x exact RGB565 nearest-neighbour output;
* even visible-column calculation and black/grey composition;
* left/right pan marker placement;
* INI ID selection, case-insensitive matching and invalid fallback;
* 127-character command history independent of wide screen capture;
* row tracking above row 31 and through at least row 79;
* complete mirror rebuild on device geometry change;
* host-size-change snapshot request.

Initial real-device validation uses `+ES3_5+`, including:

* 1x 132x48;
* 2x 80x24 at both viewport edges;
* 2x exact-fit 66x24 with a black, not grey, remainder;
* 3x and 4x transitions;
* Ctrl{plus}- host-font resizing followed by an automatic complete mirror snapshot;
* cursor, disk indicator, retained-plot clearing and heavy scrolling.

After that, build and visually regress `+ES3_35+` and `+RP2_2+`, paying particular attention to the rotated canvas path and the computed gutter replacing the RP2350 fixed indicator.

[id="12-completion-criterion"]
== 12. Completion criterion

Phases A{plus}B are complete when all three present HALs build, host tests pass, the `+ES3_5+` device can switch among 1x..4x without stale pixels or terminal-state corruption, and both compact-panel regressions preserve their current terminal, history, backlight, disk-activity and panning behavior.

Implementation and hardware validation remain separate: only a tested build for a selected target is eligible for flashing.
