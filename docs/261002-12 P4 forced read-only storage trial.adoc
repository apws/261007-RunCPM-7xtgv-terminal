= P4 forced read-only storage trial
:source-highlighter: highlight.js

== Purpose and scope

Petr requested a compile-time forced-read-only option before trying the P4
50 MHz requested SPI setting. This is independent of card INI settings.
The current option supports only `jc8012p4a1c`; no RunCPM core or installed
SdFat source is modified. Normal builds retain direct `SdFat32 SD`.

== Build and deployment

From `src/RunCPM_7xtgv-terminal`:

[source,shell]
----
python3 tools/reflash.py --target jc8012p4a1c --build-only --storage-read-only
----

The option injects `XTGV_STORAGE_READ_ONLY=1` and
`USE_BLOCK_DEVICE_INTERFACE=1` across the entire build, including SdFat.
The latter is an ABI/layout choice and must not be defined only in a sketch
header. Unsupported targets and use without a build are rejected.
The flag is deliberately not remembered in terminal.conf or the INI: every
read-only rebuild must request it explicitly. Flashing an already-built
candidate needs no flag; protection is part of that binary.

A normal rebuild without the option restores write capability. It does not
change the selected experimental SPI clock; reverting that is separate.

== Enforcement

The board-local `XtgvReadOnlyStorage` mounts FatVolume on
`XtgvReadOnlyCard`, an FsBlockDeviceInterface implementation owning a private
SdSpiCard. Only initialization, reads, status, synchronization and shutdown
are forwarded to the physical card. Both sector-write methods return false
without reaching it. No physical card handle or erase operation is exposed.

Writable opens, remove, rename, mkdir, rmdir and truncate are also rejected at
the facade, before they can modify filesystem caches. File32/directory-handle
operations that bypass that facade still encounter the sector-write guard.
This covers CP/M writes, terminal INI/history persistence and 7XF catalog
updates. It is not merely CP/M's logical drive write protection.

The boot banner explicitly says `STORAGE READ-ONLY TEST`.
Save errors and operations requiring a writable directory may fail; applications
are not promised transparent writable behavior. This is a firmware filesystem
write barrier, not physical write protection or a guarantee against electrical
faults, malformed commands on a marginal link, or internal card housekeeping.
Keep a backup/spare card for speed-limit tests.

== Validation and next step

Native tests exercise the actual board class definitions with test doubles:
mount failure, read forwarding, writable-open rejection, directory-operation
rejection and virtual single/multi-sector write rejection. Existing power-order
and build-property tests pass. Firmware compilation and hardware verification
are pending; no card operations were performed for this change.

After an explicitly requested build/reflash, first confirm the read-only boot
warning and successful mount. Petr performs the read benchmark. Any deliberate
write-rejection hardware test should use a spare card and be separately agreed.
