== Scope and verification status

This guide describes the current Linux workflow, reviewed on 261004.
The firmware and tools run without Codex or any AI service. Arduino IDE is
optional; our maintained build entry point uses Arduino CLI and Python.

Existing-machine builds and device uploads have been exercised. The complete
installation below has *not yet been tested in a fresh machine/container*.
Do not confuse a successful local build with a proven clean-clone setup.
Native Windows support for these host scripts is not established: even the
build wrapper imports POSIX serial helpers. macOS/WSL are not validated paths.

== Native desktop shortcuts

=== Optimization on all targets

In any target folder, `./rebuild.sh -O2` builds firmware using
the selected optimization; `./desktop-rebuild.sh -O2` builds its
native desktop counterpart. Choices are `O0`, `Og`, `O1`, `O2`, `O3`, `Os`
and `default`. No setting is persisted: omission uses the hardware profile's
current default, or desktop `-O2` with debug symbols. The longer
`--optimization O2` form also works. Reflash/launch use existing binaries
and reject this build-only option. `-O2` is the recommended desktop starting
point; preserve measured hardware defaults rather than assuming O3 is faster.
Source overrides do not rebuild precompiled SDK archives; low-optimization
MCU firmware can exceed memory limits. No hardware build is implied here.

=== Desktop launch

For the Arduino-compatible SDL desktop runtime, see
link:../src/RunCPM_7xtgv-terminal/desktop/README.adoc[desktop build and launch].
Each `tools/targets/DISPLAY_ID -- target/` folder now also has
`desktop-rebuild.sh`, `desktop-local.sh` and `desktop-card.sh`.
They emit short status and keep detailed same-named logs beside the scripts.
Launch uses the last native build, never firmware upload. Normal runs may write
INI/history and guest files to the selected card directory.

`tools/setup.sh --dry-run` previews normal setup, including CMake/make/C++/SDL2
packages for the detected Arch/Debian/Fedora family and Arduino dependencies.
Remove `--dry-run` to request installation; desktop prerequisites are included
by default. The former `--with-desktop` flag remains a compatibility alias.
The shared mirror prefers Konsole, then Kitty, then the current terminal;
desktop PTYs use isolated sessions and cannot invoke hardware reflash.

== Clone the repository

[source,sh]
----
git clone https://github.com/apws/260906-7xtgv.git
cd 260906-7xtgv
git status --short
git log -1 --oneline
----

Use an empty destination name if that directory already exists; do not overwrite
an existing checkout. Record the commit when comparing builds. A clone contains
only committed/pushed content, not Petr's uncommitted working tree or device files.

* `src/RunCPM_7xtgv-terminal/`: integrated firmware, board HALs and host tools.
* `cpmcard/`: complete versioned working card, including settings/history and snapshots; not an automatic SD installer.
* `docs/`: manual and development evidence.
* `build/`, `private/`, `docs/private/`, backups and local comparison material:
  ignored/local content, not supplied by cloning.

The firmware uses the RunCPM-derived sources already in this repository.
Do not replace them by independently cloning current upstream RunCPM; that
would be a separate port. There is no RunCPM submodule setup step.

=== Install tools and packages

Install Git, Python 3 and optional desktop/test tools through your Linux
distribution. Names commonly include `git`, `python3`, `g++`, `tmux`,
`konsole` or `kitty`, and `acl`; exact names vary by distribution.

Obtain Arduino CLI using the https://docs.arduino.cc/arduino-cli/installation/[official installation instructions].
Put the executable on PATH, or set `ARDUINO_CLI` to its executable path.
Do not run builds as root. Check availability:

[source,sh]
----
git --version
python3 --version
arduino-cli version
arduino-cli config dump
arduino-cli core list
----

For a new CLI installation without a config file, run `arduino-cli config init`.
Do not force-overwrite an existing configuration. Add the relevant package
index if it is not already listed. Install only the MCU families you need:

[source,sh]
----
# ESP32-S3, ESP32-P4 and ESP32-C6:
arduino-cli config add board_manager.additional_urls https://espressif.github.io/arduino-esp32/package_esp32_index.json
arduino-cli core update-index
arduino-cli core install esp32:esp32@3.1.0

# RP2350:
arduino-cli config add board_manager.additional_urls https://github.com/earlephilhower/arduino-pico/releases/download/global/package_rp2040_index.json
arduino-cli core update-index
arduino-cli core install rp2040:rp2040@5.4.4
----

Package URLs come from the https://docs.espressif.com/projects/arduino-esp32/en/latest/installing.html[Espressif installation guide]
and https://arduino-pico.readthedocs.io/en/latest/install.html[Arduino-Pico installation guide].
Use the project baseline versions above, not an unreviewed latest-core upgrade.
The ESP32 SDK bundle observed locally is `idf-release_v5.3-083aad99-v2`.

Arduino CLI profile builds resolve the library versions declared in sketch.yaml;
the first build may download those dependencies. Library installation errors
must be resolved before compiling, not bypassed with unrelated latest versions.
If manually inspecting/installing matching libraries, the CLI commands are:

[source,sh]
----
arduino-cli lib update-index
arduino-cli lib install "GFX Library for Arduino@1.6.4" "SdFat@2.3.0"
----

Profile-managed dependencies may use an isolated installation; a global
`lib install` is not proof of what a profile build selected. Check build output.

== Select and build the exact target

[cols="1,2,2",options="header"]
|===
|Module ID |Target/profile argument |Module
|ES3_35 |jc8048w535 |ESP32-S3 3.5-inch
|ES3_5 |jc8048w550 |ESP32-S3 5-inch
|EP4_10 |jc8012p4a1c |ESP32-P4 10-inch
|RP2_147 |rp2350-lcd-1-47-a |RP2350 1.47-inch
|RP2_2 |rp2350-touch-lcd-2 |RP2350 2-inch
|EC6_147 |esp32c6-lcd-1-47 |Experimental single-core ESP32-C6 1.47-inch
|===

From the clone root, for example:

[source,sh]
----
cd src/RunCPM_7xtgv-terminal
python3 tools/reflash.py --target jc8012p4a1c --build-only
----

Replace the target with the table entry for your board. No device connection
is required for `--build-only`. The wrapper reads tools/targets/*.json and
sketch.yaml, preserves platform flags, adds our target/product/SPI flags and
a fresh YYMMDD-HHMM stamp, and stages a successfully compiled image in:

[source,text]
----
build/RunCPM_7xtgv-terminal/TARGET/new/
----

That path is relative to the repository root. `current/` is left intact;
promotion of a hardware-accepted candidate is a separate operation.
Do not use the old bare `arduino-cli compile --profile ...` recipe: it omits
target metadata supplied by the wrapper and is not the supported shortcut.
Do not mix binaries from different target folders.

== Explicit Linux setup

From the sketch directory:

[source,sh]
----
./tools/setup.sh --dry-run
./tools/setup.sh
----

Setup asks before installation. System packages use sudo with the selected package manager; Arduino
CLI, pinned cores and libraries are installed as your user. Do not run the script
with sudo. It does not upgrade the system, build, flash, or install a desktop. USB serial-group membership is offered separately
with its own confirmation; `--yes` does not approve this account change.
With the device connected, rerun `./tools/setup.sh --serial-only` to check
and configure access without repeating dependency installation. Existing
membership is left unchanged; log out and back in to activate it for all apps.
Existing Arduino CLI is reused; when absent, a
checksummed 1.5.0 executable is installed under `~/.local/bin`.
`XTGV_ARDUINO_CONFIG` is honored when supplied.

Rebuild/reflash report missing required tools and suggest setup, never install
automatically. `setup.sh` detects the OS from `/etc/os-release`: exact `ID` first, then
ordered `ID_LIKE` families. Arch uses pacman, Debian/Ubuntu uses apt-get,
and Fedora uses dnf. Unsupported families stop before installation.
Options are `--dry-run`, `--yes` and `--serial-only`.
Debian refreshes package indexes with apt-get update before installation.
The installer never performs a full system upgrade. Debian/Fedora are offline-tested
with fake installers; real installation remains to be checked on those systems.
macOS/Windows adapters remain future work. USB group changes require the separate setup confirmation and sudo.

Offline tests use fake installers and isolated temporary files. They are not
proof of a real fresh Arch installation. `fresh-build.sh` remains the separate
dependency-isolated download/build test; it does not install OS prerequisites.

== Separate rebuild and reflash commands

From the sketch directory:

[source,sh]
----
cd "tools/targets/EC6_147 -- esp32c6-lcd-1-47"
./rebuild.sh
./reflash.sh
----

Each of the six targets has a `DISPLAY_ID -- TARGET` folder containing
`rebuild.sh` and `reflash.sh`. Rebuild creates/stages a fresh `new` candidate
without device or mirror access. Reflash uploads the existing `new` candidate
(falling back to `current`), without compiling, then restores the visible mirror.
Neither command promotes the candidate or edits terminal.conf.
Use the wrapper for your physical board, not the one for a previously attached
module. Upload restarts CP/M and loses active application state.

* `--port /dev/serial/by-id/...`: explicit port when discovery is ambiguous.
* `--dry-run`: show workflow without building or touching the device.
* Default output is concise step/status lines. Full details are saved beside
  the launcher as `rebuild.log` or `reflash.log` (replaced each run).
  Normal output is module, build/upload progress and completion, embedded
  stamp and mirror launch. Paths stay in the log, with BUILD/FLASH separators.
  Failures show one short reason, not a CLI transcript; a blocked target check
  explicitly reports that flashing was not performed.
* `--verbose`: show live compiler/uploader output instead.
* `--mirror terminal`: use the shared tmux terminal without a desktop GUI.

For RP2350, an eligible BOOTSEL disk already connected skips the prompt.
If none is connected, a red warning names the module and asks you to connect it
in BOOTSEL mode, then press Enter. No long target-name retyping.
The tool verifies RP2350 and the UF2 target/family. An optional
`--chip-id HEX16` further restricts disk selection; ROM alone cannot identify
the display variant.
More than one candidate is rejected without a chip selector.
For C6, uploader reset may leave a blank screen: physical RESET restored the
tested module. Do not add recovery bypass merely to fix a wrong target.
Missing ESP serial connections similarly prompt in red and wait for Enter,
without BOOTSEL wording. Ambiguous ports and mismatched firmware remain errors.

First-install/old ESP firmware may need the explicit one-shot option
`--allow-unidentified-target TARGET`; normal launchers never add it themselves.
Missing serial permissions are reported; existing configured group membership
can be entered without sudo via newgrp.

See link:../docs/261004-1848%20Isolated%20fresh%20builds%20and%20per-target%20reflash%20launchers.adoc[workflow implementation and test boundaries].

== Flashing and the desktop mirror

Existing latest images are in `build/RunCPM_7xtgv-terminal/TARGET/new/`.
Upload-only falls back to `current/` when no new candidate exists.
The launcher prints the embedded stamp when identifiable; exact image paths
are recorded in the adjacent log.
Archived top-level legacy build folders were moved into ignored
`private/261004-1907 legacy build folders/`; active target artifacts are intact.

Build and flash are deliberately separate. For an already running, identifiable
ESP32 target, stop the shared mirror, then upload the staged candidate:

[source,sh]
----
# Close the mirror normally, or stop its shared session if it exists:
tmux kill-session -t 7xtgv-cpm
# Example only: verify the board and its actual port first.
python3 tools/reflash.py --target jc8012p4a1c --port /dev/ttyUSB0
./tools/kon.sh --port /dev/ttyUSB0
----

The uploader checks firmware target identity. A reported mismatch is a stop
condition. A blank board/older firmware without the identity protocol needs
an explicitly checked, one-shot recovery workflow; do not disable the guard
permanently. Flashing restarts CP/M and loses active application state.
For RP2350 use its target shell launcher, which handles the guarded BOOTSEL
copy; the bare ESP32 upload command above is not an RP2350 recipe.
See link:technical-reference-guide.adoc[build/upload boundaries].

Review tools/terminal.conf before using the launcher, especially XTGV_TARGET,
XTGV_PORT and the optional device-triggered reflash command. They reflect a
host selection, not automatic physical-board detection. Keyboard defaults
also reflect Petr's Czech layout and may need adaptation.

Serial port names can change after reconnect. Check `arduino-cli board list`
and `/dev/serial/by-id/` rather than assuming ttyUSB0. Use your distribution's
serial-device group (often dialout or uucp), with a fresh login after membership
changes, or a narrowly scoped temporary ACL. Such an ACL can disappear when
USB recreates the device node. Never open two serial readers simultaneously.
Restore one visible mirror after uploading/transferring and confirm the build
stamp, module identity, SD mount and CP/M prompt.

== SD card and CP/M tools are separate

Flashing firmware does not copy the cpmcard working tree to an SD card or install
every COM file. Use the RunCPM FAT directory layout, e.g. drive A user 0 is
`A/0`; repository descriptive folder names are not literal SD folder names.
See link:../cpmcard/README.adoc[CP/M card layout and seed] for the mapping and
link:reference-guide.adoc[transfer commands] for selective file deployment.
Do not blindly copy historical archives or overwrite live INI/history files.
An initial card needs appropriate CP/M contents; transfer via VTPUT/VTGET also
requires those helpers already installed, so it is not a blank-card bootstrap.

Firmware compilation does not require assembling REBOOT, CARDMARK, VTCPU or
other guest tools. When their sources change, rebuild them separately using
the documented dialect/tool: Intel 8080 ASM/LOAD and Z80 assemblers are not
interchangeable. A host assembler is not currently installed by our build wrapper.

== Troubleshooting and expected effort

[cols="2,3",options="header"]
|===
|Symptom |Check/remedy
|Cannot find arduino-cli |PATH or ARDUINO_CLI; the wrapper also checks the user-local bin directory.
|Cannot resolve Arduino build flags |Read the following CLI diagnostic: absent core/profile dependencies or incompatible board options commonly stop this step.
|Unknown board/core or missing library |Package index, network access and exact profile versions; installation is normally sufficient.
|Download/TLS error |Network/proxy/CA certificates and free disk space; do not edit HAL code to compensate.
|Missing API or compilation fails with a newer core |Use the core version pinned in the profile before investigating; isolated installation/build still needs validation.
|Permission denied or missing serial port |Correct device node, USB data cable, permissions and no competing reader. Building alone does not need serial access.
|Target mismatch |Stop and select the right physical board and target; never bypass a known mismatch.
|No staged image |Build this target first; ignored build artifacts do not arrive in a clone.
|SD failure / CPU halted |Card format/layout, connection and power; flashing does not populate the card.
|Mirror launcher missing |Install its desktop terminal and tmux, or use terminal.py directly in a compatible terminal.
|===

Once installed, normal rebuilding is one command. A first setup requires
package downloads and host/USB configuration, but normally not source porting.
No universal time estimate is claimed: download speed, caches and host CPU
dominate. The isolated dependency script below is not a distro installer or
a complete device/permissions doctor.

== Tests and remaining reproducibility work

From the sketch directory:

[source,sh]
----
python3 -m unittest discover -s tests -p 'test_*.py' -v
----

Some tests compile native C++, some expect installed Arduino packages or other
tools. Use the project README for focused C++ tests. A skipped dependency test
is not a successful firmware/device qualification. Host tests cannot establish
SD electrical reliability, panel timing, backlight behavior or USB power margin.

Remaining work, not performed by documenting this guide:

* Verify the explicitly pinned ESP32 platform/index resolves in a clean install.
* Reproduce installation and builds with a fresh Arduino data/cache directory.
* Check all six targets without private/vendor ZIPs or undeclared local patches.
* Record supported CLI/Python/host versions and actual download/storage needs.
* Validate mirror, permissions, upload and initial SD preparation from that clone.
* Consider a small prerequisite checker; separately assess Windows/macOS support.

Commit/push is a separate step: publishing this guide does not publish ignored
binaries, device configuration, or uncommitted source changes.

=== Clean-clone acceptance gate

This gate is essential and still *not passed*. Documentation and existing
machine builds do not substitute for it.

. Choose a published commit and a disposable checkout on a separate machine
  or isolated environment; record Linux, Python and Arduino CLI versions.
. Use empty Arduino data/download/user directories and an empty build cache.
  Do not borrow the developer's packages, vendor ZIPs or modified libraries.
. Install only the declared package indexes, baseline cores and pinned libraries.
. Build each target through `tools/reflash.py --build-only`; save dependency
  resolution logs, effective flags, image sizes and failure/remediation notes.
. Confirm artifacts contain the correct target and new build stamp.
. Separately verify USB permissions, first upload, mirror launch and a minimally
  populated SD card. A compiler-only environment cannot prove those steps.

The wrapper now passes `XTGV_ARDUINO_CONFIG` to dependency resolution and
compilation (and upload). ESP32 profiles now pin their platform/index.
These mechanisms still need a real isolated build before claiming reproducibility.
Do not run builds as root.

=== Local dependency-isolation script

From the sketch directory:

[source,sh]
----
# Current non-ignored working files; not proof of published-clone completeness:
./tools/fresh-build.sh --snapshot --target esp32c6-lcd-1-47

# Published GitHub checkout with downloaded tools/dependencies:
./tools/fresh-build.sh --target all --ref COMMIT
----

The script downloads a checksummed Arduino CLI release, installs baseline
cores/libraries into empty temporary directories, then uses the normal
build-only wrapper. Property resolution and compilation use the same explicit
config. Logs and artifacts are retained outside the working checkout.
`--use-cli PATH` reuses only that executable, not its packages/cache;
`--source URL_OR_PATH` changes the clone source. See `--help`.

It still requires Linux, bash/coreutils, Git, Python, curl, tar, certificates
and network access. It does not simulate missing OS packages or install
desktop/USB tools. A VM/container/second-machine check remains necessary.
New uncommitted targets cannot exist in a GitHub clone until published.

== Launch the mirror separately

Each `tools/targets/<module> -- <target>/` directory has `mirror.sh` alongside
`rebuild.sh` and `reflash.sh`. Run `./mirror.sh` to attach the terminal without
building, uploading, resetting, or stopping an existing shared session.
It uses the same automatic Konsole/Kitty/current-terminal selection as reflash.
Use `--port DEVICE` or `--mirror konsole|kitty|terminal` when needed.
