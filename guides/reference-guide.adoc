not the proposed native 7xtgv interface. For tasks start with the
link:user-guide.adoc[User Guide]; for code and private protocols use the
link:technical-reference-guide.adoc[Technical Reference Guide]. Settings in the live
device INI may differ from compiled defaults and from the local copy.
The link:features_timeline.adoc[Features Timeline] tracks command and file
name changes; syntax below is the current reference.

[[starting-the-pc-mirror]]
== Starting the PC mirror

From the repository root, launch either:

[source,sh]
----
./src/RunCPM_7xtgv-terminal/tools/kon.sh
./src/RunCPM_7xtgv-terminal/tools/kit.sh
----

Both attach to one `++tmux++` session named `++7xtgv-cpm++`. It owns the USB serial device, so do not run a second serial terminal beside it. A USB reconnect can briefly blink the PC screen while the complete terminal snapshot is redrawn. This mirror-only refresh preserves a retained xterm256 image on the TFT, which remains usable throughout.

Paths such as `tools/terminal.conf` below are relative to
`src/RunCPM_7xtgv-terminal/`, the sketch directory. The launchers read that shell
configuration file; it is separate from the device INI. `XTGV_TARGET` selects
the hardware target, `XTGV_PORT` its serial node, and `XTGV_TRANSFER_ROOT` the
local transfer-folder root. No second serial reader should run during a transfer.

`++Ctrl+] q++` leaves the host bridge. `++Ctrl+]++` followed by `++Ctrl+]++` sends a literal `++Ctrl+]++` byte to CP/M.

[cols="2,3",options="header"]
|===
|Host setting |Effect
|`++XTGV_TARGET++` |Exact named target selected in `++tools/terminal.conf++`; not inferred from USB identity.
|`++XTGV_PORT++` |Optional serial-port override; absent means target JSON default/discovery. Explicit CLI `++--port++` wins over it.
|`++XTGV_TRANSFER_ROOT++` |Optional local root for VTPUT/VTGET; defaults to `++XTGV_CARD_ROOT++` or this repository's `++cpmcard++`.
|`++XTGV_REFLASH_COMMAND++` |Optional host dispatcher for a guest REFLASH request. Leaving it unset disables automatic flashing.
|===

Host target metadata lives in `++tools/targets/<target>.json++`; the device
INI does not select an uploader target. Restart the mirror after changing
host target or port configuration.

[[vtput--vtget-from-the-mirror]]
=== VTPUT / VTGET from the mirror

Leave CP/M idle at its CCP prompt. Open the host panel with `++Ctrl+Shift+X++` (or `++Ctrl+] m++`). It invokes the appropriate helper automatically; do not start XMODEM or another application first. An idle-prompt check precedes commands, but this is a screen heuristic, not a firmware state guarantee.

[cols="1,1,1",options="header"]
|===
|Direction |Choose in panel |Operation
|Host file to CP/M |`++S++`, local DU, source, target, `++Y++` |VTPUT writes target in device current DU
|CP/M file to host |`++R++`, local DU, source, target |VTGET reads device current DU; asks Y/N/C if local target exists
|===

Both directions ask for *DU* first, e.g. `++a6:++` maps to `++cpmcard/A/6++`, then ask for *Source* and *Target* filenames. Target is prefilled with Source and can be edited before Enter. `++AF:++` and `++A15:++` both select the local `++A/F++` folder. DU matching is case-insensitive; missing folders or symlinked DU directories are rejected, not created. Lowercase filenames match existing uppercase mirror names; new receive names are uppercase. Absolute paths and directory components are not accepted here. Set/export `++XTGV_TRANSFER_ROOT++` in `++tools/terminal.conf++` to use another card root (the old `++XTGV_XMODEM_ROOT++` remains a fallback). *DU selects only the local folder. The device stays in its current drive/user.* Filenames must be supported 8.3 names. To receive device A0 into local A3, leave the device at `++A0>++`, then choose `++R++`, local `++A3:++`, source and target in the panel. Use Left/Right, Home/End, Backspace/Delete to edit, Ctrl{plus}U to clear, and Enter to submit each field. Konsole's private encoded keys are handled locally. Send always asks permission to replace/create the device target (no remote existence probe). Receive asks only if the local target exists. `++Y++` proceeds, `++N++` returns to editing Target, `++C++` or Escape cancels; Enter is not consent. Confirmed local replacement is performed after the full download and a temporary-file write; a changed local target invalidates the earlier approval. Bytes are transferred unchanged, with CP/M record padding; there is no automatic text conversion or compression. Use the CLI `++--cpm-text++` option for LF-only source. New local files use exclusive creation. The result remains visible until Enter/Esc. Transfers temporarily use profile ++#++9 and RAW input. They read the original profile through Alt+Space and restore that profile and its RAW state on success or failure, without executing its `on_select` command. An unconfirmed restoration reports an error. If a transfer fails while CP/M is still running a helper, reset before retrying.

VTGET tags each hex row with its record number to reject stale mirrored rows.
The updated host also accepts the old clear-per-record format; old host clients
do not understand the new tagged format. The framing implementation is in the
link:technical-reference-guide.adoc#private-protocol-boundaries[Technical Reference Guide].

Use an 80-column *logical terminal* for transfers. At 40 logical columns,
VTGET's 69-character tagged rows wrap and the download can stall. A 26- or
40-column physical viewport onto an 80-column logical terminal is different
and does not impose that wrapping. RAW input also bypasses normal pan-command
interception; do not use interactive pan as a transfer recovery mechanism.

Before changing the device INI, fetch its current A0 copy with
`tools/fetch-7xtgvtrm-ini.sh` (explicit `--target`/`--port` if needed), edit the
fresh local mirror, then send it with overwrite approval. The helper archives
the previous local copy and replaces it only after a successful fetch. Stop
on fetch failure: an older local INI can overwrite unrelated on-device edits.
See link:../docs/260924-21%20live%20INI%20preservation%20and%20narrow%20transfer%20limitation.adoc[live INI and transfer-width notes].

Guest text in the local `cpmcard/` working tree is maintained as CRLF with a final
Ctrl-Z, ready for byte-preserving Send/Receive. No upload conversion is needed.
The CLI text-conversion option is only for deliberate external host-text imports.
Tokenized BASIC, binaries, disk images and checksummed history are not text;
host-only JSON metadata, Markdown readmes and Makefiles retain host format.

*XMODEM is not supported through this reconstructed-screen channel.* Its UI
entry was replaced; CONSOLE8 or RAW input alone does not make it binary-safe.

[[output-interpretation-modes]]
=== Output interpretation modes

There are exactly two persistent terminal-output interpretations: ANSI/VT100 (the normal default, including the implemented xterm colour extensions) and VT52. `++Ctrl+] 1++` / `++2++` select them; the host bridge can also select one at connection with `++--mode ansi++` or `++--mode vt52++`. An application can request the standard DEC transition itself: `++CSI ? 2 h++` selects ANSI/VT100, `++CSI ? 2 l++` selects VT52, and VT52 `++ESC <++` returns to ANSI/VT100.

`++## RAW++` is only an input-routing state, application profiles are keyboard translation choices, and GCLS/xterm256 plot is a temporary graphics canvas; none is a third persistent terminal emulation mode. Application cursor/keypad flags are likewise negotiated submodes within ANSI/VT100, not separate terminal types.

[[implemented-escape-sequence-subset]]
=== Implemented escape-sequence subset

ANSI/VT100-style output supports CR, LF/VT/FF, BS, BEL, SI/SO and tabs at
eight-column stops; ESC H sets a stop and CSI g clears one or all stops.
Cursor addressing/movement includes CSI A/B/C/D, E/F, G, H/f and d. CSI J/K
erase modes 0/1/2 work; CSI 3 J does not clear scrollback because there is
none. ESC D/M/E index/reverse-index/next-line; CSI r sets scroll margins and
CSI L/M inserts/deletes lines. DEC private ?6, ?7 and ?25 control origin,
autowrap and cursor visibility. ESC 7/8 and CSI s/u save/restore the relevant
cursor/rendition/charset state. CSI ?1 and ESC =/> select cursor/keypad
application modes. ESC #8, ESC c, CSI 5n/6n, CSI c and ESC Z have their
implemented alignment/reset/status/identity meanings. CSI ?2 l enters VT52.

G0/G1 may designate ASCII (ESC ( B / ESC ) B) or DEC Special Graphics
(ESC ( 0 / ESC ) 0); SI/SO selects the active set. The DEC test notes below
identify approximations and unsupported control pictures. SGR supports
0, 1/22, 4/24, 5/25, 7/27, 30..37/39, 40..47/49, 90..97 and 100..107,
subject to the palette/paper mapping below. This is not full ANSI or VT100
conformance.

VT52 mode supports ESC A/B/C/D, H, I, J, K; ESC Y plus row+32 and column+32;
ESC Z identification, ESC F/G graphics/ASCII, ESC =/> keypad selection and
ESC < return to ANSI. Its graphics use the implemented DEC set, not the
original VT52 character ROM.

There is no alternate screen, scrollback, 132-column mode, double-sized
lines, mouse, UTF-8 guest input, automatic pan or binary console transport.
Unsupported CSI commands are ignored as units; string controls are consumed
without display. Bytes above 127 do not directly index the 6x10 font. The
private 7xtgv query/control protocol is catalogued in the
link:technical-reference-guide.adoc#private-protocol-boundaries[Technical Reference Guide].

`++Alt+Esc++` and `++Alt+Backspace++` are configured globally in `++7XTGVTRM.INI++` as dual-Alt gestures. Their generated commands and the Ctrl{plus}Shift view controls are handled before application-profile bindings and are not saved in history. Backlight and palette selections persist; ordinary zoom and pan do not alter the INI or resize the logical CP/M terminal.

The forced-return chord also works in `++## RAW++`. It does not wait for an
application keyboard read, but it waits for an in-progress host SD operation
to finish. Open application files may be incomplete and unsaved work is lost.
A stopped MCU, terminal task or SD driver still needs a physical reset.
Konsole cannot distinguish Left Alt from AltGr in this key table; if
AltGr{plus}C produces Ctrl{plus}Alt{plus}C on a particular host layout, it
is unsafe during a COM. Do not rely on this shortcut until the device has
been hardware-tested on your target. Historical prompt-layout regressions and
corrections belong to the timeline/checkpoints, not current usage instructions.

[[histories-banks-and-the-active-line]]
== Histories, banks, and the active line

There are ten named FIFO histories, each retaining at most 100 entered lines.
Single-character submissions are ignored.

* Up/Down normally recall entries; profiles may reserve them for the app and
  use Alt+Up/Down for history.
* A token immediately before the cursor filters matching entry prefixes.
  Recall wraps, replaces that token and adds one trailing space.
* Filtered completion inside a nonempty prefix, e.g. `10 PR`, is not stored
  as a new history item. Edited completion at line start can be stored.
* Tabs can delimit a filter; prefer spaces in authored CP/M text.
* Ctrl+Shift+Backspace deletes the selected recalled entry.
* Separate editable keyword lists remain planned, not implemented.

The histories live in `++A0:7XTGVTRM.BUF++` and are saved after a quiet
period or by `++SYNC++`. Boot can recover from verified alternate generations.
Do not edit these checksummed files as ordinary text; preserve backups and
use checksum-aware tooling for repairs. The transaction and core ownership
are described in the link:technical-reference-guide.adoc#configuration-and-persistence[Technical Reference Guide].

Profile selection remains active until changed during the running session, but the RunCPM CCP prompt (`++A0>++`, `++AF>++`, `++A>++`, and similar) silently uses effective bank `++#0++` so shell commands do not pollute an application history. The selected bank is restored when the application prompt returns. This is not an INI-persisted bank selection. Active-line and cursor colors follow the selected palette unless explicitly overridden by the profile. The built-in PAPER defaults are pale green and mid-green, not fixed colors in every theme.

`++## RAW++` bypasses profile/history translation for direct control of an application. It is the escape hatch for diagnostic tools and unusual full screen programs. The normal terminal mode is preferable for ordinary command work.

[[editing-details]]
== Editing details

The normal terminal is a line model, not a generic editor. It records a line when Return completes it and can recall it into line-oriented interpreters.

MBASIC needs special handling because its `++EDIT n++` command enters a modal editor. The compiled MBASIC/VTESTS profiles select `mbasic_native`; the current INI can instead select `local_compose`, which provides local left/right/home/end, insert/delete/backspace and submission handling. These are different adapter choices, not an automatic generic full-screen editor. Native MBASIC EDIT operations include rubout/space movement, `L`, `X Esc` and `1D`; keep the profile paired with the intended adapter.

BBC BASIC uses its visible `++>++` prompt as the active screen line. It tracks ordinary line edits and safely retypes recalled history using the profile's configured clear/retype sequence. This is why its controls differ from MBASIC's.

[#7xtgv-cpm-commands-and-user-areas]
== 7xtgv CP/M commands and user areas

The original RunCPM `++VOL [drive]++` command reads the first printable line
of `++INFO.TXT++` in each existing user area on that drive. It does not read
the `++.7XF++` catalog files used by the extensions below.

This compact reference covers files added or adapted by this project. It does not repeat ordinary CP/M programs and imported language packages; use `++?++` at the CCP prompt for the internal CCP command list. An A0 command is found from other user areas by this RunCPM CCP, while files it creates normally belong to the current DU (for example `++A6>++`).

The internal `++7XF++` command selects the named prompt (`++/a/mbasic>++`, or `++/a/7>++` without an alias). `++7XF DD++` (the boot default) displays decimal user numbers (`++A15>++`), `++7XF DH++` uses hexadecimal (`++AF>++`), `++7XF D++` shows only the drive (`++A>++`), and `++7XF DN++` selects the named prompt. Area names are at most eight characters. The prompt style lives in memory until RunCPM restarts. There is no `++7XF.COM++` file to install.

The built-in `++LS++`/`++LL++` catalog commands list the current DU; `++LS /++` lists nonempty drives with summed host-file sizes, and `++LS /A++` lists existing areas on drive A with their own totals. Short rows show comma-grouped KiB (`++k++`), rounded up, not FAT-cluster allocation. File rows omit descriptions in this short form. `++LS -L++` adds exact host-file bytes, logical 128-byte record counts, rounded-up 32-KiB DEXT equivalents, and per-file descriptions. `++LL++` is exactly `++LS -L++`. The record and DEXT columns are also summed per file for drive and area totals; DEXT is an estimate, not the count of actual CP/M directory entries or FAT allocation units. Long drive and area descriptions appear on a second line, indented by one eight-column tab; the current-area heading has its description in both forms. Names display the case stored in `++DIR.7XF++` while lookup remains case-insensitive. `++LS /A/MBASIC/*.BAS++` and `++LS A7:*.BAS++` filter files using CP/M `++*++`/`++?++` wildcards. `++LS -O PANE.7XF /A/MBASIC++` replaces that file in the current DU with one listing, sends no listing to the terminal, and suppresses `++PAGE++` pauses only for that invocation. It does not capture `++CD++`, other built-ins, or `.COM` output. All `++LS++`/`++LL++` rows clip at the selected logical terminal width. `++PAGE 0++` disables ordinary pauses in `++LS++`, `++LL++`, and `++?++`. `++LS ..++` aliases `++LS /++`.

When a pattern has no dot, a stem `++*++` also spans any extension: `++LS *++` lists every file, and `++LS VT*++` includes `++VTESTS.BAS++` and `++VTPAL.BAS++`. The same applies after an area path or `++A7:++`; an explicit dot keeps its normal 8.3-field meaning. CP/M 2.2 records do not carry a general exact final-byte length. The byte count in `++LS -L++` is the underlying RunCPM FAT file length; a file written through CP/M record I/O may already have been rounded to 128 bytes. A text Ctrl-Z is an application convention, not a reliable binary length marker.

Bare `++CD++` reports both numeric DU and its named view, for example `++A7: /a/mbasic++`. `++CD MBASIC++` and `++CD /A/MBASIC++` select an area; `++CD /A++` returns to the last area selected on drive A. These slash paths name flat CP/M drive/user areas, not subdirectories. Each area's `++DIR.7XF++` stores a 12-character left-aligned area/file key, one space, then a description; its first key is the area name. `++A0:VOL.7XF++` stores drive letters in column 1, one space, and descriptions from column 3. `++A0:DRV.7XF++` stores the last selected area per drive as one `++/d/name++` line per drive. `++CD++` reloads this file before selection and saves it after a new explicit selection. The project `++cpmcard++` tree keeps these as CRLF text ending with Ctrl-Z.

[[shared-a0-commands]]
=== Shared A0 commands

[cols="1,1",options="header"]
|===

[[a7-visual-tests-and-dec-graphics]]
=== CARDMARK raw SD read diagnostic

`CARDMARK [CSD] [sectors [MHz [start-sector]]]` requires matching firmware
on our direct-SdFat/SPI targets: ES3_35, ES3_5, EP4_10, RP2_147, RP2_2 and
experimental EC6_147.
Desktop reports this raw-card diagnostic as unsupported. The former W535
SD_MMC alternate has been removed; all six current physical targets use SPI/SdFat.
Defaults: 1024 sectors, the configured operating SPI request, and
start sector 0. Sectors are 512 bytes; count range is 1..1048576 and requested
clock range is 1..60 MHz. Example: `CARDMARK 4096 50`.

Add `CSD` anywhere among the arguments for named CSD fields, for example
`CARDMARK 4096 50 CSD`. Matching is case-insensitive. The compact report orders
raw CID, decoded identity, raw CSD, capacity in whole MiB (rounded down, with
exact 512-byte sector count), and encoded speed. CMD6 checks High Speed support
where advertised; it does not select High Speed mode. An unsuccessful query
reports unknown support and does not prevent the raw read test.

Detailed decoding covers SD CSD v1.0 (SDSC) and v2.0 (SDHC/SDXC). CSD v3.0
(SDUC) is identified but not decoded or supported by this SdFat backend.
These are SD layouts, not MMC/eMMC layouts. See
link:../docs/261003-11%20CARDMARK%20CSD%20decoding%20and%20CMD6%20query.adoc[register decoding notes].

The native service reads reference data at requested 20 MHz and compares three
trial reads per batch at the selected clock. It reports card CID/CSD, capacity,
compared bytes and raw-read throughput, then restores the operating clock.
The ` ... ` hint appears before test reads and the result follows on that line.
Ctrl+Alt+C cancels in the integrated terminal build. It runs in ordinary writable
firmware too; CARDMARK itself uses only read operations. If clock restoration
fails, storage is stopped and a reset is required rather than returning to CP/M.

Clock values are requested, not measured. A PASS demonstrates read agreement
for the selected range, not write reliability or complete card qualification.
Use a backed-up/spare card for experimental clocks. Raw throughput is not the
same measurement as VTDRV's BDOS/file throughput. Detailed implementation and
results: link:../docs/261002-13%20Global%20SdFat%20SPI%20clock%20and%20CARDMARK%20preparation.adoc[CARDMARK checkpoint].

[[boot-autoexec-and-pending-submit-work]]
=== Boot, AUTOEXEC, and pending SUBMIT work

`++AUTOEXEC.TXT++` is a RunCPM convenience, not a standard CP/M 2.2 CCP command. It is a short first-boot command line at the SD-card filesystem root (outside every A0--AF DU). For deliberate startup, it can contain `++SUBMIT STARTUP++`, with ordinary `++STARTUP.SUB++` held in the intended CP/M DU.

`++SUBMIT++` builds the internal `++$$$.SUB++` queue. On boot the CCP can find such a pending queue and resume it; that is useful after interruption but is not a safe way to turn ordinary text prefixed with `++$++` into autorun. If an abandoned queue causes surprising commands after boot, switch to its DU and run `++UNSUB++`. A pending queue takes precedence over `++AUTOEXEC.TXT++`.

[[xterm256-graphics]]
== xterm256 graphics

`++Ctrl+] g++` or `++Alt+Shift+Backspace++` starts a local GCLS graphics layer. The extended private form is `++CSI >4;zoom;x;y v++`; `++zoom++` is 1…4 and `++x,y++` are physical pixel coordinates from the display's top-left corner, not logical text cells and not multiplied by zoom. The origin does not move with the gutter or viewport; samples at `++x=0++` may cover the gutter. Each source sample becomes a `++zoom × zoom++` RGB565 block, clipped at the physical client boundary. The next xterm256 indexed-color samples (`++CSI 38;5;<index>m++` plus byte values) are drawn directly on the TFT and are not mirrored to the PC. The normal terminal cell layer remains logically present and opaque text output can paint over the image. The first later terminal scroll retires the plot and restores the gutter without a full-screen clear. `++BROT_BS++` and `++BROT_PS++` demonstrate the compatible bare path from A6.

Use the supplied submit scripts after selecting A6:

[source,text]
----
A6>SUBMIT BROT_BS
A6>SUBMIT BROT_PS
----

The direct plot ends on SGR reset (`++CSI 0m++`). Rows used by status text and the active cursor are then repainted from terminal memory, including when the plot was launched by `++SUBMIT++`; the remaining graphics canvas stays visible. A normal `++CLS++` clears the terminal cells, while `++Ctrl+] r++` explicitly returns the screen to the normal terminal surface.

[[configuration-reference]]
== Configuration reference

`++A0:7XTGVTRM.INI++` is read once at firmware boot. Its `++[global]++` section holds the global exit/clear key policy, cursor blink, `++viewport_gutter_rgb++` (the always-present full-height display gutter), `++viewport_active_gutter_rgb++` (normally `++active_line++` when horizontal panning exists), and persisted `++backlight_level++`. The matching `++[display:HAL_ID]++` section holds boot `++view_zoom++` and the current per-zoom logical presets. Each `++[bankN]++` supports a name, `++on_select++`, `++exit_command++`, `++clear_command++`, key-first modifier bindings, history controls, active-line/cursor RGB values, and narrow editing options such as `++screen_line++`, `++line_prefix++`, `++activate_prefix++`, `++input_adapter++`, and `++history_retype_delay_ms++`.

Binding values are `++none++`, `++history_previous++`, `++history_next++`, `++send:<bytes>++`, or `++send_cancel:<bytes>++`. Escape notation accepts `++\e++`, `++\r++`, `++\n++`, `++\t++`, `++\\++`, `++\xNN++`, and `++\^X++` for an ASCII control character.

[[keyboard-overrides-in-7xtgvtrmini]]
=== Keyboard overrides in `++7XTGVTRM.INI++`

Put a binding under `++[global]++` to make it available in every profile, or under `++[bank0]++` … `++[bank9]++` for one selected application profile. A bank-specific binding wins over the global one; otherwise the profile's `++input=++` preset or the terminal's default applies. These banks are terminal profiles, *not* CP/M drives or user areas. Keep the section spelling `++[bankN]++` lowercase.

`++input=++` selects one of these keyboard-input presets. It is independent from `++mode=ansi|vt52++`, which selects the *output* interpretation:

[cols="1,1",options="header"]
|===
|`++input=++` value |Preset bindings
|`++custom++` |Retains the normal/default bindings of the selected profile; add or replace individual bindings explicitly.
|`++ansi++` |ANSI cursor/navigation sequences for arrows, Home/End, PgUp/PgDn, Insert/Delete, and their implemented Ctrl/Alt variants.
|`++vt52++` |Arrows only: `++Esc A++`, `++Esc B++`, `++Esc C++`, `++Esc D++`. Other navigation keys are unbound unless explicitly configured.
|`++wordstar++` |WordStar-style arrows `++^E/^X/^S/^D++`; Home/End `++^Q^S/^Q^D++`; PgUp/PgDn `++^R/^C++`; Insert `++^V++`; Delete `++^G++`.
|===

For every non-`++custom++` preset, `++Alt+Up++` and `++Alt+Down++` default to the profile history previous/next actions. An explicit profile or global key binding always wins. There are currently no `++input=adm3a++`, `++input=mz821++`, or `++input=fand++` presets: configure such applications with `++input=custom++` and specific bindings after their required input bytes are known.

`++input_adapter=none|mbasic_native|local_compose++` is separate again: it selects narrowly scoped local line-edit handling, not a terminal protocol. Likewise, `++## RAW++` is a temporary bypass of profile key translation rather than an `++input=++` preset.

[source,ini]
----
[global]
kp_decimal=send:.
f5_ctrl_shift=send:\eQ

[bank3]
f5_ctrl_shift=none
num1_shift=send:1
----

The left side is `++<key>[_ctrl][_shift][_alt]++`, with the base key first and modifier suffixes in exactly that order. Use `++f5_ctrl_shift_alt++`, not `++f5_alt_ctrl_shift++`; names are case-insensitive. `++_alt++` is intended for LAlt. RAlt/AltGr is reserved for the Czech layout's symbol entry, and is not a separate INI modifier.

[cols="1,1",options="header"]
|===
|Key group |Available base names
|Cursor and editing |`++left++`, `++right++`, `++up++`, `++down++`, `++home++`, `++end++`, `++insert++`, `++delete++`, `++page_up++`, `++page_down++`
|Common keys |`++backspace++`, `++escape++`, `++enter++`, `++space++`, `++f1++` … `++f12++`
|Main number row |`++num0++` … `++num9++` (separate from the keypad)
|Numeric keypad |`++kp_decimal++`, `++kp_delete++` (the latter is NumLock-off Delete)
|Czech physical positions |`++bs2++`, `++bs1++` before Backspace; `++p1++`, `++p2++` after P; `++l1++`, `++l2++`, `++l3++` after L; `++z1++` before Z; `++m1++`, `++m2++`, `++m3++` after M
|Letters |`++a++` … `++z++`, only with Ctrl or Alt; plain and Shift-only letters remain normal typing
|===

Any subset of the three modifier words is syntactically accepted for the non-letter names. Plain and Shift-only `++bs1++` and `++l3++` are deliberately excluded because these are dead-accent positions on the current Czech keyboard: their normal composition must continue to work. `++num1++` … `++num0++` send ASCII digits by default even when the unshifted Czech keycap produces `+++ěščřžýáíé++`; `++kp_decimal++` sends `++.++` by default even when the host emits `++,++`. Shifted main-row digits are separate names such as `++num1_shift++`.

The right side has five forms:

[cols="1,1",options="header"]
|===
|Value |Effect
|`++send:<bytes>++` |Send the specified bytes to CP/M.
|`++send_cancel:<bytes>++` |Send bytes and discard the current terminal history line.
|`++history_previous++` / `++history_next++` |Browse the effective history bank.
|`++none++` |Explicitly suppress that key.
|===

`++<bytes>++` may contain up to 16 decoded bytes; `++\e++` is Escape, `++\r++` is Return, and `++\xNN++` inserts a byte in hexadecimal. `++\^K++` sends Ctrl-K (0B); the backslash-caret consumes exactly one character. Thus `++\^K\^D++` sends two control bytes, while `++\^K^D++` sends Ctrl-K followed by printable `++^D++`. Bare `++^K++` stays printable. The full convention is `++\^@++` = NUL, `++\^A++` … `++\^Z++` = 01 … 1A (lowercase letters also accepted), `++\^[++` = Escape, `++\^\++` = 1C, `++\^]++` = 1D, `++\^^++` = 1E, `++\^_++` = 1F, and `++\^?++` = DEL. Invalid forms such as `++\^5++` are rejected; `++\e++` remains the clearer spelling for Escape in terminal sequences. Write comments on their own lines beginning with `++;++` or `++#++`—not after a binding value, where they would be read as part of that value. A duplicate key binding or an excess over 128 sparse overrides across the whole configuration reports a load error; the first accepted binding remains in effect.

The current source supports both control notation and full-byte `\xNN` values.
For example `send:\x81` encodes one byte, not a UTF-8 character. Use
`console_bits=8` for an application expecting bytes above 7F. The older
260920-1628 image predates control-caret notation; that is a historical
compatibility warning, not the current deployment state.

INI recognition and host delivery are distinct. The supplied Konsole/Kitty keymaps translate only physical combinations with a safe known fallback; terminal-owned shortcuts (for example Alt{plus}number profile selection and Ctrl{plus}Shift{plus}number backlight), ambiguous AltGr combinations, unmodified dead accents, and some less-tested punctuation combinations are left to the host. Konsole's key table does not encode left-versus-right Alt explicitly, and a desktop shortcut can consume a chord before this terminal sees it. In particular, a correctly spelled INI binding does not guarantee that every host keyboard will deliver that physical combination. Ordinary unbound keys retain their host output; pasted text is not remapped.

`++7XTGVTRM.INI++` accepts CR, LF or CR/LF lines and treats Ctrl{plus}Z
(`++1Ah++`) as logical end of file. It can be edited with a CP/M editor and
reloaded by `++REBOOT++`. Palette and brightness selections are saved lazily;
ordinary keyboard zoom, pan and `++VTZOOM++` are temporary and do *not*
rewrite boot `++view_zoom++`. Other settings and other display sections remain
user-authored. The host transfer tool's deliberate `++--cpm-text++` option
writes CR/LF plus Ctrl{plus}Z. Do not edit checksummed history files from
CP/M. The INI cache and save transaction are described in the
link:technical-reference-guide.adoc#configuration-and-persistence[Technical Reference Guide].

[[ini-diagnostics-and-syntax-limits]]
=== INI diagnostics and syntax limits

Boot continues after recoverable line errors and reports
`LOADED WITH ERRORS (n)`. The first ten bad lines are listed in this form:

[source,text]
----
  42: [bank3]: unknown_setting=value
----

Line numbers are one-based and right-aligned in four positions. The report
contains the section and source line, not an elaborate error explanation.
ANSI boot highlights each detail row with red paper; VT52 uses a `***` prefix.
The total can exceed the ten retained details. The same report is written to
`A0:7XTGVTRM.ERR` when storage permits, with CRLF and trailing Ctrl+Z. A clean
INI load removes a stale ERR file. If no INI is loaded, the banner reports
`COMPILED DEFAULTS`.

Use one setting per line and comments on separate lines. The line buffer holds
191 characters excluding its terminator; longer lines are diagnosed, not
silently accepted. Physical line breaks count even in comments. Ctrl+Z ends
the logical INI, so anything after it is not parsed.

For Boolean settings prefer `true` / `false`. The parser also accepts lowercase
`yes` / `no` and `1` / `0`; it does *not* accept `on` / `off`.
Ordinary setting names and enum values are case-sensitive; use the lowercase
spellings below. Key-chord names are case-insensitive. Global, palette and
display section recognition is case-insensitive, but keep `[bankN]` lowercase.

Duplicate explicit key bindings are errors; ordinary scalar settings are not
covered by that duplicate check. This is syntax validation, not a complete
logical validator: it cannot prove an application understands configured bytes
or that host shortcuts will reach the firmware.

events; the legacy name is not a reliable description of the physical chord.
These actions are processed before ordinary profile bindings. `none` disables
the corresponding policy entry. There is no implemented `boot_ansi` setting;
adding that earlier proposed name causes a load error.

After the first themed frame is drawn/flushed, `crt_rampup_ms` gradually raises
the backlight from OFF to `backlight_level` (default 16). It applies to all
palettes, not only GREEN/AMBER. For example:

[source,ini]
----
[global]
crt_rampup_ms=1500
----

There are 32 logical states: OFF=0, intermediate PWM=1..30, full ON=31.
Each target's HAL maps these states to its own duty values; level 1 is a
per-display lowest usable visible level, not a common brightness percentage.
The ramp traverses logical levels over the configured duration, so it is a
stepped effect, not a calibrated linear-light fade. Dated visual tuning and
deployment evidence remains in
link:../docs/260925-01%20RP2_2%20backlight%20minimum%20duty%203%20trial.adoc[RP2_2 notes]
and link:../docs/260925-14%20RP2_147%20backlight%20minimum%20and%20HAL%20boot%20warning.adoc[RP2_147 notes].
Normal PgUp/PgDn adjustments stay within 1..31; from OFF they first restore
remembered brightness. Explicit brightness controls cancel an active ramp
immediately. Transient ramp levels never overwrite the saved target.
Private `CSI >63;32v` remains a legacy alias for full ON; 33/34 still mean
increase/decrease. No new INI setting is needed for ordinary immediate startup.

|`view_zoom` |1..4, the boot scale for 6x10 glyph cells. Temporary ZOOM/keyboard changes do not rewrite it.
|`zoom1_terminal` through `zoom4_terminal` |Current logical `COLSxROWS` presets. The boot scale selects one; `++VTZOOM n++` deliberately selects another. Ordinary keyboard zoom leaves the logical size alone. Odd column counts round down to even. Both dimensions must fit the HAL's logical backing limits.
|`render_flush_hz` |0..60; 0 removes the software flush interval. This is not the physical panel refresh rate.
|`rgb_refresh_hz` |Accepted compatibility placeholder only; physical RGB timing remains compile-time.
|===

A bank can override `zoom1_terminal` through `zoom4_terminal`. These coupled
presets remain available for deliberate selection and may later become
independent of physical zoom. Logical width or height may exceed the physical
view. Ctrl{plus}Shift arrows pan by axis; Home/End scan the calculated views
in row-major order. Positions include both exact edges and are recalculated
for the current zoom and logical geometry. The PC mirror still represents
the complete logical terminal.
Bank overrides are shared across displays too: an oversized override is reported
and rejected on a smaller HAL, which retains its display geometry. Omitted display
settings retain each HAL's defaults, even when multiple HALs share one profile ID.
Brightness, palette selection and CRT ramp time remain global, not per-display.
See link:../docs/260924-13%20display%20profile%20selection%20and%20identity%20audit.adoc[selection, persistence and identity audit]
for the complete source-grounded flow and limitations.

[[palette-slots-and-ansi-color-mapping]]
=== Palette slots and ANSI color mapping

`[palette0]` through `[palette9]` are in this same INI. Each slot starts from
built-in PAPER defaults independently; missing entries in palette 1 do not
inherit edited palette 0. `VTPAL n` selects a slot and persists `mode_palette`.
Editing the RGB definitions still requires reloading at boot. A theme change
repaints text/UI and can retire a retained graphics image; xterm256 plot RGB
conversion itself does not use these editable ink slots.

[cols="2,3",options="header"]
|===
|Palette key |Value
|`paper0` through `paper3` |Decimal `R,G,B`, each component 0..255.
|`ink00` through `ink15` |Same RGB syntax; ink names require two digits.
|`active_line_rgb`, `cursor_rgb`, `viewport_gutter_rgb` |Same RGB syntax; additional UI roles, not extra native papers.
|`viewport_active_gutter_rgb` |RGB or `active_line`.
|===

Use `palette` on bank active-line/cursor and global gutter keys to inherit;
explicit RGB overrides win. `RGB565`, hexadecimal color literals and symbolic
color names are not accepted INI color values.

[cols="1,2,1,1",options="header"]
|===
|ANSI color |ANSI name |Normal ink slot |ALT ink slot
|0 |Black / default ink |00 |08
|1 |Red |01 |09
|2 |Green |02 |10
|3 |Yellow |07 |15
|4 |Blue |03 |11
|5 |Magenta |06 |14
|6 |Cyan |05 |13
|7 |White / silver |04 |12
|===

SGR 30..37 selects the normal set; 90..97 selects the ALT set. SGR 1 (bold)
selects the ALT variant by bit 3, not a thicker glyph. It need not be brighter:
the palette chooses the contrast appropriate to paper or dark backgrounds.
SGR 22 clears bold; SGR 0 resets rendition. Other supported text attributes
include underline (4/24), blink (5/25) and reverse (7/27).

ANSI backgrounds 40..47 map to paper slots `2,1,2,2,3,1,2,0` respectively;
100..107 use the same mapping. In particular ANSI black background does not
mean a literal black RGB paper in this compact text renderer. SGR 49 resets to
paper0. This four-paper policy is intentional current behavior, not unrestricted
ANSI background-color fidelity or the future four-plane native specification.
Indexed SGR 38/48 colors operate on the active plot canvas, not as arbitrary
256-color text cells. Truecolor SGR sequences are consumed but not applied.

For complete example palettes and the comparison program see
link:../docs/260923-16%20palette%20presets%20manual%20and%20test%20notes.adoc[palette configuration notes]
and link:../docs/260923-18%20VTPAL%20BASIC%20palette%20comparison.adoc[VTPAL.BAS comparisons].
The maintained BASIC source mirror is in A7; inspect a live card before
asserting which copy is installed there.
Current configured presets are 0 PAPER, 1 GREEN, 2 AMBER, 3 BW, 4 PLASMA,
5 VFD. VTPAL.BAS still has obsolete optional-level help for slots 3..6 and
older INK/SILVER labels; that help is not the current preset definition.
Internal ink order is implicit, red, green, blue, shade, cyan, magenta, yellow
(`irgbscmy`), with ALT slots 8..15 (`IRGBSCMY`). This does not change ANSI order.

[[zip-transfer-and-extraction]]
=== ZIP transfer and extraction

Transfer ZIPs as binary, never with `--cpm-text`. The separately installed
`A0:UNZIP157.COM` supports Linux Deflate ZIPs; the old local UNZIP 1.8 does not.
Keep uppercase 8.3 member names. Linux packing example:

[source,sh]
----
zip -9 -j VTFILES.ZIP FILE.INI
----

After transferring the archive, CP/M extraction is:

[source,text]
----
UNZIP157 VTFILES.ZIP A:
----

The destination enables extraction; without it the program only lists/checks.
Use a disposable user area or nonconflicting names for initial tests.
Automatic compression in the mirror is not implemented. See
link:../docs/260923-20%20CP-M%20UNZIP%20compatibility%20and%20download.adoc[the compatibility test and download record].
