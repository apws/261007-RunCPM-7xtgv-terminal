[[_runcpm_and_internal_ccp_fork_boundary]]
=== RunCPM and internal CCP fork boundary

The early demos, RunCPM prototype and display bring-up tools moved to
link:../src/legacy/README.adoc[`src/legacy/`] on 261007. Historical notes
may still quote their original `src/` paths; the active terminal and desktop
remain under `src/RunCPM_7xtgv-terminal/`.

[[_implemented_separation]]
==== Implemented separation

* `ccp.h` is the recovered internal CCP; `ccp7xf.h` is the extended product
  variant. The sketch selects the latter with `XTGV_CCP_7XF=1`, which requires
  `CCP_INTERNAL`. This is compile-time selection, not a guest COM replacement.
* `ccp7xf.h` owns prompt styles, its command buffer, 7XF/LS/LL/CD dispatch,
  extended help/paging and product prompt-placement behaviour.
* `ccp_catalog.h` supplies catalog/path parsing, formatting and one-shot
  `LS -O` capture. It still calls CCP/disk helpers and shares current DU state;
  it is not a standalone portable filesystem library.
* Both CCP variants retain `VOL` reading `INFO.TXT`. The 7XF catalogs
  `DIR.7XF`, `VOL.7XF` and `DRV.7XF` are separate conventions over flat DUs,
  not native CP/M directories.
* Long listings use the underlying host-file length. That exact-byte facility
  is not universally available to ordinary CP/M software.

[[_limits_of_an_upstream_port]]
==== Limits of an upstream port

The split is implemented; upstream adoption remains a separate project.

* Compare against the recovered baseline and a deliberately selected upstream
  revision, not simply the oldest demo tree under `src/legacy/`.
* Review whether catalog/metadata access and command registration need narrower
  interfaces. Existing helper extraction does not establish upstream acceptance.
* Test generic fixes against upstream behaviour, and test product changes
  through the Arduino abstraction/desktop as well as the POSIX comparator.
* External CP/M applications still run in the TPA and do not inherit C++ CCP
  internals. `$$$.SUB` is a CP/M record queue, not a process-return trampoline.

See the dated
link:../docs/260926-12%20terminal%20guide%20split%20and%20ownership%20plan.adoc[split plan]
and the link:../docs/260926-23%20XC%20commander%20return%20path%20and%207XF%20output%20boundary.adoc[CCP handoff notes]
for design context; do not treat proposed commander behavior as implemented.

[[_runtime_ownership_and_synchronization]]
=== Runtime ownership and synchronization

* RP2350 core 1 owns CP/M and SD; core 0 owns terminal, display and USB.
  The terminal side must not access the SD filesystem directly.
* Console bytes cross fixed single-producer/single-consumer rings:
  4 KiB input, 16 KiB output. Replies use a separate 1 KiB staging queue
  and take priority over new keyboard input.
* Full output queues backpressure CP/M instead of silently dropping bytes.
  The terminal continues draining output while input is full.
* USB writes stay on the terminal core. Startup waits for display initialization
  before CP/M begins.
* Other targets keep the logical ownership, with different task/core primitives.

[[_forced_com_return]]
==== Forced COM return

* Ctrl+Alt+C is a versioned host key event consumed before profile bindings,
  also in RAW mode. The terminal task only posts an atomic request.
* The RunCPM owner accepts it at a Z80 instruction polling boundary or after
  a blocked BIOS/BDOS console read wakes, then sets `++STATUS_RESTART++`.
  It does not change CPU status from the terminal task or interrupt SD mid-call.
* The owner discards queued guest bytes, deletes the exact `+++$$$.SUB+++`
  queue to cancel the remaining batch, and prints `++FORCED WARM RETURN++`.
  If deletion fails, it warns and suppresses replay in RAM for this session;
  the file may still need removal before a cold reset.
* This is not an application-safe file close: open guest files and unsaved
  editor data can be lost. A hung MCU, terminal task or storage call still
  requires physical recovery.

The link:../docs/260928-11%20forced%20COM%20warm%20return%20implementation%20checkpoint.adoc[implementation checkpoint]
maps every source touch point and records what still needs a device test.
The link:../docs/260928-13%20forced%20COM%20return%20GCLS%20abort%20regression.adoc[GCLS abort follow-up]
records the hardware-discovered parser cleanup defect and its first flashed
fix. The link:../docs/260928-18%20retained%20GCLS%20return%20and%20RP2_147%20optimization%20trials.adoc[retained-plot follow-up]
records the later image-preserving path and O2/O3 trial builds.

[[_terminal_state_geometry_and_hal]]
=== Terminal state and geometry

[[_cells_viewport_and_plot_layer]]
==== Cells, viewport and plot layer

* The logical cell array spans the CP/M terminal dimensions. The TFT or SDL
  display renders the visible rectangle; the mirror uses the complete array.
* Zoom changes 6x10 glyph scale, not logical CP/M geometry. Pan positions use
  logical/visible sizes and include both exact edges.
* Moving the viewport does not reconfigure a running full-screen application.
  Gutter and active-line rendering are composited around that viewport.
* Direct xterm256 samples use a retained physical-pixel plot layer, not cells.
  Later text can paint over it; a terminal scroll retires it.
* Current cells plus sidecar attributes are *not* the future native 7xtgv
  four-plane format.

[[trg-interfaces-and-persistence]]
== 2. Interfaces and persistence

[[configuration-and-persistence]]
=== Configuration and persistence

All application banks use identical neutral initialization; only their generic
`Bank N` labels differ. Application key maps, adapters, commands, prompt tracking
and history timing are defined in INI. `ccp_bank=0..9|none` explicitly selects the
shell profile; its compiled fallback is disabled. Runtime CCP routing, native
recall and the 125-character CCP submission boundary use that assignment.
Global fallbacks apply uniformly, display fallbacks come from the selected HAL,
and each palette slot independently starts with the same PAPER theme. Explicit
`input=ansi|vt52|wordstar` presets retain protocol mappings without app identities.

`++A0:7XTGVTRM.INI++` is parsed at boot. The text is held in memory for
targeted edits; palette and backlight choices mark their fields dirty and a
later owner-side transaction saves them. Normal keyboard zoom/pan and
temporary `++VTZOOM++` do *not* mark boot `++view_zoom++` dirty. Explicit
`++SYNC++` forces pending settings and history transactions before likely
reset or long plot work. Guest writes to an INI should not be overwritten
from a stale cache: review the cache's changed-file/collision path when
altering storage code. Keep storage operations on the RunCPM/SD owner.

Ten history banks are stored in `cpm(A0)` `++7XTGVTRM.BUF++`. After two seconds
without a history generation change (or an explicit forced save), the owner
writes and verifies `7XTGVTRM.NEW`, then rotates the old BUF through
`7XTGVTRM.BAK`. Successful replacement removes BAK; it is a transaction
fallback, not a retained archive. Boot tries valid BUF, then NEW, then BAK,
in that order, not by filesystem timestamp. Completed v2 files carry CRC-32;
legacy v1 files remain readable. These are not plain text files to edit
with a CP/M editor. The exact syntax, persistence and boot diagnostics are
in the link:03-RG-reference-guide.adoc#configuration-reference[INI reference];
source-level tests are `++tests/test_ini_runtime.cpp++`,
`++tests/test_ini_text.cpp++` and `++tests/test_ini_storage.py++`.

`LineHistory::MaxEntry` limits every retained entry to 79 text characters.
The runtime load buffer holds 80 characters including the leading `>` marker;
new saves use the same bound, excluding the newline. Older longer records are
consumed through their newline and clipped in memory. Their full original bytes
remain on disk until a later history save replaces the file. `MaxLine` remains
127 for active input/editing and CCP auto-submission tracking. The shorter entry
arrays save 48,000 bytes across ten 100-entry banks. Runtime tests cover the
78/79-character boundary, oversized imports, next-record alignment and CRC.

INI transactions use distinct `7XTCFG.NEW` / `7XTCFG.BAK` names so the FAT
8.3 namespace cannot collide with history transactions. Source ownership and
recovery order are in `src/terminal/terminal_persistence.h`; archive wanted
history separately rather than assuming a successful save keeps BAK.

History submission is independent of how a line was composed: typed input,
filtered recall and a completed token inside a prefix all follow `store()`.
Empty/single-character lines and byte-exact adjacent duplicates are excluded.
Only a real store/delete changes the history generation; browsing alone does
not create a pending save. `line_history.h` owns these rules. The focused
terminal/runtime tests and `desktop/tests/history_recall.py` cover this boundary.
Separate keyword lists must not use history-suppression flags as a substitute
for their own source-selection state.
See the link:../docs/261009-0251%20DONE%20Filtered%20recall%20returns%20to%20normal%20history.adoc[history fix, persistence test and keyword follow-up].

[[private-protocol-boundaries]]
=== Private protocol boundaries

In this table `++CSI++` is `++ESC[++`, `++DCS++` is `++ESC P++`, and
`++ST++` is `++ESC \\++`. These are *7xtgv-private* controls, not standard
VT100 commands. User commands and shortcuts are documented in the
link:03-RG-reference-guide.adoc[Reference Guide]. Guest-output private controls
validate argument count/range and ignore invalid requests. Host keyboard
events use a separate decoder; unrecognized/invalid input can fall through
as guest bytes rather than being silently discarded. Host-only output events
must be removed from displayed text. A guest application must not assume that a
logical-size change notifies other CP/M applications.

[cols="2,2,3",options="header"]
|===
|Input/event |Direction |Contract
|`++CSI >62v++` |Host to firmware |Request full PC mirror snapshot; also asks for host identity. Firmware replies `++DCS 7xtgv-id;1;<target>;<build> ST++` out of band. Older firmware may consume the query without identity.
|`++CSI >64v++` |Guest to host via firmware |REFLASH capability request. Firmware forwards this exact event separately from reconstructed text; host dispatcher may act only when configured.
|`++CSI >72v++` |Guest to firmware |VTINFO query. Reply is bounded version-1 `++DCS 7xtgv-info;1;... ST++`: display ID, exact target/build, panel pixels, zoom, logical and visible dimensions, column/row pan offsets, bank, then four resolved preset sizes.
|`++CSI >73;n v++` |Guest to firmware |Load preset `++n++` (1..4); `++n=0++` restores boot view. `++CSI >73;n;cols;rows v++` selects temporary geometry, with even columns and bounds checked.
|`++CSI >68;n v++`, `++CSI >69;n v++` |Guest to firmware |Temporary physical zoom 1..4; palette slot 0..9. Palette selection is lazily saved.
|`++CSI >63;n v++` |Host or guest to firmware |Backlight logical state: 0 OFF, 1..31 visible, legacy 32 full ON; 33/34 step up/down. HAL maps states to duty values.
|`++CSI >4[;zoom;x;y]v++` |Guest to firmware |Arm GCLS plot at physical origin, zoom 1..4. Indexed xterm256 samples follow; SGR reset ends the plot transaction.
|`++CSI >70;1;base;mods;fallback-DDD...v++` |Host to firmware |Versioned keyboard event; numeric key ID and modifier bits plus decimal fallback bytes. See `++key_chords.h++` and `++terminal.py++` for the exact generated map.
|===

Profile/history and pan shortcuts also use private host-to-firmware controls
(`++CSI >10..17v++`, `++>20..61v++`, `++>65..67v++`, `++>71;0/1v++`). Their
user-facing meaning is in the key table; the source parser is authoritative
for the byte dispatch. Transfer helpers use their own validated record stream;
see link:../src/RunCPM_7xtgv-terminal/tools/cpm-transfer/README.md[transfer protocol]
and its tests before changing either end. Reconstructing the mirror and
serializing an out-of-band event must never interleave inside one partial
mirror update.

[[_reconstructed_mirror_and_byte_ownership]]
=== Reconstructed mirror and byte ownership

[source,text]
----
CP/M + BDOS + SD owner  --output ring-->  parser/cells --> TFT viewport
        ^                                      |
        |                                      +--> reconstructed full-screen mirror --> USB
        +--input/reply rings<-- keyboard/profile routing <-- host bridge
----

The mirror is *reconstructed* ANSI, not original guest bytes. It snapshots
rows into a bounded output buffer and coalesces when USB is slow. On connect
or explicit refresh it sends the complete logical screen. A mirror refresh
does not itself clear a retained TFT plot. Host serial ownership is singular:
the shared tmux session runs one bridge; another serial client must not read
in parallel. This reconstructed path is why ordinary XMODEM is not binary
safe. VTPUT/VTGET use a separate text-safe protocol and explicit checks.

[[trg-platforms-and-integration]]
== 3. Platforms and integration

[[_board_definition_and_runtime_selection]]
=== Board definition and runtime selection

Each module now has one complete, uniformly sectioned header under
`++hardware/arduino_7xtgv/boards/++`: storage adapter and initialization,
display creation, physical backlight control, reboot and typed defaults.
`++board.h++` declares the operations and selects that header directly.
The sketch defines `++XTGV_HAL_IMPLEMENTATION++` once; terminal source
files call ordinary functions, without changing which core executes them.
`++display_policy.h++` exposes the selected defaults and small geometry
helpers. Terminal array bounds read the board's logical maximum fields;
`++runcpm-config.h++` selects product composition, not panel dimensions.

Integration uses positive `++XTGV_TERMINAL++` selection; serial-only builds
use value zero. The obsolete RUNCPM_HEADLESS flag is rejected with a migration
diagnostic. Added RunCPM hook names use XTGV_ and bind ordinary tagged helper
functions; inherited RunCPM interfaces retain their original names.
The optional seams are XTGV_ABORT_REQUESTED, XTGV_Z80RUN_ATTRIBUTES,
XTGV_MODIFIED_FILE_CLOSED and XTGV_CONFIG_GUEST_IDLE. CPU polling remains
absent without its hook and otherwise checks every 65,536 instructions.
See link:../docs/261001-2317%20XTGV%20integration%20naming%20and%20positive%20build%20guards.adoc[naming and composition checkpoint].

Host target JSON supplies upload/port metadata and the *exact* target name.
These are related but distinct selectors: a shared display ID intentionally
shares an INI section, while firmware upload identity must match the exact
target. Any port must verify compiled bounds, defaults and resolved
`++VTINFO++` together. Physical backlight tables and output live in each
board; logical fading remains terminal behavior. See the
link:../docs/260924-13%20display%20profile%20selection%20and%20identity%20audit.adoc[identity audit]
and link:../docs/261001-1322%20HAL%20challenge%20and%20readable%20board%20consolidation.adoc[HAL design correction].
Use the dated build/acceptance records for evidence on a particular target;
the HAL structure alone does not establish physical qualification.

[[_single_core_freertos_and_shared_spi]]
=== Single-core FreeRTOS and shared SPI

EC6_147 experimentally runs the same two owners as separate FreeRTOS tasks
on one application CPU. They are concurrent by preemption/time slicing, not
simultaneously executing. Blocking queue waits and periodic one-tick delays
allow the other task and the idle task to run. This does not use the C6
low-power processor as a second Arduino core. Initial CPU and verified disk
tests work; other single-core families such as C5 remain separate, untested ports.

The bus lock is not automatic protection supplied by scheduling. In our
installed Arduino-ESP32 3.1.0, SPIClass::beginTransaction takes a FreeRTOS
mutex and endTransaction releases it (HAL locks must remain enabled).
EC6_147 explicitly gives Arduino_HWSPI and SdFat the *same SPIClass object*,
uses shared-interface/SHARED_SPI mode, and lets both drivers deselect their
device before releasing the transaction. A competing task blocks on that
mutex rather than changing SPI mode/clock or asserting its CS mid-transfer.

FreeRTOS supplies the mutex and waiting mechanism; Arduino SPI uses it;
our HAL connects both clients to it. Arbitrary GPIO/direct-register SPI access,
an unrelated SPI wrapper, or a caller omitting transactions is not protected
by this arrangement. Task priorities are not a replacement for mutual exclusion.
Protecting SPI also does not synchronize filesystem objects or terminal state:
their existing single-task ownership and queues remain required. Terminal
INI/history saves are requests serviced by the RunCPM/storage owner, not a
second task independently writing the card.

See link:../docs/261004-1057%20EC6_147%20experimental%20HAL%20implementation.adoc[C6 implementation and first hardware results]
and link:../docs/261004-0030%20ESP32-C6%20single-core%20integrated%20runtime%20feasibility.adoc[feasibility notes].

[[_esp32_p4_memory_and_build_settings]]
=== ESP32-P4 memory and build settings

The link:../docs/261002-12%20SdFat%20buffer%20transfers%20and%20SPI%20clock%20audit.adoc[SdFat and SPI audit]
consolidates the RP2350/ESP32 buffer-transfer difference, measured P4 gains,
requested-versus-actual clock caveats, divider tables and forced-read-only
test-build boundary. It distinguishes source findings from hardware evidence.

The JC8012P4A1C port uses in-package HEX-SPI PSRAM, a two-level cache
architecture and separate flash/PSRAM buses. In-package PSRAM is not internal
SRAM. CPU1 Z80run is placed in IRAM; execution of ordinary code from PSRAM
is supported by the chip/SDK but not enabled in our build.

The link:../docs/261002-10%20P4%20memory%20caches%20and%20PSRAM%20execution.adoc[P4 memory reference]
records current cache/bus settings, comparison with S3, the low/high SRAM

link:../docs/261002-10%20P4%20whole-build%20Os%20O2%20O3%20comparison.adoc[Os/O2/O3 comparison]
lists ELF placement and full size statistics. Arduino's 6% globals summary
omits a DRAM bank; it must not be interpreted as actual free internal heap.

[[_corrected_automatic_boot_z80_clock_estimate]]
=== Corrected automatic boot Z80 clock estimate

The automatic boot speed test is active: the sketch includes
`cpu_mhz_coorect.h` (intentional filename spelling) and calls
`xtgvZ80estimateClock()`. This restored the test in place of the former
`Run VTCPU.COM for active/quiet Z80 speed` advice. The inherited
`cpu_mhz.h` remains unchanged; we use a separate corrected copy, not the
original estimate and not a reverted correction.

* The original accounting assigned seven T-states to `LD A,B`, `LD A,D`
  and `HALT`, instead of four. The corrected Arduino test totals
  *13,015,509 T-states*, not 14,517,012; the old numerator inflated the
  reported clock by approximately 11.5%.
* Test bytes, loop counts and CPU resets are retained. The displayed value
  is an *estimated emulated Z80 rate*, not the MCU/host clock. Timing uses
  whole milliseconds and output uses integer MHz, so short desktop runs
  are especially sensitive to timing quantization.
* The test overwrites guest RAM starting at address zero and belongs only
  at boot. It is not a safe in-session replacement for `VTCPU.COM`.
* `VTCPU.COM` remains the active/quiet comparison tool. Boot display/startup
  conditions differ, so its result need not equal a quiet VTCPU result.
* On ESP32 the test executes the same HAL-attributed CPU1 `Z80run` dispatcher.
  Its short timing/printing wrapper does not need a separate `IRAM_ATTR`.

See link:../docs/261003-1445%20Corrected%20boot%20Z80%20clock%20estimate.adoc[261003-1445 correction record]
and link:../src/RunCPM_7xtgv-terminal/cpu_mhz_coorect.h[current corrected implementation].
This is a local, identifiable correction to the recovered-era integration;
it does not imply a newer upstream core was imported.

[[trg-development-and-verification]]
== 4. Development and verification

[[_build_upload_and_test_boundary]]
=== Build, upload and test boundary

See the link:01-BG-build-guide.adoc[Build Guide] for prerequisites,
installation commands, working versions and unverified fresh-machine steps.

`++tools/reflash.py --target TARGET --build-only++` stages a target-specific
candidate under `++build/RunCPM_7xtgv-terminal/TARGET/new/++`; staging alone
does not flash or promote it. Select the exact target in host configuration.
The uploader queries compiled firmware identity and blocks a reported
mismatch. An unidentified older firmware needs a one-shot, explicitly named
recovery allowance, never a persistent automatic bypass. RP2350 boards use
manual BOOTSEL/UF2 rather than an assumed auto-reset. The POSIX RunCPM build
tests CP/M behavior but cannot validate TFT timing, SD bus, duty curves or
hardware-specific rendering. Hardware acceptance is recorded separately in
the feature ledger and dated reports.

[[_host_tests_and_direct_mirror_entry_point]]
==== Host tests and direct mirror entry point

Run the host-side checks from the main project directory:

[source,sh]
----
cd src/RunCPM_7xtgv-terminal
python3 -m unittest discover -s tests -p 'test_*.py' -v
----

These checks have their own prerequisites and are not proof of physical-board
acceptance. For real-board desktop validation, see the
link:../src/RunCPM_7xtgv-terminal/desktop/README.adoc[desktop tests and launch guide].

For the PC keyboard and complete logical-screen mirror, the low-level entry
point from the same project directory is:

[source,sh]
----
python3 tools/terminal.py
----

Use the per-target `mirror.sh` shortcut for normal hardware sessions; ensure
no other process owns the serial port before a direct launch. Press `Ctrl+]`,
then `q`, to leave the hardware terminal without rebooting CP/M. Closing a
desktop session's owning mirror instead stops its emulator.
See the link:../src/RunCPM_7xtgv-terminal/README.md[main project documentation],
link:../src/RunCPM_7xtgv-terminal/VALIDATION.md[validation record], and
link:../cpmcard/README.adoc[CP/M user-area map] for details.

[[terminal-compatibility-test-notes]]
=== RunCPM, z80pack, RomWBW and terminal compatibility checks

The historical
link:../docs/261005-7xtgv-runcpm-z80pack-romwbw-terminal-notes.adoc[261005 RunCPM / z80pack / RomWBW terminal notes]
records the architecture discussion and useful test proposals:

* Separate the guest CPU/OS environment from the console transport and terminal
  parser/renderer. A console adapter does not by itself emulate a video chip.
* Its RomWBW CIO/VDA discussion and comparisons with other projects are research
  context, not delivered RunCPM integration or freshly verified upstream status.
* The proposed four-byte native cell format remains a design proposal, not the
  current terminal buffer ABI.
* Sections 17--19 and 22 propose explicit DECSTBM/DECOM checks: protected header
  and footer, forward/reverse scrolling, origin-relative addressing, clamping,
  insert/delete lines and restoration of whole-screen scrolling.

The follow-up
link:../docs/261007-1214%20DONE%20VTESTS%20legacy%20and%20scroll%20checks.adoc[VTESTS review and desktop checks]
implements practical tests now maintained in `7xtgv(C1)` at
`cpmcard/C/1/VTESTS.BAS`:

* *3*: independent bold, underline, blink and reverse samples with selective
  attribute-off controls; only the blink sample should disappear.
* *5*: VT52 direct addressing, four cursor directions, erase-line/erase-display,
  the implemented F/G graphics mapping, and return to ANSI.
* *7*: combined ANSI samples followed by a steady, unadorned DEC frame.
* *9*: five scrolling-region stages; select *80x24 logical geometry* first.
  Small physical panels may need panning; their visible viewport is not the
  logical scrolling boundary.

The quiet SDL test runs the real MBASIC guest, production Arduino abstraction,
terminal and Arduino_GFX on disposable host-card directories. Separate renderer
tests verify exact cell movements and blink/reverse pixels. These checks are
not full VT52/VT100 certification, all-glyph coverage, or physical-panel timing
qualification. The older sketch `tests/VTESTS.BAS` remains a historical fixture.

[[_current_findings_and_developer_reading_map]]
=== Current findings and developer reading map

The current desktop execution plan is
link:../docs/261006-0935%20PLAN%20Desktop%20runtime%20using%20existing%20board%20HALs.adoc[261006 PLAN: real-board HAL reuse and desktop runtime].
It supersedes the standalone SDL board and SDL keyboard proposals: select a
real board, retain its INI/display policy, use the existing mirror and an
output-only SDL presenter. Canonical CP/M names stay uppercase; desktop
CARDMARK is unsupported. See link:../docs/README.adoc[CHAT/PLAN/DONE navigation].

The Linux desktop implementation now builds all six real-board selections:
original Arduino sketch/abstraction/7XF, real GFX Canvas, output-only SDL,
existing mirror over explicit PTY, host SD/File adapter and cooperative quit/reboot.
The desktop uses a RunCPM/storage worker and a terminal/SDL main thread. Desktop
drawing completes all dirty visible cells per frame at `render_flush_hz`;
queued output and mirror work run without inter-batch sleeps, while idle/deadline
polling yields CPU. Physical-board budgets and task scheduling are unchanged.
The desktop host-storage adapter retains at most eight idle native backing
descriptors to reduce repeated file-open costs. Logical closes still flush writes;
fresh logical streams discard old read buffers, and reuse verifies file identity.
Path containment checks remain. This is separate from physical-board SdFat; see
link:../docs/261010-2330%20DONE%20Desktop%20retained%20file%20handles%20design%20and%20validation.adoc[retained-handle design, validation and host coordination limits].

and link:../src/RunCPM_7xtgv-terminal/desktop/README.adoc[build/launch instructions].
Normal card-root runs can write INI/history and guest files. Desktop sessions
are separate from hardware; REFLASH cannot invoke its uploader. Eight tests per
board and EP4 UBSan pass; complete visual/fault-recovery, fresh-OS and other-OS
qualification remain pending. The obsolete W535 SD_MMC alternate was removed.

[[_feature_registry]]
=== Feature registry

link:../docs/features.tsv[`docs/features.tsv`] is the canonical ASCII feature
store; link:../docs/FEATURES.adoc[`docs/FEATURES.adoc`] is its human ledger plus
hand-written status and evidence notes. From the repository root, validate,
query, or regenerate it with:

[source,sh]
----
python3 src/feature_registry.py check
python3 src/feature_registry.py report --format text \
  --fields group,idea_date,state,title --sort group,idea_date,title
python3 src/feature_registry.py report --format asciidoc \
  --where group=INP --fields idea_date,title,state,qualifier,next_gate
python3 src/feature_registry.py update-ledger
----

Miller can query the same file directly with `mlr --itsv`; it is optional and
is not required for deterministic ledger generation. Edit the TSV, not the
ledger's generated tables. The link:features_timeline.adoc[Features Timeline]
is a separate curated history, not generated from the database.

[[_cleanup_already_delivered_and_how_to_find_it_without_github]]
==== Cleanup already delivered, and how to find it without GitHub

* Board definitions, runtime selection, persistence and reporting were
  separated into readable product-owned components. Recovered `ccp.h` and
  the selectable extended `ccp7xf.h` are distinct; 7XF remains a substantial
  product CCP variant, not an unmodified upstream CCP.
* Added integration helpers/state use `_xtgv` or `xtgv`; constants and
  optional hooks use `XTGV_`. Examples include `_xtgvDiskActivity`,
  `_xtgvCPUBegin`, `xtgvBenchmarkStartedAt` and `XTGV_DRV_PORT`.
  Search the local source for `xtgv` case-insensitively; GitHub is not needed.
* Core seams are `XTGV_ABORT_REQUESTED`, `XTGV_Z80RUN_ATTRIBUTES`,
  `XTGV_MODIFIED_FILE_CLOSED` and `XTGV_CONFIG_GUEST_IDLE`. Callable bindings
  point to ordinary functions; macros remain where compile-time selection
  or declaration attributes require them. Product bindings live in
  `hardware/arduino_7xtgv/runcpm_hooks.h` and
  `abstraction_arduino_7xtgv.h`.
* Positive numeric composition tests such as `#if XTGV_TERMINAL` replaced
  negative Arduino/non-headless tests. `RUNCPM_HEADLESS` is obsolete;
  historical `RUNCPM_TARGET_*` board selectors remain a separate family.
* Inherited interface names such as `_getch`, `_putch`, `_HardwareIn` and
  `_sys_readseq` intentionally remain unchanged. Thus a tag search is a
  navigation aid, *not a complete diff*. Compare inherited function bodies
  too, including the portable `_sys_extendfile` repair. Public VT tool names
  and guest port numbers were not renamed by this cleanup.
* `VOL` again reads `INFO.TXT`; `DIR.7XF`, `VOL.7XF` and `DRV.7XF` belong to
  the 7XF extensions. Cleanup and compatibility fixes did not import CP/M 3.

The 261001 naming implementation record documents host checks, target builds
and Petr's W535 acceptance. Earlier plans showing `RUNCPM_*` hook names or
pending renames remain historical evidence, not today's naming contract.
The Linux SDL desktop now runs this same Arduino-oriented product fork;
successful desktop emulation does not establish upstream or CP/M 3 parity.

. Fetch and pin a fresh upstream commit when that work is authorized; record
  its full SHA/date. Compare recovered baseline, current 7xtgv-terminal and that
  pinned upstream separately. Do not overwrite the working reference or
  Petr's intentionally modified `RunCPM_comparison` checkout.
. First establish newer-upstream *CP/M 2.2* behavior in an isolated build,
  then port the cleaned hooks, board/runtime integration and 7XF variant.
  Check console/COM return, disk I/O, SUBMIT, catalog and INI ownership.
. Only then test experimental CP/M 3 separately. Its conditional console,
  CCP and file-close paths overlap our seams; a successful CP/M 2.2 test
  does not validate those paths. Record reproducible failures and, if useful,
  prepare narrowly scoped fixes for upstream discussion.
. Keep portable repairs separate from terminal-specific policy. A submodule
  or newer checkout alone does not resolve local semantic changes. No merge,
  CP/M 3 completeness claim or upstream submission is implied by this note.
